`автогейты (сборка → тесты → scope → анти-обход → прочие включённые) → sdlc-reviewer агент
(задача+план+diff, без истории исполнителя) → вердикт по таблице → verification-report-N-attempt-K.md`

Этап 6 из семи. Приёмка: пройти по листу и отдельно посмотреть, что могли обойти.

Предыдущий шаг: `/sdlc-chunk`. Следующий: `/sdlc-handoff`, если `passed=true`; иначе обратно
`/sdlc-chunk` с `retry_instruction`, либо эскалация человеку.

## Phase 0 — Вход

Определи номер попытки `k` — последняя строка таблицы «Попытки» в
`.sdlc/<slug>/chunk-<n>-journal.md`. Читай `.sdlc/<slug>/intent.md`, `.sdlc/<slug>/plan.md`,
`.sdlc/gates.md`, журнал chunk'а, `.sdlc/<slug>/chunk-<n>-attempt-<k>-diff.patch`
и `chunk-<n>-attempt-<k>-tests.txt`. Diff'а нет — верификация не начинается, отправляй на
`/sdlc-chunk <slug>`.

**Сверка артефакта с деревом** — до всего остального: перегенерируй `git diff <base_sha>`
(база из плана) и сравни с патчем попытки. Не совпал — артефакт этапа 5 не соответствует рабочему
дереву, это самостоятельное условие `passed=false`; дальше гейты прогоняются по **дереву**,
а патч остаётся уликой.

## Phase 1 — Автоматические гейты, до ревью

Сначала убедись, что **пять обязательных строк набора всё ещё «да»**: выключение минимума
записью в журнале среди витка означает «набор не собран» — останов и эскалация человеку,
а не прогон усечённого набора (это же механически проверяет `flow-verdict` в Phase 4).

Порядок фиксирован: **гейты идут перед ревью**, их результат не держится на промпте рецензента.
Гейты прогоняются **здесь заново** — файлы исполнителя лишь свидетельство этапа 5: вердикт,
посчитанный по текстовому файлу, который написал проверяемый, — это дешёвый обход, против
которого стоит «Анти-обход тест-гейта». Прогоняй по строкам `.sdlc/gates.md`, помеченным
«этап 6», **дословно тем же именем**, что в наборе:

1. **Сборка** — команда из колонки «Чем реализован», запусти сам. Падает → `❌`.
2. **Тесты** — команда из той же колонки, **запусти сам**, посчитай passed/failed. Любой failed
   → `❌`. Итог, разошедшийся с `chunk-<n>-attempt-<k>-tests.txt`, — отдельная находка в отчёт:
   вывод исполнителя не отражал реальность.
3. **Scope: файлы вне плана** — сравни файлы перегенерированного diff с `plan.files_to_touch`;
   пути `.sdlc/**` из сверки исключены. Есть файл вне списка → `❌`, если исполнитель
   не остановился и не спросил (Phase 4 `/sdlc-chunk`) — тогда это уже должно было прерваться
   раньше, и находка здесь означает, что прерывания не было.
4. **Анти-обход тест-гейта** — грепай diff на маркеры отключения тестов (`.skip`, `@Disabled`,
   `xit(`, закомментированные ассерты и т.п.), сверяй число тестовых деклараций до/после diff'а.
   Нетто-убыль без объяснения в plan → `❌`.
5. Все прочие включённые строки «этап 6» — **командой/проверкой из колонки «Чем реализован»
   набора проекта**: источник процедуры — набор, а не этот скилл (канонические образцы механик —
   в `templates/gates.template.md`). Исключение — «Сверка отчёта с набором»: она исполняется
   скриптом в Phase 4, здесь только зарезервируй её строку.

Гейт, включённый в наборе, но не запустившийся (нет команды, нет окружения) — статус `⏭`, и это
**не** `✅`: `⏭` без подписанной строки неприменимости роняет вердикт так же, как `❌`. «Не было
окружения» никогда не годится в неприменимость — это сама по себе причина `passed=false` и повтора.

Неприменимость может дать **только человек**, с причиной и именем — спроси, если рецензент или
скилл считает гейт бессмысленным для этого diff'а, не проставляй сам. Подпись из файла
записанных ответов (неинтерактивный прогон) помечается «источник: файл ответов».

**Гейты ранних этапов** (включённые строки набора с пометкой «этап 1», «этап 2», «этап 4»,
«этап 5») в отчёт тоже входят — не повторным прогоном, а **переносом статуса**: прогонялся ли
гейт на своём этапе и с каким итогом, со ссылкой на артефакт, где это видно («Готовность
задачи» → `readiness.md`, «Заполненность артефактов» и «Независимый вывод claims» →
`exploration-report.md`, «Полнота приёмочного листа» → `plan.md`, секция «Полнота листа»,
«Бюджет итераций chunk'а» → шапка и таблица попыток `chunk-N-journal.md`).
Без этого блока отчёт приёмки слеп к халтуре на ранних этапах ровно в той точке, где считается
вердикт. Гейт, который на своём этапе не прогонялся, получает здесь `⏭` — и роняет вердикт по
общему правилу. Гейты с пометкой «этап 7» сюда **не входят** — их этап ещё не наступил, они
отчитываются в handoff'е; требовать их статус здесь значило бы вердикт, который не бывает зелёным.

## Phase 2 — Независимый агент-рецензент

Запусти агента `sdlc-reviewer` (Agent tool, `subagent_type: sdlc-reviewer`; если тип недоступен —
`general-purpose` с явной инструкцией играть эту роль и её ограничения). На вход дай **ровно
четыре артефакта**: `intent.md`, `plan.md`, `gates.md`, содержимое перегенерированного diff
(совпавшего с `chunk-<n>-attempt-<k>-diff.patch`). Не
передавай ему свой рассказ о том, как шла реализация, и не давай истории вызовов исполнителя —
рецензент должен прийти к выводу заново, от diff'а и задачи, а не подтвердить чужой.

Дождись его ответа: статусы по каждому пункту приёмки, подтверждённые расхождения, поведение без
покрытия пунктом, scope в обе стороны, инварианты, регрессии.

## Phase 3 — Вердикт

Считай строго по таблице ниже — это рабочая копия правила из SDLC.md → этап 6 репозитория
Agent-SDLC; при расхождении копию чинят по первоисточнику. Две шкалы отдельно:

| Что случилось | Статус | Вердикт |
|---|---|---|
| гейт прошёл | `✅` | не роняет |
| гейт провалился | `❌` | `passed=false` |
| гейт включён, но не запускался | `⏭` | `passed=false`, если нет подписанной строки неприменимости |
| гейта нет в проекте (в долге) | без статуса | не роняет — он в долге |
| пункт приёмки подтверждён | `✅` | не роняет |
| пункт опровергнут | `❌` | `passed=false` |
| пункт не проверяем — держится на непройденной проверке | `⚠` | `passed=false` |

Плюс семь условий, роняющих вердикт независимо от таблицы: любое подтверждённое расхождение из
ревью, даже без соответствующего пункта приёмки; включённый гейт без строки в отчёте; строка долга
без закрытия (ни ручной проверки, ни принятого риска с подписью); нарушенный инвариант; регрессия;
путь плана, помеченный «не сделано»; перегенерированный diff, не совпавший с патчем попытки.

Пунктов приёмки без приоритета нет — любой `❌` роняет вердикт целиком, «неважных» не бывает.

**Action** по итогу:
- `passed=true` → `continue`, следующий шаг `/sdlc-handoff`.
- `passed=false`, причина устранима правкой в пределах текущего plan/files_to_touch и бюджет
  попыток (шапка журнала chunk'а) не исчерпан → `retry`, с `retry_instruction` — что именно
  чинить, конкретно и по адресу из ревью, не «поправь баги».
- `passed=false`, и либо бюджет итераций исчерпан, либо причина требует выйти за scope плана,
  либо повторный отказ того же гейта на другой задаче (см. «Когда остановиться и спросить») →
  `escalate` человеку.

## Phase 4 — Артефакт

Порядок фиксирован — обрыв сессии не должен оставлять рассинхрона:

1. Скопируй `templates/verification-report.template.md` из директории этого скилла в
   `.sdlc/<slug>/verification-report-<n>-attempt-<k>.md` — **по имени попытки, не перезаписывая
   отчёты предыдущих**, — и заполни: шапку (включая итог сверки перегенерированного diff
   с патчем), таблицу гейтов с фактическими командами, строки неприменимости (с именем
   утвердившего или явным «строк неприменимости нет»), пункты приёмки, находки ревью, scope
   в обе стороны, инварианты, регрессии, вердикт с полем «Кандидаты в запись о дефекте».
   Плейсхолдеров `‹…›` не оставлять.
2. **Сразу же** обнови колонку «Итог» строки попытки `<k>` в журнале chunk'а — до любого
   финального рассказа.
3. Прогони `tools/flow-verdict.py --at verify <корень проекта> <slug>` из директории этого
   скилла (python3). Это исполнение гейта **«Сверка отчёта с набором»** и механической части
   «Заполненности артефактов»: скрипт сверяет строки отчёта со строками «вкл=да, этап 6»
   набора, claims-цепочку intent↔plan↔отчёт, плейсхолдеры и записанные решения человека.
   Его провал — чини отчёт (или честно роняй вердикт), а не игнорируй; статус запиши в строку
   гейта из Phase 1 п. 7. Скрипта нет на месте — гейт `⏭` по общим правилам.

## Phase 5 — Дефект, который прошёл раньше

Ревью нашло поведение без покрытия пунктом или расхождение, которое должен был поймать гейт
более раннего этапа (готовность задачи, полнота артефактов)? Впиши это в поле «Кандидаты
в запись о дефекте» вердикта — **при любом action, включая retry**: дефект, зачиненный второй
попыткой, всё равно был пропуском листа или гейта. Сами записи заводит `/sdlc-handoff`, собирая
кандидатов по всем отчётам витка; там же человек решает ровно одно из трёх — конструкция,
проверка, принятый риск.

## Выход

- `passed`, `action`, путь к отчёту, число гейтов в `❌`/`⏭`, число пунктов в `❌`/`⚠`.
- При `retry` — `retry_instruction` и номер следующей попытки, следующий шаг `/sdlc-chunk <slug>`.
- При `escalate` — что именно эскалируется и почему автоматический повтор не годится.
- При `continue` — следующий шаг `/sdlc-handoff <slug>`.
