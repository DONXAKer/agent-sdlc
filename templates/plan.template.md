> В Runner одобрение конкретной редакции фиксирует операторский путь. Модель не подписывает решение человека.
> Используй только сохранённые ответы. Строки-образцы ответами не являются.
> Если ответов нет, укажи «Ответов человека нет».

> Этап 4. Агент заполняет план. Человек заполняет поле «Одобрение».
> Список `files_to_touch` используется для сравнения с фактическим diff. Правила: SDLC.md → этап 4.

- **Задача:** `intent.md` (‹название витка›)
- **Вход:** отчёт разведки ‹да/нет› · отчёт по вопросам ‹да / шага не было›
- **База:** ‹base_sha — коммит, от которого пойдёт diff›
- **Вид базы:** git
- **Одобрение:** ‹имя› · ‹дата› / **не одобрен — этап 5 не начинается**

Для базы рабочего дерева явно выбери `snapshot` до первой правки.

## files_to_touch

Под таблицей объясни каждое расширение и сужение. Пути `.sdlc/**` исключены из scope и в список не входят._

| Путь | Что делаем |
|---|---|

## Затронутые вызовы/сигнатуры

_Если меняется сигнатура, контракт или видимое поведение экспортируемого символа, проверь его вызывающих.
Используй список рантайма и поиск `Grep` по репозиторию. Для каждого адреса `путь:строка` создай строку.

## Уточнения и разрешение расхождений

_Ответы человека хранятся как неизменяемые факты в `clarification-report.md`.
Сошлись на ID ответа, исходный `claim-N` и решение. Вопрос и ответ повторно не переписывай.
Используй точные формы решений: `подтверждает claim-N без изменений`, `уточняет claim-N: <новая принятая формулировка>`, `заменяет claim-N: <новая принятая формулировка>`.
Если факт противоречив или ID отсутствует, вернись к человеку. План на одобрение не отправляй._
