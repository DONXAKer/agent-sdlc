# Отчёт разведки: PAY-412 — идемпотентность создания платежа

> Заполненный пример по [`../templates/exploration-report.template.md`](../templates/exploration-report.template.md).
> Адреса — `файл:метод`, без номеров строк: номер живёт две правки.

- **Задача:** [`intent.md`](intent.md) (PAY-412) — повторный запрос с тем же ключом не создаёт
  второй платёж.

## Стек и конвенции
- Язык / стек: Java 21, Spring Boot 3.2, JPA/Hibernate, PostgreSQL 15, Flyway

- Конвенции: контроллер не содержит логики — только валидация и вызов сервиса · доступ к БД только

## Найдено для переиспользования

_Идемпотентность в проекте уже реализована — для заказов, включая хранение ключей. Задача сводится
к переиспользованию готового механизма, а не к написанию своего._

| Символ | Где | Что делает | Как используем |
|---|---|---|---|
| `IdempotencyGuard` | `src/main/java/com/acme/common/idempotency/IdempotencyGuard.java` | `execute(key, endpoint, requestHash, Supplier<T>)` → `IdempotentResult<T>`. Владеет своей транзакционной границей и хранит ключи в **собственной таблице, общей для всех endpoint'ов** — поэтому у ключа есть колонка `endpoint`. Повтор с тем же телом → сохранённый результат; другое тело → `IdempotencyConflictException`; гонка → результат победителя, тоже как повтор | вызываем из `PaymentService.create` |
| `IdempotentResult` | `src/main/java/com/acme/common/idempotency/IdempotentResult.java` | `value()` + `isReplay()` — признак, что результат взят из сохранённого | контроллер по `isReplay()` выбирает `200` против `201` — claims 1, 4, 9 |
| `RequestHasher` | `src/main/java/com/acme/common/idempotency/RequestHasher.java` | SHA-256 канонизированного тела; используется `OrderService` | считаем `requestHash` — claims 6, 7 |
| `IdempotencyConflictException` | `src/main/java/com/acme/common/idempotency/IdempotencyConflictException.java` | смаплено на `409` в `GlobalExceptionHandler` | ничего не добавляем — `409` из claim 6 получается сам |
| `AbstractIntegrationTest` | `src/test/java/com/acme/support/AbstractIntegrationTest.java` | поднимает PostgreSQL через Testcontainers, чистит схему между тестами | базовый класс для `PaymentIdempotencyIT` — обязателен для claims 8–10 |

**Следствие для плана:** пять найденных символов дают пять шагов в форме «использовать». Своего кода
остаётся пробрасывание заголовка, выбор кода ответа по `isReplay()` и ветка «ключ пустой».

**Миграция не нужна.** Таблица ключей у guard'а уже есть и общая; новый endpoint отличается только
значением колонки `endpoint`. Своя таблица потребовала бы править `common/idempotency` — файл вне
«Что придётся тронуть», то есть сработавшее стоп-условие.

_Ничего подходящего не найдено: нет_ — искали и нашли, таблица выше. Это утверждение о проведённом
поиске, поэтому `н/п` здесь не подходит: содержание у поля есть.

## Точка правки

- `src/main/java/com/acme/payments/service/PaymentService.java:create` — сюда, а не в контроллер: гарантия «один платёж» должна
  накрывать все вызовы сервиса, а не только HTTP-путь. Guard владеет своей транзакционной границей,
  поэтому метод сервиса своей `@Transactional` не получает: и при обычном вызове, и при пустом ключе
  `Supplier` исполняется внутри границы, открытой guard'ом, — атомарность сохранения платежа и
  публикации события на этих путях сохраняется.
- **Путь проигравшего в гонке этим не покрыт.** Конфликт по уникальному ключу переводит транзакцию
  в rollback-only, так что результат победителя guard читает уже в новой границе, и утверждать
  что-либо про атомарность публикации на этом пути по прочитанному нельзя: propagation и способ
  публикации внутри `common/idempotency` разведка не разбирала, а править этот файл нельзя.
  **Это пропуск в приёмочном листе, а не риск:** claim на однократную публикацию события в гонке
  нужен, и он вынесен в блокирующий вопрос ниже — до ответа человека виток не стартует.

## Риски

- `IdempotencyCleanupJob` чистит таблицу ключей по списку endpoint'ов в своей конфигурации. Новый
  endpoint в список не добавлен, поэтому его строки не удаляются никогда и таблица растёт. Вопрос
  вынесен в задачу как открытый и осознанно отложен — принятый риск, а не дефект реализации.
- `PaymentRetryScheduler` вызывает `create` без ключа: ретраи неуспешных платежей идемпотентностью
  не покрыты. Это второй источник дублей, и claim'а на него нет — но он **назван в «Чего не делаем»**
  задачи («не покрываем идемпотентностью вызов из `PaymentRetryScheduler`… это следующий виток»),
  то есть отложен осознанно. Риск остаётся риском: следующий виток его закрывает.
- Смена сигнатуры `create` задевает планировщик. Он внесён в «Что придётся тронуть»: попутный файл, который
  не внесли в список, — это сработавшее Stop Condition, а не мелочь.
