# Guided: выполнение малых задач одной локальной моделью

Статус: экспериментальный профиль Runner. Режим включается явно только для новой задачи.
Основа: проработка v3 и семь этапов SDLC. Завершение требует проверки поведения по согласованной редакции требований.

## Общий принцип: модель решает — рантайм пишет

Модель выбирает значения из схем рантайма и предлагает новое содержимое.
Рантайм формирует фрагменты исходников, точные цитаты и карты ссылок по исходным данным.
Модель не должна повторно воспроизводить показанные байты для подтверждения совпадения.
Для `whole-file` действует отдельный формат предложения полного файла, описанный ниже.
Правила рантайма должны быть предметно-нейтральными. Не добавляй эвристики для отдельной задачи или фикстуры.

## Ответственность

Человек сообщает отсутствующие бизнес-правила и одобряет конкретный план.
Модель исследует код, предлагает изменения и анализирует результаты.
Рантайм хранит состояние, проверяет ограничения, применяет изменения, запускает зарегистрированные проверки и собирает доказательства.
Исполнение использует одну локальную модель на всех этапах.
Для независимого ревью можно назначить отдельный маршрут `provider:model`, отличный от исполнителя.
Без такого маршрута саморевью является справочным. Переход к более сильной модели не считается успехом этого профиля.

## Цикл Деминга: Plan → Do → Study → Act

### Plan

1. Сохрани исходный запрос.
2. Получи проверяемые требования и основания из исследования.
3. Выясни недостающие бизнес-правила.
4. Для каждого шага укажи файл, символ, действие, требования, проверку, ожидаемый результат и зависимости.
5. Символ выбери из закрытого списка карточек. Новый символ пометь `isNew`.
6. Для каждого адреса вызывающего укажи включение в `files_to_touch` либо совместимость без правок с причиной.
7. Проверь план и получи одобрение человека.

Адреса вызывающих формирует рантайм из индекса проекта.
Рантайм объединяет зависимые шаги и шаги одного файла в группы. Контракт проверяется вместе с потребителями.

### Do

Передай модели одну группу, согласованные требования, исходники с хэшами и карточки символов.
Модель возвращает прогноз и предложение в выбранном представлении правки.
До записи рантайм проверяет все операции и разрешения. Затем он симулирует всю группу.
После успешной проверки рантайм применяет группу с журналом восстановления.

### Study

После всей группы выполни зарегистрированные проверки.
Сохрани прогноз, фактический результат и редакции требований и кода.
Отсутствие среды или пропуск проверки не дают положительного результата.

### Act

При расхождении передай модели результат проверки для изменения гипотезы.
Ремонт выполняй по правилу «Ремонт только с новым входом».
Если ремонт исчерпан, раздели группу или эскалируй проблему.
Неразрешённая ошибка останавливает задачу и блокирует следующие группы.
Изменение процесса обосновывай серией измерений. Один успешный прогон не меняет стандарт.

Финальный verify повторно проверяет требования и код.
Вердикт вычисляет рантайм по гейтам verify, скрытым тестам бенча, проверкам честности и сверке diff с деревом.
Находки отдельного маршрута ревью могут блокировать завершение. Саморевью остаётся справочным.

## Операции этапа chunk

В guided v5 поле `editRepresentation` задаёт формат правки.
По умолчанию используется `typed-ir`. Модель возвращает типизированные узлы поддерживаемого подмножества TS/JS.
Рантайм компилирует узлы в операции. Неподдерживаемая конструкция получает явный отказ.
Произвольный код в строковом поле не заменяет IR.

В пределах разрешений доступны механические операции `rename`, `delete`, `ensure_import`, `ensure_reexport`.
Одобренное механическое действие рантайм может выполнить без запроса модели.

### Представление whole-file

Режим включается явно через `editRepresentation: "whole-file"`.
Ответ модели содержит `content`, `prediction` и `evidenceIds`.
Режим требует движок v5, привязанный файл и отсутствие split. Существующий файл должен быть разрешён для такого предложения.
Чисто механические правки сохраняют отдельный протокол.
Поддерживаются `.ts`, `.mts`, `.cts`. Для текстовых документов используется привязанный `replace_text`.
До записи рантайм проверяет хэш исходника, целостность ответа, синтаксис и разрешения всей группы.
Предложение полного файла сохраняет согласованный scope, требования к доказательствам и применимые гейты.

### Символьные операции

Ниже описан символьный протокол, а не JSON-формы `typed-ir`.
Прежние байт-точные SEARCH/REPLACE упразднены. Позиции символов рантайм определяет по показанным карточкам.

- `replace_body {file, symbol, body}` — заменить тело символа или полное объявление.
- `insert_after {file, anchor, body}` — вставить содержимое после символа.
- `insert_before {file, anchor, body}` — вставить содержимое перед символом.
- `rename {file, symbol, newName}` — переименовать символ.
- `delete {file, symbol}` — удалить символ.
- `create_file {file, body}` — создать новый файл, указанный в плане.
- `ensure_import {file, from, names[]}` — обеспечить импорт имён.
- `ensure_reexport {file, from, names[]}` — обеспечить реэкспорт имён.

Для вставки используй `anchor` из показанной карточки.
Переименование охватывает текущий файл и разрешённые файлы группы с распознанным импортом модуля.
Это ограниченное переименование. Остальных потребителей учитывай в плане и проверках.
Объединение имён поддерживает определённые формы именованных import/export. Поддержка всех форм модулей не заявляется.

### Инварианты выполнения

- Шаги объединяются в транзакционные группы `workItems`.
- Вся группа симулируется до записи.
- Журнал откатывает только известные собственные байты рантайма.
- Полный файл принимается только в разрешённом `whole-file`.
- Результат проходит синтаксическую проверку TypeScript.
- Гейты запускаются после всей группы.
- Наблюдения связываются с редакциями кода.

Байт-точное совпадение SEARCH и уникальность SEARCH-фрагмента больше не являются нормами этого профиля.
Вместо остановки «не исправлено за N попыток» действует ограниченное восстановление с новым входом.

## Poka-yoke: предотвращение ошибок конструкцией

| Ошибка | Ограничение рантайма |
|---|---|
| Модель переписала план или решение человека | Отдельные защищённые артефакты; одобрение только через операторский путь |
| Правка чужого файла | Белый список группы и плана, проверка пути и симлинков |
| Замена по старому коду | Хэш исходника; символ и позицию резолвит рантайм из показанной карточки |
| Вымышленный символ или склейка имён | Закрытый список символов из карточек исследования; поле — одиночное значение; новый символ только с `isNew` |
| Повтор имён в поддерживаемой форме import/export | `ensure_import` / `ensure_reexport`: объединение имён рантаймом |
| Потеря файла при переписывании | Ограничения представления правки, проверка хэша, scope и синтаксиса до записи |
| Половина группы применена до отказа | Все разрешения и симуляция группы до записи; журнал восстановления до первой записи |
| Потеря внешней правки при откате | Восстанавливаются только известные версии собственных изменений |
| Успех без изменения там, где оно не нужно | no_change разрешён, но проверки и финальная приёмка обязательны |
| Зелёный результат от старого кода | Привязка доказательств к редакциям и повторная проверка при возобновлении |
| Бесконечные исправления | Ремонт только с новым входом; ограниченные повторы, чтения и время |
| Саморевью как основание вердикта | Вердикт считает рантайм; ревью исполнителя — только справочный отчёт |
| Человек выполняет инженерную работу за модель | Стенд отвечает только известными бизнес-фактами; неизвестный вопрос остаётся без ответа |

На задачу отводится 30 минут активного времени. Ожидание человека не учитывается.
Счётчик сохраняется между этапами. Бюджет ограничивает работу, но не гарантирует успех.
После перезапуска рантайм восстанавливает незавершённую группу.
Если внешний процесс меняет те же файлы, может потребоваться остановка и разбор конфликта.

## Ремонт только с новым входом

Допускается один повтор по той же схеме.
Следующий ремонт требует диагностики отказа, суженной схемы и релевантного фрагмента.
Без нового входа раздели группу через split или эскалируй проблему.
Для chunk допускаются одна повторная выборка и адресные ремонты с новым входом.
Для plan допускается до трёх адресных ремонтов.
Повтор без изменения условий расходует время и не устраняет причину отказа.

## Приёмка профиля

План пилота: Qwen 8B, Granite 8B, Gemma 12B.
Задачи: freeship, config-default, two-right-answers, wrong-diagnosis.
Для legacy и guided выполни по три повтора. Используй одинаковые проработку v3, модель и банк ответов.
Сохраняй версию исходников, условия, время и все неудачи.

Успех требует финальной приёмки, всех скрытых проверок, соблюдения времени и отсутствия нарушений честности.
Ошибку среды учитывай отдельно. Целевой порог — минимум 80% на каждой модели; он пока не подтверждён.
После пилота нужны шесть моделей, восемь задач, пять повторов и отдельный отложенный набор.
Отложенные задачи нельзя использовать для настройки.
До этой проверки guided не становится режимом по умолчанию.
Результаты известных задач не доказывают пригодность любой модели.

Основания: [Deming Institute — PDSA](https://deming.org/explore/pdsa/), [Lean Enterprise Institute — poka-yoke](https://www.lean.org/lexicon-terms/poka-yoke/).

## Закрытие и ожидание оператора

Независимое ревью свободного хода допускает максимум два запроса исправления контракта ответа.
Каждый запрос содержит ошибки последнего ответа. Найденные дефекты и неопределённости должны сохраниться.
Только полный валидный ответ подтверждает выполненное ревью. Отклонённые ответы сохраняются как справочные.
Ремонт исправляет форму ответа. Он не предназначен для повторной оценки ради положительного результата.
Конвейер `reviewFill` сохраняет прежний протокол.

Зелёный вердикт относится к проверенному патчу. Если патч изменён, повтори Verify.
При свежем отрицательном вердикте оператор выбирает доработку или эскалацию.
Ожидание оператора отображается отдельно от выполнения этапа. Указывается время начала ожидания.
Истечение времени не заменяет решение человека.

## Бюджет средовых повторов

Завершённый Verify с `blocked_env` увеличивает серию средовых отказов одного chunk.
Повторный расчёт внутри одного прогона серию не увеличивает. Другой исход сбрасывает серию.
Номер попытки после `blocked_env` сохраняется.
По умолчанию третий средовой отказ подряд получает `escalate`.
Оператор восстанавливает среду и повторяет Verify либо оформляет обрыв.
Восстановление подтверждается свежим прогоном. Сброс счётчика не заменяет проверку.

Настройка располагается в таблице «Набор» `.sdlc/gates.md`:

| Гейт | Вкл | Где отчитывается | Чем реализован |
|---|---|---|---|
| Бюджет средовых повторов | да | вне витка | 3 |

Это настройка рантайма без команды проверки. Допустимо целое положительное число до 20.
При отсутствующей, выключенной или некорректной настройке используется 3.
Серия хранится атомарно вне проекта рядом с вердиктами и сохраняется после перезапуска.
Отмена или ошибка до расчёта вердикта бюджет не расходует.
Повреждённое состояние требует восстановления файла. Молчаливый сброс запрещён.

## История изменений методологии

### 2026-10-18 — каноническое состояние и независимая приёмка

State-first включается отдельно. Он использует `agent-sdlc/state/v1` и сохраняет требования, гейты, попытки, решения и JSON-ревью в `state.json`.
При повреждении или подмене состояния возврат к Markdown-вердикту запрещён.
Прерванную запись восстанавливают по журналу известных байт.
Импортированные claims получают uncertain. Нужны новое одобрение плана и свежий Verify.

До Chunk оператор фиксирует независимо подготовленный набор вне проекта.
На Verify отдельный исполнитель запускает набор на снимке кандидата. Отрицательный результат блокирует сдачу независимо от ответа модели.
Изменение кода, требований, плана или набора делает соответствующие доказательства недействительными.
Происхождение набора и квалификацию проверяющего подтверждает оператор.

Первый адаптер поддерживает простые Node-команды и test/spec `.mjs`/`.cjs`.
Запуск выполняется в одноразовом Docker-контейнере без сети и Docker socket.
Кандидат и тесты доступны только для чтения. Модель не получает Bash/MCP.
Если поддерживаемого исполнителя нет, успешный результат невозможен. Запасного запуска на хосте нет.
Структурированное ревью требует маршрута, отличного от исполнителя. Старые режимы автоматически не переключаются.
Подробности: [state-first в Runner](https://github.com/DONXAKer/Agent-SDLC-Runner/blob/main/docs/state-first.md).

### 2026-10-18 — проверяемое завершение и экспериментальные маршруты

Guided v4 включался явно через `guidedEngineVersion: 4`. Версия по умолчанию тогда не менялась.
Успех требовал заполненных обязательных полей и проверки актуального контракта.
Подтверждение связывало документ с исходными запросами по хэшам. Изменение входа требовало новой проверки.
Неудачный ремонт и смена замечаний не означали успеха.

Восстановление ограничивалось бюджетом и требовало нового входа: диагностики, уточнённого контекста или суженной схемы.
Типизированный отказ указывал причину и этап восстановления. Он не отменял предусловия и одобрение.
Нераспознанные требования оставались непроверенными.
Символьные операции ориентировались на JavaScript/TypeScript. Распознавание требований сохранности ограничивалось поддерживаемыми русскими и английскими конструкциями.

Пилот task-loop использовал отдельный маршрут: задача и границы → чтение → правка → проверки → ремонт → итог.
`ready_for_review` требовал финального ответа и успешных проверок текущего дерева.
Любая правка делала доказательства недействительными. Статус не доказывал выполнение всех требований.
Скрытая приёмка выполнялась после остановки модели и не передавалась в ремонт.
Адаптер поддерживал доверенные Node-команды. Универсальная поддержка языков не заявлялась.

Результаты версий, параметров и отпечатков учитывались раздельно.
Прерванная серия или проверка компонента не заменяли полный виток.
Серия guided v4 от 13–14 октября дала 0/8 успешных витков. Улучшение относительно v3 не доказано.
Серия task-loop v2 дала local 7/8 и evidence 6/8. Evidence-режим не включался по умолчанию.
Лента связывала реальные операции, запросы и результаты. Отсутствующее событие не восстанавливалось как факт.

Подробности: [guided v4](https://github.com/DONXAKer/Agent-SDLC-Runner/blob/main/docs/guided-v4.md),
[task-loop](https://github.com/DONXAKer/Agent-SDLC-Runner/blob/main/docs/task-loop-pilot.md),
[наблюдение выполнения](https://github.com/DONXAKer/Agent-SDLC-Runner/blob/main/docs/execution-transparency.md).

### 2026-10-05/06 — редизайн «модель решает — рантайм пишет»

Серии guided-sample от 05.10 включали 26+ прогонов. Получены три одиночных успеха и 0/6 на финальных повторах.
Этапы Verify и Handoff не достигнуты.
Основные отказы: байт-точный SEARCH/REPLACE и расхождение карты плана с кодом.
Измеренная локальная 20B-модель не обеспечивала устойчивое воспроизведение показанных байт.

Изменения процесса:

1. В Chunk SEARCH/REPLACE заменили символьными операциями. Позиции и слияние импортов определял рантайм.
2. В Plan ввели закрытый список символов и предзаполненные адреса вызывающих. Новые символы помечались `isNew`.
3. В intent/ask цитаты заменили ссылками `{file, lines:[from,to]}`. Цитаты формировал рантайм.
4. Ввели ремонт с новым входом: одна повторная выборка chunk, затем адресные ремонты; максимум три ремонта plan.
5. Вердикт Verify передали рантайму. Саморевью стало справочным; блокирующие находки требовали отдельного маршрута.
6. Из норм удалили подсказки для конкретных задач.

Тогда сохранили гейты записи, WAL собственных байт, проверки честности и запрет полной перезаписи существующего файла.
Также сохранили одобрение редакции плана, 30 минут активного времени и одну модель исполнения.
Позднее явно включаемый `whole-file` изменил допустимое представление правки. Его текущие ограничения описаны выше.
