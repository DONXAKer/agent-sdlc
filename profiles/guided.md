# Guided: выполнение малых задач одной локальной моделью

Статус: экспериментальный профиль Runner, включается только для новой задачи.
Основа — проработка v3 и семь этапов SDLC. Критерий завершения — проверенное поведение
на согласованной редакции требований, а не заполненные документы.

## Общий принцип: модель решает — рантайм пишет

Модель никогда не воспроизводит байты, которые рантайм ей показал. Модель выбирает
из вариантов, построенных рантаймом (закрытые схемы значений, списки символов,
диапазоны строк), и генерирует только новое содержимое: тела функций, тексты
аргументов, формулировки. Всё, что требует совпадения с существующим кодом или
запросом — фрагменты исходников, цитаты, карты ссылок — материализует рантайм.
Рантайм не содержит эвристик под конкретную задачу: нормы этого профиля
предметно-нейтральны и не подстраиваются под отдельные фикстуры.

## Ответственность

Человек сообщает отсутствующие бизнес-правила и одобряет конкретный план. Модель
исследует код, предлагает изменения и анализирует результаты. Рантайм хранит состояние,
проверяет ограничения, применяет изменения, выполняет зарегистрированные проверки и
собирает доказательства. Одна локальная модель используется на всех этапах.
В конфиге может быть задан отдельный review-маршрут (provider:model, отличный от
исполнителя) для независимого ревью на этапе verify; без него ревью исполнителем
самим себя допускается только как справочный отчёт. Повышение до более сильной
модели не считается успехом этого профиля.

## Цикл Деминга: Plan → Do → Study → Act

1. **Plan.** Сохранить исходный запрос. Получить проверяемые требования и основания
   из исследования. Выяснить недостающие бизнес-правила. Собрать связный план:
   файл, символ, действие, требования, проверка, ожидаемый результат, зависимости.
   Символ каждого шага выбирается из закрытого списка, который
   рантайм строит из карточек исследования; новый символ оформляется пометкой
   `isNew`. Адреса карты вызывающих пред-заполняет рантайм из индекса проекта;
   модель заполняет по каждому адресу решение (учтён вызов в files_to_touch или
   совместим без правок, с обоснованием). Проверить план и получить одобрение человека. Рантайм объединяет
   зависимые шаги и шаги одного файла в группы: изменение контракта проверяется
   вместе с потребителями.
2. **Do.** Показать модели одну группу, согласованные требования и исходники с хэшами
   и карточками символов. Модель возвращает прогноз и операции над символами
   (см. «Операции этапа chunk»), а не байтовые замены. Рантайм резолвит позиции
   символов, сначала проверяет все операции и разрешения и симулирует всю группу,
   затем применяет её с журналом восстановления.
3. **Study.** Выполнить зарегистрированные проверки после всей группы. Записать
   прогноз, фактический результат, редакции требований и кода. Отсутствующая среда
   и пропущенная проверка не дают положительного результата.
4. **Act.** При расхождении модель получает результат проверки и меняет гипотезу.
   Ремонт допустим только с новым входом (см. «Ремонт только с новым входом»);
   при его исчерпании — переразбиение группы или эскалация. Неразрешённая ошибка
   останавливает задачу, следующие группы блокируются.
   Обучение процесса выполняется по серии измерений; один удачный прогон не меняет стандарт.

Финальный verify повторно проверяет требования и код. Вердикт считает рантайм из
гейтов этапа verify, скрытых тестов (в бенче), проверок честности и сверки diff с
деревом изменений. Модельное ревью не является уровнем вердикта: находки отдельного
review-маршрута могут быть блокирующими, ревью исполнителем самим себя — только
справочным отчётом.

## Операции этапа chunk

Протокол байт-точных замен SEARCH/REPLACE упразднён. Модель запрашивает изменения
операциями над символами; рантайм находит символ в исходнике по карточке, которую
сам показал, и материализует результат:

- `replace_body {file, symbol, body}` — заменить тело символа или символ целиком.
- `insert_after {file, anchor, body}` / `insert_before {file, anchor, body}` —
  вставить содержимое; `anchor` — имя символа из показанной карточки, позицию
  резолвит рантайм.
- `rename {file, symbol, newName}` — переименовать символ; рантайм переписывает
  идентификаторы в файле и разрешённых файлах группы с распознанным импортом модуля.
  Это не полное семантическое переименование проекта; остальные потребители должны
  быть учтены планом и проверками.
- `delete {file, symbol}` — удалить символ.
- `create_file {file, body}` — создать файл; только для новых файлов, названных
  в плане.
- `ensure_import {file, from, names[]}` / `ensure_reexport {file, from, names[]}` —
  обеспечить импорт или реэкспорт имён. Рантайм объединяет имена в поддерживаемой
  форме именованных import/export; это не универсальный анализ всех форм модулей.

Сохраняются инварианты выполнения: шаги группируются в транзакционные группы
(workItems); вся группа симулируется до записи; журнал восстановления откатывает
только собственные байты рантайма; полная перезапись существующего файла запрещена;
результат проходит синтаксическую валидацию TypeScript; гейты выполняются после
всей группы; наблюдения привязываются к редакциям кода.

Упразднены как норма: байт-точное совпадение SEARCH, требование уникальности
SEARCH-фрагмента и останов по счётчику «не исправлено за N попыток» — вместо него
действует правило «Ремонт только с новым входом».

## Poka-yoke: предотвращение ошибок конструкцией

| Ошибка | Ограничение рантайма |
|---|---|
| Модель переписала план или решение человека | Отдельные защищённые артефакты; одобрение только через операторский путь |
| Правка чужого файла | Белый список группы и плана, проверка пути и симлинков |
| Замена по старому коду | Хэш исходника; символ и позицию резолвит рантайм из показанной карточки |
| Вымышленный символ или склейка имён | Закрытый список символов из карточек исследования; поле — одиночное значение; новый символ только с `isNew` |
| Повтор имён в поддерживаемой форме import/export | `ensure_import` / `ensure_reexport`: объединение имён рантаймом |
| Потеря файла при переписывании | Запрет полной замены существующего файла |
| Половина группы применена до отказа | Все разрешения и симуляция группы до записи; журнал восстановления до первой записи |
| Потеря внешней правки при откате | Восстанавливаются только известные версии собственных изменений |
| Успех без изменения там, где оно не нужно | no_change разрешён, но проверки и финальная приёмка обязательны |
| Зелёный результат от старого кода | Привязка доказательств к редакциям и повторная проверка при возобновлении |
| Бесконечные исправления | Ремонт только с новым входом; ограниченные повторы, чтения и время |
| Саморевью как основание вердикта | Вердикт считает рантайм; ревью исполнителя — только справочный отчёт |
| Человек выполняет инженерную работу за модель | Стенд отвечает только известными бизнес-фактами; неизвестный вопрос остаётся без ответа |

На задачу отводится 30 минут активного времени; ожидание человека исключается.
Счётчик сохраняется между этапами. Это ограничение работы, а не обещание успешного решения.
После перезапуска незавершённая группа восстанавливается; одновременное редактирование
тех же файлов внешним процессом может потребовать остановки и разбора конфликта.

## Ремонт только с новым входом

Один повтор по той же схеме допустим. Дальше ремонтный запрос обязан нести новую
информацию: диагностику отказа, суженную схему ответа и показ релевантного фрагмента.
Ремонт без нового входа не выполняется — вместо него немедленное переразбиение
(split) группы или эскалация.

Лимиты: chunk — одна повторная выборка плюс адресные ремонты с новым входом, затем
split или escalate; plan — до трёх адресных ремонтов.

Обоснование: повтор без изменения условий — повторная выборка из того же
распределения ошибок; он не приближает решение и расходует бюджет времени.

## Приёмка профиля

Пилот: Qwen 8B, Granite 8B, Gemma 12B; freeship, config-default, two-right-answers,
wrong-diagnosis; по три повтора legacy и guided с одинаковой проработкой v3,
моделью и банком ответов. Сохранять версию исходников, условия, все неудачи и время.
Успех: финальная приёмка, все скрытые проверки, отсутствие нарушений честности и
соблюдение времени. Ошибка среды учитывается отдельно и не становится успехом.
Целевой порог — не менее 80% на каждой модели; он пока не подтверждён.

После пилота — шесть моделей, восемь задач, пять повторов и отдельный удержанный
набор задач, не использованный для настройки. До этого guided не становится режимом
по умолчанию. Результаты известных задач нельзя выдавать за обобщение на любую модель.

Основания: [Deming Institute — PDSA](https://deming.org/explore/pdsa/),
[Lean Enterprise Institute — poka-yoke](https://www.lean.org/lexicon-terms/poka-yoke/).

## Закрытие и ожидание оператора

Независимое ревью свободного хода получает не более двух запросов на исправление
контракта ответа. Каждый запрос содержит ошибки последнего ответа и требует сохранить
найденные дефекты и неопределённости. Только полный валидный ответ подтверждает факт
ревью; отклонённые ответы сохраняются как справочные. Это исправление формы, а не
повторная оценка кода ради зелёного результата. Конвейер reviewFill не меняется.

Вердикт verify считает рантайм: гейты этапа, скрытые тесты (в бенче), проверки
честности, сверка diff с деревом изменений. Ревью исполнителем самим себя не может
быть основанием красного вердикта и остаётся справочным отчётом. Блокирующими могут
быть только находки отдельного review-маршрута, если он задан в конфиге.

Зелёный вердикт относится к проверенному патчу. Если патч изменён, оператор повторяет
Verify; по свежему красному вердикту выбирает доработку или эскалацию.
Ожидание оператора отображается отдельно от выполнения этапа, с временем начала.
Истечение времени ожидания не заменяет решение человека.

## Бюджет средовых повторов

Завершённый прогон Verify с исходом `blocked_env` увеличивает серию средовых красных
одного chunk. Повторный расчёт вердикта внутри этого прогона не увеличивает серию.
Другой исход сбрасывает её. Номер попытки после `blocked_env` сохраняется.
По умолчанию третий средовой красный подряд получает `escalate`: оператор восстанавливает
среду и повторяет Verify либо оформляет обрыв. Исправление среды подтверждается свежим
прогоном, а не сбросом счётчика.

Настройка в таблице «Набор» `.sdlc/gates.md`, рядом с бюджетом итераций:

| Гейт | Вкл | Где отчитывается | Чем реализован |
|---|---|---|---|
| Бюджет средовых повторов | да | вне витка | 3 |

Это настройка рантайма, без команды проверки. Значение — целое положительное число;
потолок 20, отсутствующая/выключенная/некорректная настройка означает 3.
Серия хранится атомарно в защищённом состоянии рантайма вне проекта, рядом с вердиктами,
и переживает рестарт сервера. Отмена или ошибка до расчёта вердикта не расходует бюджет.
Повреждённое состояние требует восстановления файла и не обнуляется молча.

## История изменений методологии

### 2026-10-18 — каноническое состояние и независимая приёмка

Отдельно включаемый state-first использует `agent-sdlc/state/v1` и сохраняет
требования, гейты, попытки, решения и JSON-ревью в state.json. При повреждении или
подмене состояния возврата к Markdown-вердикту нет. Прерванная запись восстанавливается
только по журналу известных байт. Старые артефакты импортируются с uncertain claims;
прежний вердикт не доверяется, нужны новое одобрение плана и свежий Verify.

До Chunk оператор фиксирует подготовленный независимым проверяющим набор вне проекта.
На Verify отдельный исполнитель запускает его на снимке кандидата; отрицательный
результат блокирует сдачу независимо от текста модели. Изменение кода, требований,
плана или набора инвалидирует соответствующее доказательство. Происхождение набора
и квалификацию проверяющего подтверждает оператор, а не имя модели само по себе.

Первый адаптер — простые Node-команды и test/spec .mjs/.cjs в одноразовых Docker-контейнерах
без сети и Docker socket, с кандидатом и тестами только для чтения. Bash/MCP модели
не выдаются. Нет поддерживаемого исполнителя — нет зелёного результата; запасного
запуска на хосте нет. Требуется отдельный маршрут структурированного ревью, отличный
от исполнителя. Старые режимы не переключаются автоматически.

Протокол и ограничения: [state-first в Runner](https://github.com/DONXAKer/Agent-SDLC-Runner/blob/main/docs/state-first.md).

### 2026-10-18 — проверяемое завершение и экспериментальные маршруты

Guided v4 включается явно (`guidedEngineVersion: 4`); версия по умолчанию не
изменена. Успех этапа требует заполненных обязательных полей и завершённой
проверки актуального контракта. Подтверждение связывает документ с исходными
запросами по хэшам; изменение входа требует новой проверки. Неудачный ремонт
и смена замечаний рецензента не означают успешного завершения.

Восстановление ограничено бюджетом и требует нового входа: диагностики,
уточнённого контекста или суженной схемы. Типизированный отказ указывает причину
и этап восстановления, но не отменяет предусловия и одобрение человека.
Нераспознанные требования остаются непроверенными. Операции над символами
ориентированы на JavaScript/TypeScript; распознавание требований сохранности
ограничено поддерживаемыми русскими и английскими конструкциями.

Пилот task-loop — отдельный экспериментальный маршрут: задача и границы записи
человека → чтение → правка → зарегистрированные проверки → ремонт → итог.
`ready_for_review` требует финального ответа и зелёных проверок текущего дерева;
любая правка инвалидирует доказательства. Это не доказательство выполнения всех
требований. Скрытая независимая приёмка выполняется после остановки модели и
не передаётся в ремонт. Адаптер проверок пилота поддерживает доверенные
Node-команды; универсальная поддержка языков не заявлена.

Результаты разных версий, параметров и отпечатков исходников учитываются
раздельно. Прерванная серия и проверка отдельного компонента не заменяют
полный виток. Серия guided v4 от 13–14 октября дала 0/8 успешных витков;
доказательства улучшения относительно v3 нет. Evidence-режим task-loop
не включается по умолчанию: серия v2 дала local 7/8 и evidence 6/8.

Лента выполнения связывает реальные операции, запросы и результаты; отсутствие
события не восстанавливается как факт. Подробности и границы экспериментов:
[guided v4](https://github.com/DONXAKer/Agent-SDLC-Runner/blob/main/docs/guided-v4.md),
[task-loop](https://github.com/DONXAKer/Agent-SDLC-Runner/blob/main/docs/task-loop-pilot.md),
[наблюдение выполнения](https://github.com/DONXAKer/Agent-SDLC-Runner/blob/main/docs/execution-transparency.md).

### 2026-10-05/06 — редизайн «модель решает — рантайм пишет»

Причина: итоги серий guided-sample от 05.10 (26+ прогонов) — три одиночных успеха,
0 из 6 на финальных повторах, этапы Verify и Handoff не достигнуты. Доминирующие
классы отказов — дефекты байт-точного SEARCH/REPLACE и расхождение карты плана с
кодовой базой: локальная 20B-модель статистически не способна воспроизводить
показанные ей байты.

Суть редизайна:

1. Chunk: протокол SEARCH/REPLACE заменён операциями над символами (`replace_body`,
   `insert_after`/`insert_before`, `rename`, `delete`, `create_file`,
   `ensure_import`); позиции символов и слияние импортов материализует рантайм.
2. Plan: символы шагов выбираются из закрытого списка рантайма, а адреса карты
   вызывающих пред-заполняются рантаймом из индекса проекта (решение по каждому
   адресу — за моделью); новый символ оформляется `isNew` без проверки вхождения
   в код; склейки имён исключены структурно.
3. Intent/ask: дословные цитаты заменены ссылками `{file, lines:[from,to]}` на
   показанные карточки и запрос; цитату в отчёты рендерит рантайм.
4. Введено правило «ремонт только с новым входом»; лимиты сокращены (chunk — одна
   повторная выборка плюс адресные ремонты; plan — до трёх адресных ремонтов).
5. Verify: вердикт считает рантайм из гейтов, скрытых тестов, проверок честности и
   сверки diff с деревом; саморевью исполнителя — только справочный отчёт,
