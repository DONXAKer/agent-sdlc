# Agent-SDLC

Как разрабатывать с агентом так, чтобы можно было принять работу. Центральная мысль: **узкое место —
не написание кода, а приёмка.** Человек владеет целью, агент — исполнением.

```
ЦЕЛЬ → РАЗВЕДКА → ВОПРОСЫ → ПЛАН → CHUNK → ВЕРИФИКАЦИЯ → COMMIT
  ↑                                                          │
  └──────────────────────────────────────────────────────────┘
```

## С чего начать

1. **[`SDLC.md`](SDLC.md)** — вся методология: семь этапов, гейты, вердикт, зачем так. Один файл,
   читается подряд.
2. **[`example/`](example/)** — тот же процесс на живой задаче (Java/Spring), все документные артефакты.
   Виток не принят: ревью нашло дефект, интеграционные тесты не запустились. Артефакты
   этапа 5 (diff и вывод тестов) в пример не включены — они порождаются кодовой базой витка.
3. **[`templates/`](templates/)** — канонические формы документов витка.
   Копии внутри реализаций служат для установки. Изменяй исходные формы, затем запускай
   `python tools/distribution.py sync`, чтобы обновить оба комплекта.
4. **[`implementations/`](implementations/)** — готовые реализации методологии на конкретных
   инструментах.
5. **[`model-runs/`](model-runs/)** — результирующие карточки моделей: какая модель какой
   этап тянет, на общей фикстурной задаче, с метриками (время/деньги/скрытые тесты),
   сравнением с эталоном и приложенными артефактами. Матрица «модели × этапы» — в её README.

## Что защищает результат

- Человек задаёт приёмку; предложения ИИ имеют источник и становятся требованиями только после явного утверждения.
- Пункты приёмки имеют процедуры проверки; гейты выполняет программа, результаты относятся к проверенной редакции кода. Дополнительный независимый набор приёмочных тестов можно описать в `acceptance-checks.md`, но наличие бланка само по себе не создаёт защищённого исполнителя. В state-first Runner отдельный набор фиксирует оператор после подготовки независимым проверяющим; Docker-исполнитель использует read-only снимки без сети и Docker socket.
- План фиксирует последствия и принятые риски по правилам SDLC.md. Риски не отменяют пять обязательных гейтов; один файл не означает отсутствия риска. Автоматическая классификация низкого, обычного и высокого риска текущим Runner не заявляется.
- Записанное ограниченное разрешение плана позволяет автономные обратимые действия внутри scope без повторного согласования. Решения о цели, приёмке, разрушительных и внешних действиях остаются у человека.
- Модели допускаются к роли по испытаниям, включая пропуски дефектов и ложные замечания; native tool calling не обязателен при проверяемом исполнителе.
- Новую версию процесса сравнивают с baseline на отложенных задачах; правила меняет человек, а не метрика.

Нормативные детали — в [`SDLC.md`](SDLC.md), прежде всего в этапах 1, 4 и 6 и разделе калибровки. Реализация должна подтвердить эти защиты; наличие требования в документе само по себе не доказывает изоляцию или работоспособность.

Для проверки исполнения без модели в соседнем `Agent-SDLC-Runner` есть стенд
`npm run bench:simulate`: сценарные ответы проходят через настоящие компоненты рантайма.
PASS означает ожидаемое поведение, включая корректную остановку; готовность TaskLoop
к ревью не равна человеческой приёмке полного SDLC. Границы и запуск — в
[`test/README.md`](test/README.md#симулятор-реализации-runner).

## Реализации

Выбери реализацию под свой инструмент. Комплекты Codex и Claude Code находятся в этом репозитории.
Runner развивается отдельно. Каталог `runner-contract/` содержит контракт и проверяющие инструменты для рантайма.

| Вариант | Что это | Статус |
|---|---|---|
| [Codex](implementations/codex/README.md) | Десять скиллов `$sdlc-*`: общий запуск `$sdlc-run`, семь этапов, посев и ретроспектива. Четыре роли. Установка в проект или домашний каталог | Переносимый Markdown-флоу без Runner. Есть автоматические проверки комплекта. Живой полный виток Codex пока не подтверждён |
| [Claude Code](implementations/claude-code/README.md) | Девять скиллов `/sdlc-*`: семь этапов, посев и ретроспектива. Четыре субагента и hook. Установка в `~/.claude/` | Есть сквозной пример и e2e-раннер. Hook требует подключения в настройках проекта; его ограничения описаны в README реализации |
| Agent-SDLC-Runner, отдельный репозиторий | Сервис с UI, политикой доступа, программным запуском гейтов и вычислением вердикта. Поддерживает Claude Agent SDK и собственный цикл вызова инструментов | Результаты запусков опубликованы в [model-runs/](model-runs/). State-first требует явного включения и адаптера; прежние витки автоматически не мигрируют |
| [Контракт Runner](implementations/runner-contract/README.md) | Схемы `state.json`, формат ревью и reference-проверки состояния, свидетельств и вердикта | Это контракт для исполнителя. Изоляцию, запуск команд и происхождение решений должен обеспечить конкретный рантайм |

В обоих комплектах роли `sdlc-claims`, `sdlc-locator`, `sdlc-reviewer` и `sdlc-methodologist`
отвечают за слепой вывод приёмочного листа, разведку, ревью и разбор методологии.
В Codex отдельный агент разделяет контекст, но не создаёт отдельную песочницу.
Защиты Claude Code hook и Runner в комплект Codex не входят.

State-first Runner хранит каноническое состояние в `state.json`.
Независимая приёмка использует защищённый набор проверок и одноразовые Docker-контейнеры.
Границы протокола описаны в [контракте Runner](implementations/runner-contract/README.md).

Другие варианты — CI-пайплайн с ручными паузами, другой агентный харнесс, чек-листы в трекере —
добавляются соседними директориями: методология одна, отличается только то, чем именно построены
гейты и кто держит артефакты.

## Артефакты витка

Правило одно: **нет артефакта — нет шага.** «Я исправил» без diff не принимается.

| Этап | Что появляется | Форма |
|---|---|---|
| _(до витка)_ | набор гейтов проекта | [`templates/gates.template.md`](templates/gates.template.md) |
| 1. Цель | задача + результат проверки готовности | [`templates/intent.template.md`](templates/intent.template.md), [`templates/readiness.template.md`](templates/readiness.template.md) |
| 2. Разведка | отчёт разведки | [`templates/exploration-report.template.md`](templates/exploration-report.template.md) |
| 3. Вопросы _(если были)_ | вопросы и ответы | [`templates/clarification-report.template.md`](templates/clarification-report.template.md) |
| 4. План | план с последствиями, принятыми рисками и записанным одобрением; acceptance-checks.md — дополнительный манифест независимой приёмки при наличии соответствующего исполнителя | [`templates/plan.template.md`](templates/plan.template.md), [`templates/acceptance-checks.template.md`](templates/acceptance-checks.template.md) |
| 5. Chunk | журнал chunk'а + git diff и вывод тестов попытки | [`templates/chunk-journal.template.md`](templates/chunk-journal.template.md) |
| 6. Верификация | отчёт приёмки (по попытке) | [`templates/verification-report.template.md`](templates/verification-report.template.md) |
| 7. Commit | коммит и передача контекста с записанной приёмкой | [`templates/handoff.template.md`](templates/handoff.template.md) |

## Чем это собирается

Методология не про стек — она задаёт шаги, артефакты и гейты. Минимум, без которого виток
не стартует: команда сборки, команда тестов, сверка diff со списком файлов из плана, проверка
на обход тестов и ревью независимым агентом. Остальное включается поверх; чего ещё нет — живёт в долге набора с подписью.

Готовые комплекты для Codex и Claude Code покрывают семь этапов, калибровку гейтов посевом и ретроспективу методологии.
Для мелких правок используй правила раздела «Мелкий виток» в [`SDLC.md`](SDLC.md).
Команды установки приведены ниже.

## Как получить и установить скиллы

Скачай репозиторий через Git:

```bash
git clone https://github.com/DONXAKer/agent-sdlc.git
cd agent-sdlc
```

Также можно скачать **Code → Download ZIP** на GitHub и распаковать архив.
Открой терминал в корне скачанного репозитория.

Для установки без полного репозитория используй архив своего инструмента из
[Releases](https://github.com/DONXAKer/agent-sdlc/releases) или артефактов workflow
[«Комплекты SDLC»](https://github.com/DONXAKer/agent-sdlc/actions/workflows/distribution.yml).
Релиз появляется после публикации тега `v<версия>`. Артефакты создаются при успешной сборке workflow.

Внутри комплекта Codex установщик лежит в корне. После распаковки перейди в `agent-sdlc-codex/`
и замени `python implementations/codex/install-codex.py` в командах ниже на `python install-codex.py`.
Для Claude Code перейди в `agent-sdlc-claude-code/` и выполни те же команды `bash install.sh`.
Файл `SHA256SUMS` содержит контрольные суммы ZIP.

### Codex

Требуются Python 3.11+, Git и авторизованный Codex с поддержкой пользовательских агентов.
Установщик добавляет десять скиллов и четыре роли. Runner и Bash не нужны.

1. Проверь доступность инструментов:

   ```bash
   python implementations/codex/install-codex.py --doctor
   ```

2. Установи комплект в свой проект. Замени путь на каталог проекта:

   ```bash
   python implementations/codex/install-codex.py --project "/путь/к/проекту"
   python implementations/codex/install-codex.py --project "/путь/к/проекту" --check
   ```

   Для установки всем своим проектам используй пользовательский каталог:

   ```bash
   python implementations/codex/install-codex.py --user
   python implementations/codex/install-codex.py --user --check
   ```

3. Открой новую сессию Codex в целевом проекте и запусти:

   ```text
   $sdlc-run demo Добавить проверку входных данных
   ```

   Для продолжения этого витка вызови `$sdlc-run demo`.

На Windows можно заменить `python` на `py -3.11`, на Linux и macOS — на `python3`.
Проектная установка размещает скиллы в `.agents/skills/`, а роли — в `.codex/agents/` целевого проекта.
При `--user` эти каталоги создаются в домашнем каталоге пользователя.
Отличающиеся файлы сохраняются в `.codex/sdlc-backup-*`. Конфигурация Codex и чужие скиллы сохраняются.

Подробнее: [комплект Codex](implementations/codex/README.md), включая ограничения и проверку установки.

### Claude Code

Требуются Claude Code, Python 3 и Bash с Unix-утилитами. На Windows используй Git Bash или WSL.
Выполни из корня репозитория:

```bash
bash install.sh
bash install.sh --check
```

Установщик размещает девять скиллов, четыре агента и hook в `~/.claude/`.
Прежние отличающиеся версии сохраняются в `~/.claude/sdlc-backup-<время>/`.
Подключи hook в настройках проекта по [инструкции Claude Code](implementations/claude-code/README.md#установка).
Открой новую сессию Claude Code в проекте и начни с `/sdlc-intent demo`.

### Как обновить комплект

В исходном клоне выполни `git pull --ff-only`. Затем повтори установку и проверку для выбранного инструмента.
Если скачивал ZIP, скачай свежий архив и запусти установщик из него.
После обновления открой новую сессию агента.

## Сборка комплектов

Этот раздел предназначен для сопровождения репозитория. Выполни команды из его корня.
Требуются Python 3.11+ и Git:

```bash
python tools/distribution.py sync
python implementations/codex/test_package.py
python check.py
python tools/distribution.py package
```

Команда `sync` обновляет установочные ресурсы Claude Code, копирует общие ресурсы в Codex и пересчитывает манифест Codex.
Тексты скиллов и роли остаются отдельными для каждой реализации.
Команда `package` проверяет актуальность ресурсов и упаковывает текущие файлы.
Она не синхронизирует ресурсы и не запускает полный набор тестов.

Результат в `dist/`:

- `agent-sdlc-codex.zip` — самостоятельный комплект Codex;
- `agent-sdlc-claude-code.zip` — комплект Claude Code с установщиком;
- `SHA256SUMS` — контрольные суммы архивов.

Каждый архив содержит `build.json` с ревизией Git, версией и контрольными суммами файлов.
Сборщик использует файлы реализаций и не читает пользовательские каталоги настроек.

Workflow [distribution.yml](.github/workflows/distribution.yml) запускает сборку на Linux, Windows и macOS.
Он публикует артефакты после проверок. При запуске на `main` отдельная задача создаёт PR синхронизации ресурсов, если обнаружены изменения.
Для этого разреши создание pull requests через GitHub Actions в настройках репозитория.

Для релиза обнови `version` в `implementations/codex/manifest.json` и выполни команды выше.
Сохрани изменения в коммите. Затем создай и отправь тег `v<версия>` для этого коммита.
Workflow проверяет совпадение версии и тега, проверяет актуальность установочных копий и публикует архивы в GitHub Releases.

Синхронизация и проверка ресурсов работают через Python без Bash: `python tools/distribution.py check`.
Каталог `dist/` содержит воспроизводимые архивы. При расхождении ресурсов упаковка останавливается.

Список распространяемых файлов задаётся в `distribution-files.json`. Новые ресурсы добавляй в этот список явно.
Синхронизация нормализует распространяемый UTF-8 текст в LF перед расчётом SHA-256.
Удаление затрагивает только файлы из `generated-resources.json`; прочие файлы сохраняются и не включаются в ZIP.
