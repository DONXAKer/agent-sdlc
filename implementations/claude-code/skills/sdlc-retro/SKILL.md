`корпус методологии → корпус трения проектов → sdlc-methodologist → триаж с человеком → отчёт`

Методология сама формулирует правило, из которого этот скилл выведен: «систему правим, когда
один и тот же отказ повторился на двух разных задачах» (`SDLC.md` → «Когда дефект проскочил»).
Проблема в том, что заметить повтор через несколько витков и, возможно, несколько проектов —
задача не для памяти между сессиями. `/sdlc-retro` — это тот же самый вопрос, поставленный не
после одного дефекта, а системно: собрать всё трение сразу и посмотреть, где методология сама
нуждается в правке, а не только код витка.

Скилл не меняет ни один файл методологии — он производит находки и решение человека по каждой,
записанные в отчёт. Саму правку `SDLC.md`/`SKILL.md`/шаблонов человек делает отдельно, обычной
сессией редактирования репозитория методологии (`./install.sh` после правки — как любое другое
изменение, см. `CLAUDE.md` репозитория).

## Phase 0 — Вход

Аргументы: `[<путь к репозиторию методологии>] [<путь к проекту> ...]`. Путь к репозиторию
методологии по умолчанию — там, откуда установлен `~/.claude/skills/sdlc-*` (обычно
`~/Code/Agent-SDLC`; если неочевидно — спроси человека один раз, не гадай по имени директории).
Путь(и) к проекту(ам) по умолчанию — текущая рабочая директория; можно передать несколько, если
человек хочет расширить эмпирический корпус за пределы одного проекта.

Для каждого проекта проверь `.sdlc/gates.md` — нет файла значит методология в этом проекте ещё
не заводилась ни разу, у него нечего собирать по Phase 2, скажи об этом прямо и не притворяйся,
что читал витки, которых не было.

## Phase 1 — Корпус методологии

Прочитай целиком:

- `SDLC.md` репозитория методологии;
- каждый `implementations/claude-code/skills/sdlc-*/SKILL.md`;
- каждый `templates/*.template.md` в корне репозитория (канонические, не установочные копии);
- `implementations/claude-code/agents/*.md` (оба существующих субагента).

## Phase 2 — Корпус трения

Для каждого переданного проекта, у которого есть `.sdlc/gates.md`:

1. Прочитай `.sdlc/gates.md` целиком — набор, «Долг», «Журнал изменений набора».
2. Найди все витки с `handoff.md` (`.sdlc/*/handoff.md`) — это завершённые или честно оборванные
   витки. Для каждого прочитай `handoff.md` целиком и все `verification-report-*-attempt-*.md`
   рядом с ним.
3. Собери из этого **инвентарь трения** — не пересказ, а список конкретных случаев: записи
   о проскочившем дефекте (из `handoff.md`), строки «Долга», которые остаются висеть больше
   одного витка без изменения формулировки, гейты, давшие `❌`/`⏭`/ложное срабатывание, находки
   ревью (`sdlc-reviewer`), не покрытые ни одним пунктом приёмки. Список — то, что передаётся
   агенту как эмпирический корпус; не сокращай его до «показалось важным», агент сам ранжирует.

Витков с `handoff.md` нет вообще — так и скажи в Phase 4, эмпирический корпус этого проекта пуст,
это не ошибка скилла.

## Phase 3 — Агент

Запусти `sdlc-methodologist` (Agent tool) с двумя собранными корпусами целиком. Не пересказывай
их своими словами и не добавляй собственных предположений о том, что не так, — это его работа,
не твоя; ты только собрал вход. Дождись ответа: разбор по шести углам и сводная таблица находок
с предлагаемым действием (конструкция/проверка/принятый риск) и черновиком правки там, где агент
уверен.

## Phase 4 — Триаж с человеком

По каждой находке из сводной таблицы — `AskUserQuestion`, как в `/sdlc-handoff` с записью
о дефекте: ровно один из **конструкция / новая проверка / принятый риск**, с именем и датой.
Агент только предлагает — выбирает человек. Находка, с которой человек не согласен (методология
здесь работает как задумано, повтор случаен), — тоже валидный исход, запиши «отклонено» и почему
одной строкой, не спорь и не дожимай.

## Phase 5 — Отчёт

Заведи (при первом запуске) директорию `retros/` в корне репозитория методологии — рядом
с `example/` и `test/`, тем же уровнем, что и остальные не-`implementations/`-директории. Запиши
`retros/<дата>-<scope>.md` (`<scope>` — имя проекта или `multi-project`, если проектов было
несколько), не перезаписывая прошлые отчёты — как и остальные артефакты Agent-SDLC, ретро-отчёты
не затирают друг друга, история находок должна оставаться читаемой. Перед первым запуском
проверь `git log` репозитория методологии на упоминание «ретроспектива» — если там уже есть след
неформального разбора (например коммит `fix: … находок ретроспективы …` без файла-отчёта),
отчёт `/sdlc-retro` — первый персистентный такого рода, скажи это явно в шапке отчёта, не
делай вид, что продолжаешь несуществующую серию.

Структура отчёта — простая, без отдельного шаблона (по образцу `seed-log.md` у `sdlc-seed`:
не каждый внецикловый артефакт методологии нуждается в отдельном каноническом шаблоне):

```
# Ретроспектива методологии: <дата>

- Репозиторий методологии: <путь> · Проекты: <список путей, или «нет» для одного>
- Первый персистентный отчёт серии: да/нет (см. Phase 5)

## Находки

| id | Угол | Что | Адрес | Действие агента | Решение человека | Черновик правки |
|---|---|---|---|---|---|---|

## Отклонено
- <находка> — почему / нечего
```

## Выход

- Путь к отчёту в `retros/`.
- Число находок, из них — сколько привели к конструкции/новой проверке/принятому риску/отклонено.
- Если решение «конструкция» или «новая проверка» принято — явно назови, что правка `SDLC.md`/
  `SKILL.md`/шаблонов и `./install.sh` после неё — отдельный, следующий шаг, не часть этого прогона.
