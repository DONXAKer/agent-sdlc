# Повторная верификация и runtime-испытания

Это дополнительный протокол для переносимых профилей. Он дополняет свидетельства попытки и пакет `review_evidence.py`.
Он не разрешает автоматически возобновлять остановленную задачу. Существующие гейты и ручная приёмка сохраняются.

## Проверка поставки Codex

1. Выбери доверенную поставку методологии. Используй её `manifest.json` как явную точку сравнения.
2. Выполни `python profile_guard.py <корень установки> <manifest.json>` инструментом из этой поставки.
3. При отказе запусти её `install-codex.py --project <корень>` либо `--user`.
4. Задай `SDLC_PROFILE_MANIFEST` абсолютным путём к выбранному manifest перед prepare.
5. Повтори проверку. Затем вызови prepare обычной командой.

Проверка сопоставляет каждый skill, agent и tool с SHA-256 выбранной поставки.
Квитанция установки содержит `manifest_sha256`. Старые установки без этого поля считаются неопознанными.
Используемые пути возвращаются программой. Активный tools должен происходить из `.agents/skills/sdlc-verify/tools` этой установки.
Второй корень `.codex/skills/sdlc-*` блокирует подготовку. Сохрани его копию и явно устрани конфликт загрузки.
Для старых инструментов запускай проверку из новой доверенной поставки: старый инструмент не может проверить неизвестный контракт.
Prepare закрепляет результат проверки поставки в своей ready-квитанции.
Проверка не обращается к сети. Она доказывает соответствие выбранной поставке, а не существование самой новой версии.
Установщик сохраняет заменяемые компоненты в backup. Он не изменяет пользовательскую конфигурацию и архивы `.sdlc`.
Не используй обновление установки для изменения исторических квитанций или подмены приёмки.

## Отдельный verification_run

До prepare создай `verification-policy.json` внутри витка:

```json
{"version":1,"fix_id":"fix-one","candidate_budget":3,"verification_run_limit":3,"status":"active"}
```

Закрепи SHA-256 исходных байтов в плане: `**Политика повторной верификации:** <sha256>`.
Политика действует на весь виток и одно исправление `fix_id`. Новый chunk не создаёт новый бюджет.
Остановку обозначай `status: stopped`. Решение о возобновлении зафиксируй отдельно и проведи согласованную новую подготовку.
Не переписывай прежнюю политику для продолжения той же истории. Сохраняй прежний отказ и решение человека.

Сначала запиши обычную попытку. Затем выполни:

```text
python verification_runs.py <корень> <slug> <N> <K> <manifest.json>
```

Manifest использует формат `review_evidence.py`. Новые первичные файлы храни внутри служебного каталога витка.
Пустой `files` допустим для повторного запуска команды. Он не доказывает достаточность evidence.
Digest охватывает все наблюдаемые исходники, тесты, фикстуры, настройки, режимы файлов и объявленные цели `.sdlc`.
Команда проверки, layer, контекст команды, gates.md и gate-context.json также входят в digest.
Новый evidence-файл вне кандидата не считается исправлением кода. Новый тест или настройка изменяют кандидата.
Каждая запись `verification-runs/run-NNNN.json` содержит `candidate_digest`, `candidate_attempt`, `verification_run_id` и исходную попытку.
Счётчик исправлений вычисляется из всей истории обычных попыток write, включая попытки до первого verification_run.
Счётчик verification_run вычисляется из отдельной истории проверок всего витка. Политика закреплена историческим планом prepare.
В режиме политики write заранее проверяет бюджет и запрещает --force. Старые попытки без candidate_tracking не мигрируют автоматически.
Патч исходной попытки должен соответствовать текущему дереву. Команда и её контекст берутся из свидетельства попытки.
Вывод и первичные файлы копируются отдельно. SHA-256 связывает записи и обнаруживает изменение прежних файлов.
Параллельную запись блокирует каталог `.lock`. После аварии проверь незавершённый запуск вручную.
Два последовательных одинаковых отказа одного кандидата блокируют дальнейшую автоматическую проверку.
Дополнительно действует `verification_run_limit`. Смена chunk не позволяет изменить политику того же исправления.
Успешная команда сохраняет `acceptance: requires_review`. Она не устанавливает итоговый `passed`.
Этот журнал не заменяет обычный отчёт попытки, claims, независимое ревью, ручную приёмку или разрешение публикации.
Файловый переносимый профиль не защищает историю от произвольной записи владельца каталога. Runner должен обеспечить эту границу отдельно.

## Runtime-сеанс

Запусти приложение командой:

```text
python runtime_session.py <исходники> <хранилище вне исходников> <exe> [args...]
```

Для локального документа используй `runtime_session.launch(..., document=...)`.
Документ должен существовать внутри исходников. Квитанция закрепляет его путь и SHA-256.
Хранилище не может находиться внутри исходников или содержать их. Все пути проверяются до записи и очистки.
Каждый запуск получает новый каталог, `sessionId` и `instanceId`.
Квитанции `launch.json`, `started.json`, `ended.json` сохраняют exe, cwd, документ, PID и время запуска.
Аргументы и окружение процесса в квитанцию не записываются.
Диагностика передаётся приложению через `SDLC_RUNTIME_DIAGNOSTICS`; временные данные — через TMP/TEMP/TMPDIR.
Проверь реальный диагностический файл приложения и его SHA-256. Стандартный вывод сам по себе не доказывает размещение crash-пакетов.
Если приложение игнорирует cwd, используй его явный параметр диагностического пути и повтори контроль.
Для приложения с фиксированным каталогом журналов передай точные `diagnostic_roots` в `runtime_session.launch`.
Адаптер сохраняет только новые файлы из этих каталогов с уникальным sessionId в первых 64 КиБ.
Укажи sessionId в безопасном пути аргумента приложения. Адаптер не приписывает сеансу журналы только по времени создания.
Квитанция сохраняет исходный путь, SHA-256 и основание происхождения. Одинаковые байты из разных путей сохраняются отдельно.
Без подтверждённого размещения не заявляй изоляцию. Инструмент наблюдает изменения и не создаёт песочницу процесса.
`observed_clean` относится только к наблюдаемым исходникам и объявленным каталогам. Произвольные внешние записи он не исключает.
Изменение наблюдаемых исходников даёт `isolation: violated`. Scope продолжает отклонять файлы вне плана.
Не вводи blanket-ignore для crashes или диагностики. Не меняй baseline ради прохождения Scope.
Сохраняй исторические отказы, чужие dirty-файлы, прежнюю диагностику и исходные хэши.
`cleanup_temporary(storage, sessionId)` удаляет только собственный временный каталог завершённого сеанса.
Очистка требует полного совпадения инвентаря. Новые чужие файлы блокируют удаление.
Диагностика, рабочие файлы и квитанции сохраняются после ошибки процесса.
Не завершай чужие процессы ради проверки. Локальный пилот не разрешает upload, публикацию сцены или внешнее развёртывание.

## Объявление испытания

До запуска выполни `runtime_protocol.py declare <каталог протокола> <spec.json>`.
Объявление содержит следующие поля:

| Поле | Содержание |
|---|---|
| `runId`, `claim_id` | Уникальное имя испытания и канонический claim-ID |
| `revision` | `head_sha`, `diff_sha256` и `source_sha256` проверяемого кандидата |
| `initial_state`, `environment` | Исходное состояние и выбранные параметры среды |
| `inputs`, `expected`, `procedure` | Входная последовательность, ожидаемый результат и процедура |
| `readiness_state` | Наблюдаемое состояние готовности до ввода |
| `material_conditions` | Все существенные условия испытания |
| `nonmaterial_reasons` | Обоснование несущественных различий по имени параметра |
| `preparation`, `restoration` | Подготовка среды и отдельное восстановление состояния |
| `restart_required` | Нужна ли доказанная граница restart |

Разрешённые поля среды: `os`, `application_version`, `role`, `exampleVersion`, `camera`, `viewport`, `inset`, `character_position`, `scene_generation`.
До объявления вычисли `source_sha256` через `runtime_session.tree_digest(runtime_session.source_tree(root))`.
Каждый запуск независимо закрепляет HEAD и digest исходных байтов с режимами файлов. Finish сверяет их с объявлением.
Для игрового пилота фиксируй все применимые игровые поля. Существенные значения также включай в `material_conditions`.
Не включай секреты и полное окружение процесса. Фиксация камеры, teleport и RPC обозначаются как подготовка.
Они не подтверждают ходьбу, слышимость, настоящее касание или визуальную приёмку.
После подготовки и восстановления заново наблюдай готовность и существенные условия. Простая задержка не доказывает readiness.
Файл готовности содержит `sessionId`, `observedAt` с часовым поясом и наблюдаемое `state`.

## Завершение и сравнение

Выполни `runtime_protocol.py finish <каталог протокола> <observations.json>`.
Передай `revision`, `sessions` с каталогами квитанций, `conditions`, `ready`, `primary` и `outcome`.
Для каждого sessionId в `ready` укажи `path`, `sha256`, `expected`, `conditions_rechecked: true`.
Для каждого первичного файла укажи `path`, `sha256`, `sessionId`, `observedAt`.
Исходы различаются: `success`, `rule_rejection`, `setup_error`, `input_loss`, `dependency_failure`.
Подмена, отсутствие файла, другая ревизия, изменённые условия и неготовая среда отклоняются.
Restart требует разных instanceId с временем запуска и завершения первого процесса до запуска второго.
Повтор одного PID или одинаковые снимки не доказывают restart. Каждый сеанс требует собственных первичных файлов, включая состояние после restart.
Сравни результат командой `runtime_protocol.py compare <каталог до> <каталог после>`.
Изменение существенных условий делает before/after несопоставимым. Несущественные различия требуют обоснования в обоих объявлениях.
Compare заново сверяет исходное объявление, квитанции, readiness и первичные файлы с закреплёнными хэшами.
Закрепи JSON протокола и первичные файлы в пакете `review_evidence.py` для reviewer.
`acceptance: requires_review` означает готовность записи к ревью, а не успешную приёмку продукта.
