`выбор класса дефекта → посев в изолированной ветке → прогон гейтов → пойман? → откат → отчёт`

Зелёный гейт — недоказанное утверждение о самом себе: не бывает так, что гейт есть, а
чувствительность его никто не проверял. Этот скилл — реализация строки набора «Калибровка гейтов
посевом». Он работает **вне витка**: не на живой задаче, а между ними.

## Phase 0 — Предохранители

Посев — это намеренный дефект, поэтому изоляция обязательна:

1. Рабочее дерево чистое (`git status`) — иначе остановись: посев поверх незакоммиченной работы
   неотличим от неё же при откате.
2. Заведи ветку `sdlc-seed/<дата>` от текущего HEAD. Всё происходит в ней.
3. В конце ветка удаляется целиком — посев не попадает ни в какую живую ветку ни при каком
   исходе. Отчёт — единственный выживший артефакт.

## Phase 1 — Выбор посева

Классы — из `SDLC.md` → «Набор гейтов» (посев проверяет пару «гейт ↔ класс дефекта»):

| Класс дефекта | Какой гейт обязан поймать |
|---|---|
| инвертированное условие / удалённый guard | Тесты · Ревью независимым агентом |
| отключённый тест (`.skip`, `@Disabled`, закомментированный ассерт) | Анти-обход тест-гейта |
| файл вне плана | Scope: файлы вне плана |
| секрет в diff | Секреты в diff (если включён) |
| сломанная сборка (незакрытая скобка в неисполняемом пути) | Сборка |

Выбери один-два класса — не все сразу: непойманный посев должен быть атрибутируем одному гейту.
Человека спроси только если он сам хочет выбрать класс; иначе чередуй классы между запусками.

## Phase 2 — Посев и прогон

1. Внеси дефект минимальной правкой в ветке посева и **сразу закоммить его в ветке посева**
   (`git commit -m "seed: <класс>"`). Незакоммиченный посев при переключении веток переехал бы
   в рабочую — коммит делает это невозможным по построению. Запиши точный адрес (`файл:строка`)
   и класс.
2. Составь фиктивный `files_to_touch` (для scope-посева — файл, которого в нём нет).
3. Прогони гейты этапа 6 по строкам `.sdlc/gates.md` теми же командами, что `/sdlc-verify`:
   сборка, тесты, scope-сверка, анти-обход-греп, прочие включённые. Ревью-агента зови только
   для классов, которые ловятся ревью (инвертированное условие) — остальным хватает механики.

## Phase 3 — Итог и откат

- **Пойман** — гейт сработал: зафиксируй, какой и чем.
- **Не пойман** — дефект процесса, не прогона: гейт слеп к классу, который обязан ловить.
  Это кандидат в запись «конструкция / проверка / принятый риск» — решает человек, покажи ему
  находку через `AskUserQuestion`.

Откати: сначала `git status` **в ветке посева** — если посев почему-то не закоммичен, сбрось его
`git restore .` (и `git clean -fd` для новых файлов) до переключения; затем `git checkout`
рабочей ветки и удали ветку посева `git branch -D`. Финальная проверка: `git status` — дерево
чистое, `git log -1` — верхний коммит не содержит «seed:».

## Phase 4 — Отчёт

Допиши в `.sdlc/seed-log.md` (заведи при первом запуске) блок: дата, класс, адрес посева,
какие гейты прогнаны, пойман/не пойман и чем, решение человека по непойманному. Обнови дату
в колонке «Чем реализован» строки «Калибровка гейтов посевом» набора — по ней видно, когда
посев был в последний раз.

## Выход

- Класс посева, пойман/не пойман, каким гейтом, путь к `seed-log.md`.
- Непойманный посев — что человек решил (конструкция/проверка/риск) и куда это записано.
