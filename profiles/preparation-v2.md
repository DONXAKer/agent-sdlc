# Проработка задачи в Runner: версии 2 и 3

Новые витки используют версию 3. Версия 2 доступна для существующих витков и явного выбора при создании.
Витки без `preparation.json` сохраняют v1. Имя `preparation-v2.md` сохранено для совместимости.
Версия 3 хранит канонические данные документов и редакции их источников.

ИИ готовит требования, сценарии и план. Человек подтверждает поведение, существенные компромиссы и риски.
Этапы intent, exploration, clarification и plan допускают повторные проходы. Пригодные результаты исследования сохраняются.
До реализации нужны независимая проверка и подтверждение конкретной редакции требований и плана.

Используй входные артефакты как текущее состояние. Не создавай отдельный пересказ этих данных.
Формат ответа задаёт текущий запрос Runner.
При заполнении полей или guided верни значение либо JSON по указанной схеме. Документ сохраняет рантайм.
В свободном инструментальном режиме сначала прочитай исходники. Затем подготовь полный черновик и запиши одним `Write`.
Для точечного исправления по замечанию используй `Edit`.

Если правка не закрыла замечание, не повторяй тот же проход без новых данных.
Допускается один повтор по той же схеме. Затем ремонт требует диагностики отказа, суженной схемы и релевантного фрагмента.
Для плана допускается до трёх адресных ремонтов.
Если ремонт исчерпан, сохрани лучший полный черновик. Укажи оставшиеся препятствия и прекрати цикл.

## intent

Составь черновик `intent.md` по запросу пользователя. Укажи аудиторию, проблему, наблюдаемый результат и заданные границы.
Сохрани все заголовки и секции формы. Отвечай только на поля текущего запроса Runner.
Исходники решения исследуются на этапе explore. Указанные пользователем пути и тесты точно сохрани как вопросы к исследованию.
На intent не вызывай `AskHuman`. Существенные неизвестные запиши в «Открытых вопросах».

В «Что делаем» описывай наблюдаемое поведение.
Если пользователь отложил выбор способа до исследования, сохрани этот выбор как требование плана.
Не закрепляй предварительный вариант реализации как принятое решение.
Разделяй факты с источниками, предложения и предположения. Код описывает текущее поведение. Желаемое поведение определяет задача.

Предложи приёмку самостоятельно. Не требуй от человека писать её с нуля.
Не добавляй возможности ради числа пунктов. Число claims и `[edge]` определяется поведением и границами задачи.
Сохраняй только необходимые требования. Для каждого укажи один проверяемый сценарий и один контрпример.

Исследование допускает открытые вопросы к реализации. Метку `[исследование]` используй только для вопроса, блокирующего безопасное исследование.
Существенные неизвестные о поведении помечай `[блокирующий]`. Отложенные обратимые детали помечай `[неблокирующий]`.
Спрашивай только о недоступных из источников данных, которые меняют существенное решение. Укажи рекомендацию и последствия выбора.

В новых intent v2 заполняй `sdlc-json:acceptance` и `sdlc-json:basis` валидными JSON-массивами.
Markdown-таблицы вручную не создавай. Используй строковые поля:

- acceptance: `id`, `behavior`, `procedure`, `expected`;
- basis: `id`, `basis`, `scenario`, `counterexample`.

Каждый `claim-N` должен иметь ровно одну запись basis с тем же id.
Runner проверяет схему и строит таблицы. При рендеринге basis он ставит ID последним.

В guided основание задавай ссылкой `{file, lines:[from,to]}` на показанный исходник или исходный запрос.
Runner проверяет диапазон и формирует цитату.
При заполнении строкового basis следуй текущей схеме. Основание: исходный запрос, ответ человека или подтверждённое ограничение с источником.
Контрпример описывает правдоподобную ошибку, которую обнаружит проверка. Неприменимость объясни.
Первый проход допускает предварительную приёмку. До реализации она должна быть полной. Готовность вычисляет рантайм.

## explore

Исследуй текущий сценарий и вопросы, способные изменить решение. Исследование требуется даже для небольшой правки.
Runner передаёт ограниченные карточки исходников и тестов, выбранные по запросу и claims.
Анализируй только полученные карточки. Не называй прочитанным файл, которого среди них нет.

Сначала найди существующую реализацию и механизмы переиспользования. Затем проверь контракты, потребителей, тестовую инфраструктуру и ограничения.
В `exploration-report.md` сохрани карту кода, переиспользование, риски, границы разведки и вопросы.
Каждый существенный факт подкрепи адресом файла и символа либо другим проверяемым источником из карточек.
Не подменяй желаемое поведение текущим кодом.

Заполни «Что придётся тронуть» в `intent.md`. Список файлов предварительный. Границы задачи определяются поведением и ограничениями.
Если есть развилка, сравни реальные альтернативы. Укажи противоречия исходному пониманию и неизвестные, меняющие подход.
После обоснования существенных решений останови поиск. Оставшиеся неизвестные вынеси в вопросы или отложи с причиной.

Не читай всё дерево без конкретного вопроса. Не повторяй приложенные артефакты.
Каждый поиск свяжи с claim или границей. После ответа сохрани путь и символ. Перейди к следующему нерешённому вопросу.
Независимо выведенные требования являются кандидатами. Они не создают обязательств автоматически.
Не требуй отдельного подтверждения механических таблиц.

## ask

До вопроса проверь код, документацию и конфигурацию. Доступное исследование выполни самостоятельно.
Спрашивай о поведении, границах, совместимости, существенной стоимости или риске. Для каждого вопроса укажи рекомендацию и последствия.

Ответы сохраняются дословно в `clarification-report.md`. Пустой ответ не является согласием.
Вопросы и основания связывай с источником через `{file, lines:[from,to]}`. Runner проверяет диапазон и формирует цитату.
Обнови `intent.md` по ответам. До одобрения плана это черновик.
Сохраняй ID требований. Изменения формулировок делай явными.
Закрой отвеченные вопросы также в `exploration-report.md`. Сошлись на сохранённый ответ.

Неблокирующий вопрос можно отложить с причиной.
В этом профиле изменение scope оформляй новой редакцией того же витка. Получи подтверждение плана.
Не выдумывай ответ человека. Если ответы противоречат друг другу, предъяви конкретную развилку.

## plan

Перед планом сведи решения в актуальный `intent.md`.
Проверь цель, границы, требования, инварианты, сценарии, основания и контрпримеры.
Исполнитель и проверяющий используют это представление требований. Исходные запросы и ответы сохраняются отдельно дословно.
Отвечай на поля плана по одному. Runner собирает документ и оставляет одобрение человеку.

При уточнении сохраняй `claim-N`. Добавление и удаление пункта объясни в «Изменения требований».
Покажи отличие от предыдущей редакции.
Каждый ответ человека свяжи с требованием, границей или решением подхода в «Уточнения и разрешение расхождений».
Для организационного ответа не создавай искусственный claim.
Таблица имеет колонки `ID ответа | Исходный пункт | Решение`.
Используй ID `ответ-N` из входных данных. Решение должно соответствовать действующему `intent.md`.

До завершения закрой существенные вопросы. Не заменяй решение предположением или словом «обычно».
Сверь вопросы `intent.md` и `exploration-report.md` с ответами человека.
Отвеченные закрой со ссылкой на источник. Отложенные пометь `[неблокирующий]` и укажи причину.

Сохрани стандартные секции: подход, шаги, `files_to_touch`, покрытие claims, контекст-пакет, последствия, принятые риски и одобрение.
В guided выбирай символ из закрытого списка карточек исследования. Поле содержит одно значение.
Новый символ задавай как `{isNew: true, name}`.
Адреса вызывающих подставляет рантайм. Модель выбирает решение для каждого адреса.
В остальных режимах следуй текущей схеме. Не заявляй закрытый список, если его не передали.

Укажи контракты, изменения состояния, обработку ошибок, существующие механизмы и условия возврата к проработке.
Для каждого требования назови процедуру и ожидаемый результат из независимого основания.
Проверь контрпример. Если неверная реализация может пройти тест, усиль проверку.

Глубину плана выбирай по неопределённости и последствиям. Разбей работу на проверяемые части.
Не расписывай каждую строку кода. Не дублируй требования: ссылайся на `claim-N`.
Заполни обязательные разделы. Для неприменимого поля укажи `н/п` с короткой причиной.
Не создавай шаги для механики, уже выполняемой рантаймом.

После записи рантайм независимо проверит план.
Подтверждённые замечания исправь новым проходом plan либо вернись к исследованию или вопросам.
Покажи человеку изменения, существенные решения и риски.
Реализацию открывает только явное одобрение текущей редакции.
Готовность, хеш требований, подпись и историю редакций ведёт рантайм. Не заполняй их от лица человека.

## implementation

Текущий `intent.md` содержит согласованные требования. План задаёт реализацию и проверки. Обе редакции связаны с одобрением.
В guided формат правки задаёт текущая схема и профиль guided.
Для символьной операции модель выбирает символ показанной карточки и новое содержимое. Позицию определяет Runner.
В legacy используй инструменты текущего маршрута. Проработка v3 сама по себе не включает guided и не меняет протокол записи.

Если обнаружено противоречие требованиям, новый существенный контракт или изменение поведения, останови зависимую работу. Вернись к проработке.
Независимые части можно продолжить. Не меняй требования или ожидания тестов ради успешного прогона.
Проверяй код по исходному запросу, текущим требованиям, сценариям и контрпримерам.
Согласие реализации и написанных к ней тестов само по себе недостаточно.
