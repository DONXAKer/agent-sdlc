## Контракт этапа

- **Вход:** diff, вывод тестов и evidence попытки; `intent.md`, `plan.md`, `.sdlc/gates.md`, журнал chunk'а
- **Выход:** `verification-report-N-attempt-K.md`; «Итог» в журнале; `chunk-N-attempt-K-review.md` (ответ рецензента как есть)
- **Паузы человека:** только неприменимость гейта — её даёт человек; иначе пауз нет
- **Инструменты:** гейты — эталонными скриптами или командами набора; рецензент `sdlc-reviewer` под замком `.review-lock`
- **Останов:** diff не совпал с деревом; минимум выключен; ответ рецензента дважды невалиден → гейт `⏭`
- **Дальше:** `continue` → `/sdlc-chunk` (следующий chunk) или `/sdlc-handoff` · `retry` → `/sdlc-chunk` · `escalate` → человек

`автогейты (сборка → тесты → scope → анти-обход → прочие включённые) → sdlc-reviewer агент
(задача+план+diff, без истории исполнителя) → вердикт по таблице → verification-report-N-attempt-K.md`

Этап 6 из семи. Приёмка: пройти по листу и отдельно посмотреть, что могли обойти.

Предыдущий шаг: `/sdlc-chunk`. Следующий: при `passed=true` — `/sdlc-chunk` (следующий chunk),
если план оставляет пункты следующим chunk'ам, иначе `/sdlc-handoff`; при `passed=false` —
обратно `/sdlc-chunk` с `retry_instruction`, либо эскалация человеку.

## Кто исполняет фазы

Скилл писан для интерактивной сессии, где у агента есть оболочка. Под **исполняющим
раннером** (Agent-SDLC Runner и подобные) часть фаз выполняет программа ДО того, как
этап дойдёт до модели, и повторять их нечем: оболочки на этапе 6 у неё нет.

| Фаза | В сессии | Под раннером |
|---|---|---|
| Phase 0, сверка diff с деревом | агент | **рантайм**, факт приходит во вход этапа |
| Phase 1, прогон автогейтов | агент | **рантайм**, итоги приходят таблицей во вход |
| Phase 2, вызов рецензента | агент через Task | **рантайм** отдельным прогоном, отчёт приходит блоком |
| Phase 3, вердикт | агент по таблице | **рантайм**, чистой функцией по той же таблице |
| Phase 4.1–4.2, отчёт и «Итог» в журнале | агент | **рантайм** собирает шапку, гейты, ранние гейты и вердикт; агент возвращает только результат ревью |
| Phase 4.3, `flow-verdict.py` | агент | **рантайм** |
| Phase 5, кандидаты в запись о дефекте | агент | агент |

Раннер обязан сказать об этом в промпте этапа сам — читатель этого файла не должен
угадывать, под чем он работает. Работа модели под раннером — §1–§5 отчёта: пункты приёмки
со ссылкой на место, находки ревью, scope в обе стороны, инварианты, регрессии.

## Phase 0 — Вход

Аргументы: `<slug>` и опционально `<n>` — номер chunk'а (`/sdlc-verify <slug> [<n>]`);
без `<n>` бери chunk последнего журнала `chunk-*-journal.md`. Определи номер попытки `k` — последняя строка таблицы «Попытки» в
`.sdlc/<slug>/chunk-<n>-journal.md`. Читай `.sdlc/<slug>/intent.md`, `.sdlc/<slug>/plan.md`,
`.sdlc/gates.md`, журнал chunk'а, `.sdlc/<slug>/chunk-<n>-attempt-<k>-diff.patch`
и `chunk-<n>-attempt-<k>-tests.txt`. Diff'а нет — верификация не начинается, отправляй на
`/sdlc-chunk <slug>`.

**Сверка артефакта с деревом** — до всего остального:

```
python tools/attempt-evidence.py verify <корень проекта> <slug> <n> <k>
```

(из директории этого скилла — все инструменты методологии живут здесь, в `tools/`, и оба этапа
снимают diff одним и тем же способом: без `.sdlc/**`, с нетракованными файлами, байт в байт). `diff_matches_tree: false` —
артефакт этапа 5 не соответствует рабочему дереву, это самостоятельное условие `passed=false`;
дальше гейты прогоняются по **дереву**, а патч остаётся уликой. `evidence_present: false` —
патч и вывод тестов написал исполнитель, а не программа: в шапке отчёта строка «Свидетельства
попытки: написаны исполнителем», вывод исполнителя ни в одной сверке не участвует.

Затем — задача не переписана внутри витка: `python tools/intent-sections.py --check <корень> <slug>`
(снимок снял этап 1). `legal: false` — секции задачи изменены вне трёх законных правок без записи
об одобрении; это самостоятельное условие `passed=false` (`SDLC.md` → этап 6, условия вердикта).

Патч и запись о тестах — улики, а не свидетельства сами по себе: составлять их обязана
исполняющая программа из фактического дерева и фактического прогона (`SDLC.md` → «Свидетельства
производит программа, а не агент»). Если их составил агент этапа 5, они не значат ничего — измерено:
файл `tests.txt` со строками «PASS ✓» был написан моделью, ни разу не запускавшей тесты. Там, где
патч и гейты производит программа, командная строка рецензенту не нужна вовсе — проверка утверждений
по коду делается чтением.

## Phase 1 — Автоматические гейты, до ревью

Сначала убедись, что **строки обязательного минимума всё ещё включены** — в колонке «Вкл»
у них «да — минимум» (или legacy-«да» — механика принимает обе формы; канонических пять,
проект мог пометить и свои). Выключение
минимума записью в журнале среди витка означает «набор не собран» — останов и эскалация
человеку, а не прогон усечённого набора (это же механически проверяет `flow-verdict`
в Phase 4: канонический минимум зашит фолбэком, снятая пометка от проверки не освобождает).

Перед прогоном — preflight: `python tools/gates-preflight.py <корень проекта>` из директории
этого скилла. Неисполнимая команда включённого гейта — `⏭` с диагностикой «исполнить нечем» до
запуска, а для класса «Сборка»/«Тесты» — вход в `blocked_env` по правилам Phase 3, если всё
остальное зелёное.

Порядок фиксирован: **гейты идут перед ревью**, их результат не держится на промпте рецензента.
Гейты прогоняются **здесь заново** — файлы исполнителя лишь свидетельство этапа 5: вердикт,
посчитанный по текстовому файлу, который написал проверяемый, — это дешёвый обход, против
которого стоит «Анти-обход тест-гейта». Прогоняй по строкам `.sdlc/gates.md`, помеченным
«этап 6», **дословно тем же именем**, что в наборе:

1. **Сборка** — команда из колонки «Чем реализован», запусти сам. Падает → `❌`.
2. **Тесты** — команда из той же колонки, **запусти сам**, посчитай passed/failed. Любой failed
   → `❌`. Итог, разошедшийся с `chunk-<n>-attempt-<k>-tests.txt`, — отдельная находка в отчёт:
   вывод исполнителя не отражал реальность.
   Эталонные реализации гейтов лежат в `tools/gates/` этого скилла и печатают последней строкой
   JSON контракта (`gate`, `status`, `evidence`, `detail`, `missing_tool` — `SDLC.md` → «Контракт
   гейт-скрипта»): `scope.py outside|unchanged <корень> <slug> <патч>`, `anti_bypass.py <патч>`,
   `secrets.py <патч>`, `untracked.py <корень> <slug>`, `tests_claims.py <корень> <slug> <патч>`,
   а также `tools/base-check.py <корень> <slug> <n> <k>`. Набор проекта вправе назвать свою
   команду — тогда исполняй её; строки с эталоном исполняй эталоном. Статус — из JSON, цитаты —
   из `evidence`.
3. **Scope: файлы вне плана** — сравни файлы перегенерированного diff с `plan.files_to_touch`;
   пути `.sdlc/**` из сверки исключены. Файл в diff'е, которого нет в `files_to_touch`, роняет
   гейт — **кроме** файлов, чьё изменение зафиксировано в базе chunk'а
   (`.chunk-<n>-baseline.json`, `sdlc-chunk/SKILL.md` Phase 2) до его старта и чей хэш с тех пор
   не менялся: такой файл — чужая незакоммиченная правка в дереве, не работа chunk'а, и
   отчитывается отдельной строкой «вне плана, из базы chunk'а» — не `✅` и не `❌`. Файла в базе
   нет → `❌`, если исполнитель не остановился и не спросил (Phase 4 `/sdlc-chunk`) — тогда это
   уже должно было прерваться раньше, и находка здесь означает, что прерывания не было. Базы
   нет вовсе (chunk снят до этой правки методологии, либо проект её не завёл) — сверяй по
   голому diff'у, как раньше; объяснение «это осталось от прошлого витка» без базы задним числом
   не принимается.
4. **Анти-обход тест-гейта** — грепай diff на маркеры отключения тестов (`.skip`, `@Disabled`,
   `xit(`, закомментированные ассерты и т.п.), сверяй число тестовых деклараций до/после diff'а.
   Нетто-убыль без объяснения в plan → `❌`.
5. **Тесты красные на базе** (если включён) — `python tools/base-check.py <корень> <slug> <n> <k>`:
   тестовые hunk'и патча на `base_sha` обязаны дать **новые** падения относительно чистой базы;
   нет новых → `❌` (пункты, которые они закрывают, не доказаны — даже если база и так красная от
   чужого теста). Тот же прогон печатает `base_failures` — тесты, красные ещё на чистой базе: это
   «чужой падающий тест», не регрессия chunk'а, назови их в §5 отдельно.
5a. **Перезапись файла** (если включён) — по `diffstat.per_file` и `diffstat.deleted_paths` из
   `attempt-evidence.py verify`: файл из `deleted_paths` — удалён целиком; для остальных доля
   `deleted` к длине файла на базе (`git show <base_sha>:<путь> | wc -l`) ≥ порога (50 %,
   `sdlc-constants.json` → `overwrite_threshold_percent`). Такой файл обязан иметь в журнале
   chunk'а, секция «Перезапись файлов», строку с путём и именем человека. Нет строки → `❌`.
6. Все прочие включённые строки «этап 6» — **командой/проверкой из колонки «Чем реализован»
   набора проекта**: источник процедуры — набор, а не этот скилл (канонические образцы механик —
   в шаблоне набора: `templates/gates.template.md` рядом со скиллом sdlc-intent, он же в корне
   репозитория методологии). Набор задаёт способ, но **санкции канонических гейтов — норма**,
   и они не переопределяются набором: «Сверка тестов с claims» — тест без claim-id → `❌`,
   лист дополняет **человек** до вердикта; «Scope: нетракованные файлы» — необъяснённый
   нетракованный путь вне `.sdlc/**` → `❌`. Исключение — «Сверка отчёта с набором»: она
   исполняется скриптом в Phase 4, здесь только зарезервируй её строку.

**Статус гейта считается по артефакту прогона, а не по коду возврата команды** (`SDLC.md` →
этап 6): для «Тестов» — по отчётам прогона (`surefire-reports/*`, JUnit XML, вывод раннера), для
scope-гейтов — по перечню путей, который сам же цитируешь в отчёте. Команда, упавшая на отказ
инструмента («`git: not found`», «`java: command not found`»), не даёт права поставить `✅` —
только `⏭`: её код возврата свидетельствует о среде, а не о предмете гейта. Расхождение между
статусом builtin-реализации и артефактом того же прогона — самостоятельное условие `passed=false`
и отдельная строка находки, а не молчаливое доверие коду возврата.

Гейт, включённый в наборе, но не запустившийся (нет команды, нет окружения) — статус `⏭`, и это
**не** `✅`: `⏭` без подписанной строки неприменимости роняет вердикт так же, как `❌`. «Не было
окружения» никогда не годится в неприменимость — это сама по себе причина `passed=false` и повтора.

Неприменимость может дать **только человек**, с причиной и именем — спроси, если рецензент или
скилл считает гейт бессмысленным для этого diff'а, не проставляй сам. Подпись из файла
записанных ответов (неинтерактивный прогон) помечается «источник: файл ответов».

**Гейты ранних этапов** (включённые строки набора с пометкой «этап 1», «этап 2», «этап 4»,
«этап 5») в отчёт тоже входят — не повторным прогоном, а **переносом статуса**: прогонялся ли
гейт на своём этапе и с каким итогом, со ссылкой на артефакт, где это видно («Готовность
задачи» → `readiness.md`, «Заполненность артефактов» и «Независимый вывод claims» →
`exploration-report.md`, «Полнота приёмочного листа» → `plan.md`, секция «Полнота листа», «Разбор последствий» →
`plan.md`, секция «Последствия шагов»,
«Бюджет итераций chunk'а» → шапка и таблица попыток `chunk-N-journal.md`).
Без этого блока отчёт приёмки слеп к халтуре на ранних этапах ровно в той точке, где считается
вердикт. Гейт, который на своём этапе не прогонялся, получает здесь `⏭` — и роняет вердикт по
общему правилу. Гейты с пометкой «этап 7» сюда **не входят** — их этап ещё не наступил, они
отчитываются в handoff'е; требовать их статус здесь значило бы вердикт, который не бывает зелёным.

## Phase 2 — Независимый агент-рецензент

Перед запуском поставь замок ревью: `python ~/.claude/hooks/sdlc-guard.py --lock <корень проекта> <slug>`
— при подключённом hook'е он закрывает инструменты записи вне `.sdlc/` и мутирующие команды на
время ревью (артефакты витка — ответ рецензента, отчёт — писать можно). Сними его сразу после
ответа рецензента, до Phase 3: `python ~/.claude/hooks/sdlc-guard.py --unlock <корень проекта> <slug>`
(обычный `rm` под замком отклоняется). Оставленный маркер заблокирует следующий этап — deny
называет команду снятия.

Запусти агента `sdlc-reviewer` (Agent tool, `subagent_type: sdlc-reviewer`; если тип недоступен —
`general-purpose` с явной инструкцией играть эту роль и её ограничения). Перед запуском сверь силу моделей: модель исполнителя — поля `executor_model` и
`executor_model_source` в `chunk-<n>-attempt-<k>-evidence.json` (в сессии — самоотчёт исполнителя
через `--executor-model`, под раннером — факт рантайма), рецензента — `model:` frontmatter
`sdlc-reviewer`; порядок — `sdlc-constants.json` → `model_order` (haiku < sonnet < opus < fable).
Рецензент не сильнее, модель `unknown` или источник — самоотчёт — в колонку «Результат» строки
гейта «Ревью независимым агентом» пиши это явно («исполнитель opus (самоотчёт), рецензент opus —
превосходство не обеспечено»), гейт при этом остаётся тем статусом, который дал прогон:
оговорка — наблюдение для handoff'а и ретро, не подмена статуса.

На вход дай **ровно
четыре артефакта**: `intent.md`, `plan.md`, `gates.md`, содержимое перегенерированного diff
(совпавшего с `chunk-<n>-attempt-<k>-diff.patch`), плюс неизменяемую таблицу результатов
автогейтов. Таблица — факт рантайма, не пятый артефакт и не рассказ исполнителя. Не
передавай ему свой рассказ о том, как шла реализация, и не давай истории вызовов исполнителя —
рецензент должен прийти к выводу заново, от diff'а и задачи, а не подтвердить чужой.

Дождись **структурированного ответа рецензента**: статусы по каждому пункту приёмки,
подтверждённые расхождения, поведение без покрытия пунктом, оси плана, объявленные незатронутыми и опровергнутые diff'ом, scope в обе
стороны, инварианты,
регрессии и конкретный `retry_instruction`. Не проси его повторять шапку, гейты, ранние гейты,
неприменимость, `passed` или `action`: это факты и чистый расчёт рантайма, не мнение рецензента.

Ответ рецензента сохрани как есть в `.sdlc/<slug>/chunk-<n>-attempt-<k>-review.md` (улика попытки,
не перезаписывается) и проверь механически:

```
python tools/review-validate.py <корень проекта> <slug> <n> <k> <корень проекта>/.sdlc/<slug>/chunk-<n>-attempt-<k>-review.md
```

(путь ответа — от корня проекта; относительный инструмент ищет и от корня, и от cwd). Он принимает
ответ только если каждый claim имеет `id` из задачи, статус из словаря `passed|failed|uncertain|manual`
и доказательство, а каждая находка во всех четырёх массивах — kind своего массива и адрес из патча
(`файл:строка`, `файл:метод`, hunk, имя теста); контракт один с раннером — `verify-review-v1`. `valid: false` — один
повторный запрос рецензенту с перечислением `errors`; повторно невалидный ответ оставляет гейт
«Ревью независимым агентом» `⏭`, а вердикт считается по общим правилам. Скилл не дописывает
содержательные выводы за рецензента.

Строку про оси перенеси в §2 отчёта как есть. Она приходит из четвёртого угла рецензента и
роняет вердикт по тому же условию, что и любое подтверждённое расхождение, — отдельного условия
у неё нет.

**Состояние гейта читай из набора, а не из плана.** «Разбор последствий» выключен — в §2 строка
`н/п — гейт в наборе выключен`, и в таблице ранних этапов строки нет вовсе (у гейта в долге
статуса не бывает). Гейт включён, а секции «Последствия шагов» в плане нет либо её статус `⏭` —
это `⏭` в таблице ранних этапов, и он роняет вердикт: разбор не проводился. Вывод «секции нет,
значит гейт выключен» запрещён — он подменяет чтение набора догадкой и делает включённый гейт
невидимым ровно там, где считается вердикт.

## Phase 3 — Вердикт

Считай строго по таблице ниже — это рабочая копия правила из SDLC.md → этап 6 репозитория
Agent-SDLC; совпадение копии с первоисточником сверяет `tools/check-consistency.py` методологии. Две шкалы отдельно:

| Что случилось | Статус | Вердикт |
|---|---|---|
| гейт прошёл | `✅` | не роняет |
| гейт провалился | `❌` | **`passed=false`** |
| гейт включён, но не запускался | `⏭` | **`passed=false`**, если нет подписанной строки неприменимости |
| гейта нет в проекте | статуса не получает вовсе | не роняет — он в долге |
| пункт приёмки подтверждён по diff или тесту | `✅` | не роняет |
| пункт опровергнут | `❌` | **`passed=false`** |
| пункт не проверяем — доказательство держится на непройденной проверке | `⚠` | **`passed=false`** |
| пункт с тегом `[manual]` — по построению не проверяется этим этапом | `manual` | не роняет — уходит в handoff как открытая ручная проверка |

Плюс восемь условий, роняющих вердикт независимо от таблицы: любое подтверждённое расхождение из
ревью, даже без соответствующего пункта приёмки; включённый гейт без строки в отчёте; строка долга
без закрытия (ни ручной проверки, ни принятого риска с подписью); нарушенный инвариант; регрессия;
путь плана, помеченный «не сделано»; перегенерированный diff, не совпавший с патчем попытки;
задача изменена внутри витка вне трёх законных правок (`intent-sections.py --check`).

Пунктов приёмки без приоритета нет — любой `❌` роняет вердикт целиком, «неважных» не бывает.

**Action** по итогу:
- `passed=true` → `continue`. Следующий шаг: план оставляет пункты следующим chunk'ам
  (строка плана «Уходит следующим chunk'ам» называет chunk с номером больше текущего) —
  `/sdlc-chunk <slug>`; план закрыт — `/sdlc-handoff <slug>`.
- `passed=false`, причина устранима правкой в пределах текущего plan/files_to_touch и бюджет
  попыток (шапка журнала chunk'а) не исчерпан → `retry`, с `retry_instruction` — что именно
  чинить, конкретно и по адресу из ревью, не «поправь баги».
- `passed=false`, и либо бюджет итераций исчерпан, либо причина требует выйти за scope плана,
  либо повторный отказ того же гейта на другой задаче (см. «Когда остановиться и спросить») →
  `escalate` человеку.

## Phase 4 — Артефакт

Порядок фиксирован — обрыв сессии не должен оставлять рассинхрона:

1. Разложи бланк — `python tools/scaffold.py <корень проекта> verification-report <slug> --chunk <n> --attempt <k>`
   (из директории этого скилла): он кладёт `verification-report-<n>-attempt-<k>.md` **по имени попытки,
   не перезаписывая отчёты предыдущих**, и сам заполняет механику — шапку, строки гейтов по набору,
   таблицу ранних гейтов, строки `claim-N`, номер попытки и бюджет. Тебе остаётся содержательное: шапку (включая итог сверки перегенерированного diff
   с патчем), таблицу гейтов с фактическими командами, строки неприменимости (с именем
   утвердившего или явным «строк неприменимости нет»), ранние гейты и вердикт с полем
   «Кандидаты в запись о дефекте». Вставь структурированный ответ рецензента в §§1–5;
   его `retry_instruction` — в одноимённое поле, при необходимости дополнив фактической
   причиной упавшего гейта. `passed` и `action` вычисляются по Phase 3, а не берутся из
   ответа модели.
   Плейсхолдеров `‹…›` не оставлять.
2. **Сразу же** обнови колонку «Итог» строки попытки `<k>` в журнале chunk'а — до любого
   финального рассказа.
3. Прогони `tools/flow-verdict.py --at verify <корень проекта> <slug>` из директории этого
   скилла (python3). Это исполнение гейта **«Сверка отчёта с набором»** и механической части
   «Заполненности артефактов»: скрипт сверяет строки отчёта со строками «вкл = да / да — минимум, этап 6»

   Артефакт, байт в байт равный своей форме, заполненным не считается независимо от
   результата скана `‹…›`: бланк раскладывает сама программа, и проверка «файл есть» с этого
   момента ничего не доказывает.
   набора, claims-цепочку intent↔plan↔отчёт, плейсхолдеры, записанные решения человека и —
   при включённом «Разборе последствий» — адресатов исходов осей плана (`claim-N` есть в задаче,
   гейт включён, вопрос записан, риск в таблице).
   Тот же прогон сверяет **согласованность `passed` со статусами таблиц отчёта** — `passed=true`
   при хотя бы одной строке `❌`/`⚠` (без подписанной неприменимости) невозможен механически, не
   только по правилу из Phase 3. Провал — чини отчёт (или честно роняй вердикт), а не игнорируй;
   статус запиши в строку гейта «Сверка отчёта с набором», зарезервированную в Phase 1 п. 5.
   Скрипта нет на месте — гейт `⏭` по общим правилам.
4. **Слепые зоны скана заполненности — твои, не рецензента**: скрипт не видит `‹…›` внутри
   цитат-«ёлочек» и fenced-блоков. Пробеги глазами ВСЕ артефакты витка (журнал chunk'а,
   readiness, отчёты, handoff прошлых обрывов) на такие дыры — рецензент проверяет только
   свои четыре входных артефакта, остальные не получает.

## Phase 5 — Дефект, который прошёл раньше

Ревью нашло поведение без покрытия пунктом или расхождение, которое должен был поймать гейт
более раннего этапа (готовность задачи, полнота артефактов)? Впиши это в поле «Кандидаты
в запись о дефекте» вердикта — **при любом action, включая retry**: дефект, зачиненный второй
попыткой, всё равно был пропуском листа или гейта. Сами записи заводит `/sdlc-handoff`, собирая
кандидатов по всем отчётам витка; там же человек решает ровно одно из трёх — конструкция,
проверка, принятый риск.

## Выход

- `passed`, `action`, путь к отчёту, число гейтов в `❌`/`⏭`, число пунктов в `❌`/`⚠`.
- При `retry` — `retry_instruction` и номер следующей попытки, следующий шаг `/sdlc-chunk <slug>`.
- При `escalate` — что именно эскалируется и почему автоматический повтор не годится.
- При `continue` — следующий шаг: `/sdlc-chunk <slug>` (следующий chunk), если план оставляет
  ему пункты, иначе `/sdlc-handoff <slug>`.
