# E2E-тест флоу Agent-SDLC

Прогоняет **весь цикл** `/sdlc-intent → … → /sdlc-handoff` на нетривиальной задаче, затем
механически проверяет артефакты и выносит вердикт «что улучшить во флоу».

## Состав

- `fixture/` — сложный код под задачу: планировщик с DAG-зависимостями, приоритетной очередью,
  ретраями с backoff и LIFO-освобождением ресурсов (Python, 16 тестов, `make build` / `make test`).
- `task.md` — задача витка: `SCHED-101` — отмена задач с каскадом на транзитивных зависимых,
  снятием с retry-пробуждения и сохранением инварианта пула. Гоняет ромбы, состояния и ресурсы.
- `answers.md` — записанные ответы человека («Тест-Оператор») на каждую паузу флоу: приёмочный
  лист, набор гейтов, ответы на развилки, критерии одобрения плана и приёмки.
- `run-e2e.sh` — раннер: собирает рабочую копию fixture с git, ставит **глобальные** скиллы
  через `./install.sh` (та же семантика, что у README: бэкап расходящихся версий
  в `~/.claude/sdlc-backup-<время>/`, честная синхронизация), затем гонит этапы через
  `claude -p` (роль человека — `answers.md`, это проговаривается в системном промпте).
  Retry-цикл крутится до бюджета попыток из журнала chunk'а; все значения из артефактов читает
  единственный парсер `flow-verdict.py --print` (включая RESUME-предикаты); verify без нового
  отчёта — немедленный обрыв; обрыв любого этапа всё равно завершается handoff'ом и вердиктом.
- `seed-flow-verdict.py` — самопосев в инструмент: инвертирует по одной проверке `v.check` в копии
  `flow-verdict.py` и ждёт, что корпус покраснеет; выжившие мутанты — проверки без кейса, они
  записываются долгом в `seed-flow-verdict.known.txt` (по одной строке, с причиной), новый
  выживший без строки долга — красный итог.
- `verdict.py` — тонкая обёртка совместимости над носителем логики
  `implementations/claude-code/skills/sdlc-verify/tools/flow-verdict.py` (инструмент скилла,
  исполняющий гейт «Сверка отчёта с набором»). Проверяется механический контракт флоу по
  `.sdlc/<slug>/`: артефакты на месте и непусты, `‹…›` нет, решения человека записаны, попытки
  не затёрты (`attempt-K`), claims сквозные, минимум гейтов включён, каждый включённый гейт
  «этап 6» имеет строку в отчёте. Каждый провал мапится на конкретную слабость флоу.

## Запуск

```bash
test/run-e2e.sh              # полный прогон, ~10–30 минут, тратит токены реальных сессий
test/run-e2e.sh /path/dir    # прогон в заданной директории (для разбора артефактов)
python3 test/verdict.py <run-dir> SCHED-101   # только вердикт по готовым артефактам
```

## Быстрые проверки контракта без модельных вызовов

```bash
./sync-templates.sh --check
python3 -B -m unittest discover -s test -p 'test_state*.py' -v
python3 -B test/run-corpus.py
```

State-тесты проверяют противоречивый зелёный вердикт, вложенные поля, обязательные гейты,
ручные claims, приоритет state над устаревшим Markdown, повреждённый JSON, хеши и границы
evidence-путей. Отдельный случай запускает копию инструмента вне checkout — валидатор и
схемы должны распространяться вместе со скиллом. Их канонический источник —
`implementations/runner-contract/`; `sync-templates.sh` разливает и сверяет установочные копии.
Эти тесты не запускают гейты продукта и не доказывают пригодность конкретной модели.

Старый e2e-раннер использует Markdown-проекции `--print all`. State v1 не содержит всех нужных
ему полей: переход требует адаптера, а не только создания state.json. Ошибка canonical state
не разрешает возврат к Markdown. Глобальная установка для быстрых проверок не нужна.

## Симулятор реализации Runner

Стенд находится в отдельном checkout `Agent-SDLC-Runner`, в `bench/src/simulator`.
Команды выполняются из его корня после установки зависимостей:

```bash
npm run bench:simulate
npm run bench:simulate -- --suite task-loop
npm run bench:simulate -- --suite guided
npm run bench:simulate -- --suite full-flow --output /tmp/agent-sdlc-simulator-report
```

По умолчанию запускается `--suite all`. GPU, облачный API и настоящая модель не нужны;
локальный сценарный HTTP endpoint заменяет модель в полном прогоне `Run`. В остальных
наборах проверяются настоящий `TaskLoopExecutor` и компоненты guided. Покрытие компонентного
набора нельзя считать покрытием всего guided-флоу: граница набора отражается в отчёте.

Для каждого сценария заранее заданы ответы и независимые ожидания событий и состояния
проекта. Скрипт конечен: неожиданный запрос или исчерпание ответов завершают испытание ошибкой.
Положительные контроли проверяют, что защита пропускает корректную работу. Сохранённый след
показывает ход выполнения и первое расхождение с ожиданием; временные проекты и созданное
стендом внешнее состояние рантайма очищаются, конфигурация модели отделена от пользовательской.

Зелёный сценарий может закончиться блокировкой, если именно она ожидается. `ready_for_review`
TaskLoop означает только готовность к ревью; handoff полного SDLC и человеческая приёмка —
другие результаты. Сценарное решение оператора проверяет механику решения, не заменяя
разрешение пользователя. Стенд не даёт гарантии универсальной изоляции произвольных команд
и не измеряет способности модели. Живые прогоны, воспроизведение реальных ответов и
сравнение версий на отложенных задачах учитываются отдельно.

## Регрессионный корпус flow-verdict.py (`flow-verdict-corpus/`, `run-corpus.py`)

Между этой фикстурой (код под задачу) и дорогим `run-e2e.sh` (реальные сессии claude) не было
ничего, что проверяло бы сам парсер артефактов — `tools/flow-verdict.py`. Он написан по живой
markdown-разметке (докстринги `row_glyphs()`/`plan_approved()` ссылаются на конкретные строки
реальных отчётов CV), и три правки §6b подряд 2026-08-27..28 проверялись только ручным прогоном
по пяти виткам CV — без сохранённого следа. `python3 run-corpus.py` — секунды, без сети и токенов:
для каждого кейса в `flow-verdict-corpus/<case>/` (самодостаточный корень с `.sdlc/gates.md` +
`.sdlc/<case>/*`) сверяет вывод `flow-verdict.py --at verify` с зафиксированным `expected.txt`.
Правило то же, что и у любой проверки без кейса, — `SDLC.md` → «Когда дефект проскочил»: правка
`tools/flow-verdict.py` без прогона этого корпуса не коммитится. Кейсы: три исторических
(`attempt-gap`, `gates-placeholder`, `passed-table-mismatch` — по находкам живых витков), зелёный
эталон `green`, по кейсу на ветку вердикта (`plan-unapproved`, `skip-unexcused`, `sdlc-in-scope`,
`gate-enabled-after-report`, `chunk-oversize`, `axes-outcome-dangling`, `axes-quoted-reason`,
`review-md-ignored`), два кейса режима `--at handoff` (`handoff-green`, `handoff-two-loops`) и
`example` — канонический пример репозитория, который не копируется в корпус, а материализуется из
`example/` через `case.json` (`{"mode", "source", "slug"}`; `mode` — verify|handoff, `source` —
каталог с плоскими артефактами). Что корпус НЕ ловит, показывает
`python test/seed-flow-verdict.py --report`.

## Что считается провалом флоу, а не кода

`verdict.py` не проверяет, правильно ли реализована отмена, — это работа гейтов витка.
Он проверяет, что **процесс оставил обещанные следы**: если тесты упали, но
`verification-report-*-attempt-*.md` честно говорит `passed=false` с retry-инструкцией — флоу
исправен. Провал флоу — это отсутствие артефакта, незаписанное решение человека, затёртая попытка,
потерянный claim или включённый гейт без строки.
