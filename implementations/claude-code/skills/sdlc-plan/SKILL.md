## Контракт этапа

- **Вход:** `intent.md`, `readiness.md`, `exploration-report.md`, `clarification-report.md` (если был), `.sdlc/gates.md`
- **Выход:** `plan.md` с полем «Одобрение» и секцией «Контекст-пакет»; `readiness.md` (прогон 2)
- **Паузы человека:** дыры листа и осей (дописывает человек), принятые риски, **одобрение плана**
- **Инструменты:** чтение, `git grep` вызывающих, `git rev-parse` базы, инструменты методологии; оболочка шире не нужна
- **Останов:** прогон 2 «не готова»; задача изменена вне трёх законных правок; одобрения нет
- **Дальше:** `/sdlc-chunk <slug>`

`повторная готовность → подход из найденного → files_to_touch со сверкой → покрытие пунктов → последствия по осям → необратимое → одобрение человека`

Этап 4 из семи. Смета: что трогаем, чем закрываем каждый пункт приёмки.

Предыдущий шаг: `/sdlc-explore` или `/sdlc-ask`. Следующий: `/sdlc-chunk`.

## Phase 0 — Вход и повторная готовность

Читай `.sdlc/<slug>/intent.md`, `.sdlc/<slug>/readiness.md`, `.sdlc/<slug>/exploration-report.md`
и, если он есть, `.sdlc/<slug>/clarification-report.md`. Отчёта разведки нет — плана не строим:
план без карты кодовой базы это план из догадок (исключение — мелкий контур, там разведка
точечная на этапе 5, а планом служит подтверждённая человеком «Что придётся тронуть»).

Прогони **второй прогон готовности** — только то, что могло измениться после прогона 1
(его результат уже стоит в `readiness.md`; гонять неизменяемое второй раз — работа без выхода):

1. блокирующих вопросов без ответа нет — `- [ ] **[блокирующий]**` не встречается;
2. `grep -c '‹' .sdlc/<slug>/intent.md` = 0 — плейсхолдеров не появилось;
3. секция **«Что придётся тронуть» заполнена** — её заполнила разведка; пустая означает,
   что этап 2 не доведён;
4. **примеры пересчитаны**: если после этапа 1 задача менялась (уточнения разведки, ответы
   `/sdlc-ask`), каждый литеральный пример в изменённых или добавленных пунктах пересчитай
   исполнением заново — ошибочный пример в негативном пункте тест подтвердит молча;
5. **структура листа после правок**: лист законно меняется этапами 2–3 — если менялся, проверь
   по изменённым строкам, что у каждого пункта заполнено «Как проверить» (не размытая фраза),
   а счёт пунктов и `[edge]` не упал ниже минимума контура. Пункт, добавленный без процедуры
   проверки, прогон 1 бы забраковал — прогон 2 не имеет права его пропустить.

6. **задача правилась только законно**: `python ~/.claude/skills/sdlc-verify/tools/intent-sections.py --check <корень проекта> <slug>`
   — `legal: false` значит, что секции задачи изменены вне «Что придётся тронуть», «Открытых
   вопросов», дописанных строк листа и секций с новой записью «уточнено с одобрения ‹имя›»; это
   переписанная задача — останов. Уточнение формулировки с одобрения человека записывай в той
   же секции этой фразой с именем — иначе для снимка это переписывание.

Запиши результат в `readiness.md`, секция «Прогон 2», с вердиктом (`scaffold.py … readiness <slug> --run 2`
проставит дату прогона 2). Любой невыполненный пункт — останов, план не строим.

## Phase 1 — Подход и шаги

**Подход** — одно-два предложения: как решаем. Нашёлся на разведке готовый механизм — здесь
сказано, что мы его **используем**, а не пишем свой.

**Шаги** — каждый проверяемое действие. Каждая строка из «Найдено для переиспользования» обязана
превратиться в шаг формы **«использовать `путь:символ`»**. Ненайденный хелпер порождает второй
экземпляр той же логики, который потом ловится ревью как дефект; найденный и проигнорированный —
то же самое, только осознанно. Если решено не использовать найденное — это не молчание, а строка
с причиной.

## Phase 2 — files_to_touch

`files_to_touch` — **не копия** «Что придётся тронуть». Разведка говорит, что придётся тронуть;
план говорит, что **решено** тронуть. Список вправе сузиться или расшириться, но каждое расхождение
объясняется здесь одной строкой:

- путь добавлен сверх разведки → строка «Добавлено сверх разведки» под таблицей с причиной;
- путь из задачи исключён → строка «Из задачи исключено» с причиной. В `files_to_touch`
  он не входит: иначе scope-проверка этапа 6 разрешит правку в файле, который трогать
  не собирались;
- пути `.sdlc/**` в `files_to_touch` не пишутся — артефакты процесса из scope-сверки исключены.

Именно это расхождение и проверяет человек. Потом с `files_to_touch` сверяется настоящий diff —
в обе стороны.

Для каждого шага, меняющего сигнатуру, контракт или видимое поведение существующего символа
(не для новых символов — им вызывающих ещё нет), `Grep` **по всему репозиторию**, не только
по `files_to_touch`, и заполни «Затронутые вызовы/сигнатуры»: кто зовёт символ сейчас, и назван
ли этот вызывающий файл в `files_to_touch`. Не назван — либо допиши его в список (это и есть
«добавлено сверх разведки» с причиной «правка сигнатуры требует правки вызывающего»), либо
объясни здесь же, почему вызывающего трогать не нужно (например, он совместим с новой сигнатурой
без изменений). Шаг «добавляет параметр» без единой строки в этой секции — недоведённый план,
не мелочь: расхождение, найденное на разведке этапа 5 или, хуже, на этапе 6, стоит дороже, чем
`Grep` здесь.

## Phase 3 — Чем закрывается каждый пункт приёмки

На каждый пункт из задачи — строка: чем он будет закрыт (тест или место в коде) и попадает ли
в **этот** chunk. Пункт без строки означает, что chunk его не закрывает: тогда он либо уходит
следующему chunk'у явно, либо план неполон. Новых id не выдумывать — работать строго по id из задачи.

Chunk должен остаться достаточно малым, чтобы его можно было проверить целиком, и «достаточно»
здесь измеримо: **ориентир — до ~400 изменённых строк и до ~8 файлов**. Больше — режь на
несколько chunk'ов и скажи, какие пункты в каком. Ориентир, а не запрет: превышение
законно, если названо в плане строкой «почему этот chunk больше ориентира». Молча выйти за него
нельзя — рецензент вправе вернуть diff как «слишком велик, проверить целиком нечем», и это
самостоятельная причина красного.

Число взято из измерения, а не из вкуса: виток на 1146 строк и 19 файлов прошёл четыре попытки
и дал пять пропущенных дефектов (ретро 2026-08-27, находка X1).

## Phase 3.5 — Полнота листа (если гейт включён)

Если в наборе включена строка **«Полнота приёмочного листа»** — прогони её здесь, до одобрения:

1. выпиши сценарии из текста задачи («Что делаем», требования словами) — у каждого есть claim-id?
2. выпиши **новые публичные контракты**, которые вводят шаги плана: методы, поля, исключения,
   события, экспорты — у каждого есть claim-id?

Дыра — это дыра в задаче, не в плане: покажи её человеку сейчас, когда правка листа стоит
минуту, а не на этапе 6, когда за ней круг реализации и ревью. Человек либо дополняет лист
(законная правка задачи с одобрения), либо явно выносит сценарий в «Чего не делаем».
Статус и список контрактов запиши в секцию «Полнота листа» плана — оттуда его переносит
отчёт приёмки. Гейт выключен — в секции «⏭ — гейт в долге».

## Phase 3.6 — Разбор последствий (если гейт включён)

Строку **«Разбор последствий»** читай в наборе гейтов проекта, а не выводи из того, есть ли
секция в плане. Выключена — удали таблицы секции и оставь `⏭ — гейт в долге`: шесть строк «н/п»
при выключенном гейте это работа без выхода. Включена — прогони здесь, до одобрения, рядом с
полнотой листа.

Пройди шаги плана по шести осям канона и напиши строку на каждую:

| Ось | О чём спрашиваешь у своих же шагов |
|---|---|
| Безопасность | откуда приходит недоверенный вход, кто имеет право на действие, не появился ли секрет или чужие данные в коде, логе или сообщении об ошибке |
| Ресурсы и скорость | как растёт стоимость с объёмом данных, нет ли обращения в базу или по сети внутри цикла, память, таймаут |
| Отказы зависимостей | что произойдёт, когда зависимость недоступна или ответила ошибкой; нужен ли ретрай и безопасен ли повтор |
| Настройки | вводится ли новая настройка: где её умолчание, кто задаёт, что при отсутствии значения |
| Совместимость и данные | меняется ли контракт, схема, формат файла; нужна ли миграция и чем откатывается |
| Наблюдаемость | по чему в проде поймём, что сломалось именно это, а не соседнее |

Ось, затронутую шагом, называй **адресом**: «шаг 3, `src/tariffs.ts:priceFor` — читает
`TARIFF_URL`», а не «влияет на настройки». Механизм, который в проекте уже есть, бери из секции
«Опоры осей» отчёта разведки: исход «используем `app/validate.ts:parseInput`» стоит дороже, чем
«надо бы добавить валидацию».

**На каждую ось — исход, а не совет.** Ровно одно из шести, и у каждого обязан быть
существующий адресат — иначе это то же ключевое слово вместо решения:

- `claim-N` — пункт **уже лежит** в приёмочном листе задачи. Дописывает его **человек**:
  покажи дыру, предложи формулировку, дождись, и только потом ставь id в план. Пункт, вписанный
  за автора, правкой задачи не является; id несуществующего пункта — не исход, а выдумка.
  У нового пункта обязано быть заполнено «как проверить» либо стоять тег `[manual]`: иначе
  этап 6 не сможет его закрыть и уронит вердикт находкой, которую породил этот же разбор;
- `инвариант` — записан в задачу и назван парой «утверждение + чем проверяется»;
- `гейт «‹имя дословно›»` — строка с этим именем в наборе **включена**. Включение — решение
  человека с записью в журнале набора (дата, причина, кто утвердил). Заполни ей и колонку
  «Чем реализован»: включённый гейт этапа 6 без команды и без встроенной реализации не даёт
  стартовать следующему этапу — «исполнить нечем» ловится на входе, а не в конце витка;
- `риск` — строка в таблице принятых рисков плана: что может пойти не так, почему допустимо
  сейчас и **когда вернуться**. Подписи в строке нет: риски человек принимает полем
  «Одобрение», одобряя план целиком, — покажи их ему отдельно перед этим;
- `следующий виток` — неблокирующий вопрос **записан** в «Открытых вопросах» задачи;
- `н/п — ‹почему›` — ось не затронута шагами, и причина названа. Пустое `н/п` не годится.

Дыра — та же порода, что у полноты листа: она в задаче, а не в коде, и стоит здесь минуту.
Статус запиши в секцию «Последствия шагов» — оттуда его переносит отчёт приёмки.

Ось объявляется незатронутой **под ответственность**: на этапе 6 рецензент сверяет с diff'ом
и «нет», и заявленные исходы, а объявленная незатронутой ось, которую diff трогает, — это
подтверждённое расхождение и красный вердикт.

## Phase 4 — Необратимые шаги

Выпиши отдельно: миграции, удаление или перезапись данных, внешние вызовы, публикации, письма.
Каждый требует подтверждения человека **перед выполнением** — это записывается в план, а не
вспоминается на этапе 5.

## Phase 5 — Артефакт и одобрение

Разложи бланк — `python ~/.claude/skills/sdlc-verify/tools/scaffold.py <корень проекта> plan <slug>`
(нет установки — `templates/plan.template.md` из директории этого скилла, механику заполни сам):
он сам проставит «База» (`git rev-parse HEAD`), строки `claim-N` в «Чем закрывается» и шесть осей
(или сведёт секцию к `⏭ — гейт в долге` по набору). Заполни содержательное. Плейсхолдеров `‹…›` не оставлять,
пустое — `н/п`. **Повторный виток той же задачи:** `plan.md` уже есть и одобрен — сначала
переименуй его в `plan-v<K>.md` (K — номер редакции) **как есть**, с подписью человека под той
редакцией (поле решения человека не трогается и в архиве), затем разложи новый `plan.md` — поле
«Одобрение» у него пустое до нового решения; инструменты читают только `plan.md`.

Секцию **«Контекст-пакет»** заполни здесь же — стек и команды, конвенции, соседний пример
`путь:символ`, символы для переиспользования. Это артефакт для исполнителя, не сообщение в
чате: `/sdlc-chunk` в следующей сессии прочитает секцию, а не память диалога.

**План одобряет человек.** Покажи ему: подход, шаги, `files_to_touch` с расхождениями против
разведки, покрытие пунктов, исходы разбора последствий — и отдельно те, где предлагается
принять риск, — необратимые шаги. Если сессия в plan mode — бери одобрение через
`ExitPlanMode`; иначе через `AskUserQuestion` с вариантами «одобряю», «правки» (и какие),
«переделать подход».

Получив одобрение, **запиши его в поле «Одобрение» плана — имя и дата** и сними снимок секций
задачи заново — `python ~/.claude/skills/sdlc-verify/tools/intent-sections.py --snapshot <корень проекта> <slug>`:
дописанные по находкам гейтов пункты листа с этого момента — часть неизменяемой задачи; одобрение из файла
записанных ответов (неинтерактивный прогон) помечается там же: «источник: файл ответов». Одобрение, оставшееся
в чате, для следующей сессии не существует: `/sdlc-chunk` проверяет поле в файле, а не память
диалога. Без заполненного поля `/sdlc-chunk` не начинается. Молчание одобрением не считается.
Правки плана после одобрения обнуляют поле — новая редакция одобряется заново.

Одобрением является только явное «одобряю» человека. Любой другой ответ — молчание, общий
fallback («смотри по коду», «реши сам»), уход от вопроса — одобрением НЕ является: поле
«Одобрение» не заполняется, остановись и скажи, что план ждёт решения. Вписать в поле
«одобрено», не получив явного ответа, — значит сочинить решение человека; противоречие
«поле говорит „одобрено“, проза рядом — „одобрения не было“» останавливает следующий этап
(измерено дважды на живом прогоне).

## Выход

- Путь к плану, число шагов, число путей в `files_to_touch`, число пунктов, не покрытых этим chunk'ом.
- Статус одобрения и следующий шаг: `/sdlc-chunk <slug>`.
- Контекст-пакет — секция «Контекст-пакет» плана (стек, конвенции, соседний пример, найденные
  символы); в выходе — ссылка на неё, не пересказ. Качество создаётся на входе, а не инспекцией
  на выходе, и вход обязан пережить сессию.
