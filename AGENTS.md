## Абстрактность материалов проекта

Описывай методологию, инструкции, шаблоны и примеры абстрактно. Это обязательное правило для всех агентов.
Не добавляй сведения о сторонних проектах в файлы этого проекта.
Не указывай их названия, ссылки, пути, номера задач, конфигурации, предметные данные и внутренние детали реализации.
Не копируй такие сведения из issue, комментариев, отчётов, журналов и рабочих примеров.
Для примеров используй нейтральные обозначения и вымышленные данные. Сохраняй технический смысл без привязки к конкретному стороннему проекту.
Перед завершением проверь свой diff. Замени сведения о сторонних проектах абстрактными формулировками.
Упоминай конкретный сторонний проект только по прямому указанию пользователя для текущего изменения.

## Обработка GitHub issue

Когда пользователь просит полный цикл обработки issue, передай выполнение проектному агенту `issue_maintainer`.
Передай репозиторий, номера issue, область и отдельные разрешения на commit, push и закрытие.
Агент изучает issue, исправляет дефект или обосновывает отклонение. Для ревью он вызывает `code_review_all`.
Для явно разрешённых Git-действий он вызывает `commit_push`. Дождись результата и сообщи итог по каждой задаче.
Если агент не может самостоятельно проверить результат, он закрывает issue при разрешённом закрытии и опубликованном исправлении.
Перед закрытием он указывает причину недоступности проверки, выполненные проверки и рекомендации: что проверить, как проверить и какой результат ожидать.
Он явно отмечает непроверенные критерии. Не выдаёт рекомендации за выполненную проверку.
Если роль ещё не загружена, используй `default` с инструкциями из `.codex/agents/issue_maintainer.toml`.
