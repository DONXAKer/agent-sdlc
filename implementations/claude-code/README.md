# Реализация: Claude Code (скиллы + агенты)

Семь этапов [методологии](../../SDLC.md), собранные как скиллы Claude Code, плюс скилл посева,
скилл ретроспективы методологии и четыре субагента с урезанными правами — там, где методология
требует, чтобы ограничение было конструкцией, а не инструкцией.

## Установка

Из корня репозитория методологии — единственная команда (она же используется e2e-раннером):

```bash
./install.sh          # бэкапит расходящиеся глобальные версии и СИРОТ (sdlc-* сущности,
                      # удалённые из репо) в ~/.claude/sdlc-backup-<время>/, затем честно
                      # синхронизирует: удалённые файлы и целые сущности не выживают,
                      # кэш-мусор (__pycache__, .DS_Store, *.pyc) вычищается
./install.sh --check  # только сверить (включая сирот), exit 1 при расхождении
```

Вместе со скиллами и агентами ставится hook `~/.claude/hooks/sdlc-guard.py`. Он держит две границы
конструкцией, пока в `.sdlc/<slug>/` лежит маркер: `.scope.json` — Write/Edit только в
`files_to_touch` (гейт «Граница scope hook'ом», этап 5); `.review-lock` — на время ревью этапа 6
закрыты инструменты записи вне `.sdlc/` и штатные мутирующие команды оболочки; `.claims-lock` —
на время слепого вывода приёмочного листа этапа 2 закрыто чтение `.sdlc/` (запретный список по
тексту команды — сильнее промпта, слабее конструкции). Маркеры ставят и снимают скиллы через
`--lock/--unlock/--scope/--unscope`; действует только активный виток (`.sdlc/.active`). Подключается
в `.claude/settings.json` **проекта** — hook стартует отдельным процессом на каждый вызов
инструмента, глобально платить за это всем проектам незачем:

```json
{"hooks": {"PreToolUse": [{"matcher": "Write|Edit|MultiEdit|NotebookEdit|Bash",
  "hooks": [{"type": "command", "command": "python ~/.claude/hooks/sdlc-guard.py"}]}]}}
```

После этого в любой сессии Claude Code доступен весь цикл:

```
/sdlc-intent → /sdlc-explore → /sdlc-ask → /sdlc-plan → /sdlc-chunk → /sdlc-verify → /sdlc-handoff
```

Плюс `/sdlc-seed` — калибровка гейтов посевом, вне витка, и `/sdlc-retro` — ретроспектива самой
методологии, тоже вне витка. На мелком контуре (критерий — `SDLC.md` → «Мелкий виток») этапы 2–3
схлопываются в точечную разведку этапа 5.

## Как пройти виток: что запускать, когда и с чем

Все скиллы, кроме первого запуска `/sdlc-intent`, принимают один аргумент — slug витка
(из id задачи или короткого имени: `/sdlc-explore PAY-412`). Артефакты живут
в `.sdlc/<slug>/`, набор гейтов проекта — один на репозиторий, в `.sdlc/gates.md`. Правило
сквозное: **нет артефакта — нет шага** — каждый скилл на входе проверяет файлы предыдущего
и при их отсутствии останавливается, а не «продолжает по памяти».

| # | Команда | Когда запускать | Что должно уже лежать в `.sdlc/` | Что появится | Пауза на человеке |
|---|---|---|---|---|---|
| 1 | `/sdlc-intent <slug>` | старт витка; повторно — если задача менялась перед планом | `gates.md` (нет — скилл заведёт) | `<slug>/intent.md`, `<slug>/readiness.md` (прогон 1) | интервью: цель, границы, **приёмочный лист пишет человек** |
| 2 | `/sdlc-explore <slug>` | после вердикта «готова» в `readiness.md` | `intent.md`, `readiness.md` | `exploration-report.md` + заполненная секция «Что придётся тронуть» в задаче | нет |
| 3 | `/sdlc-ask <slug>` | **только если** разведка или задача вскрыли развилки; нет развилок — шаг пропускается без артефакта | `intent.md`, `exploration-report.md` | `clarification-report.md` | ответы на развилки через `AskUserQuestion` |
| 4 | `/sdlc-plan <slug>` | после разведки (и вопросов, если были) | `intent.md`, `readiness.md`, `exploration-report.md` | `plan.md` с заполненным полем «Одобрение», `readiness.md` (прогон 2) | **одобрение плана** — имя и дата в поле файла |
| 5 | `/sdlc-chunk <slug>` | после одобренного плана; повторно — по `retry_instruction` с этапа 6 | `plan.md` с одобрением | `chunk-N-journal.md`, `chunk-N-attempt-K-diff.patch`, `chunk-N-attempt-K-tests.txt` | подтверждение места правки после read-only разведки `sdlc-locator` |
| 6 | `/sdlc-verify <slug> [<n>]` | после каждой попытки chunk'а | diff и вывод тестов попытки | `verification-report-N-attempt-K.md` | нет (эскалация — только если бюджет попыток исчерпан) |
| 7 | `/sdlc-handoff <slug>` | при `passed=true` в отчёте верификации — или при любом обрыве витка раньше | последний `verification-report-*` (при обрыве — что есть) | `handoff.md` с полем «Приёмка», локальный коммит | **приёмка вердикта** и решение о публикации (push/PR — человек) |

Развилки цикла:

- **Этап 6 → этап 5**: `passed=false` — обратно `/sdlc-chunk <slug>`, скилл сам возьмёт
  `retry_instruction` из отчёта и увеличит номер попытки; артефакты попыток не затирают друг
  друга. Исчерпан бюджет итераций — эскалация человеку и выход через `/sdlc-handoff` как обрыв.
- **Несколько chunk'ов**: план может закрываться серией chunk'ов — пары этапов 5–6 повторяются
  (`chunk-2-…`, `chunk-3-…`), пока план не закрыт; `/sdlc-handoff` один, в конце витка.
- **Мелкий контур** (поле «Контур» в задаче): этапы 2–3 не запускаются вовсе — после
  `/sdlc-intent` сразу `/sdlc-plan` (план вырождается в подтверждение «Что придётся тронуть»
  с полем «Одобрение»), затем `/sdlc-chunk` с точечной разведкой внутри. `plan.md` обязателен
  и здесь: без него `/sdlc-chunk` не стартует.
- **Между витками**: `/sdlc-seed` — по расписанию из `gates.md`, никогда во время живого витка;
  `/sdlc-retro` — тоже между витками, по расписанию или когда один и тот же класс отказа
  повторился на двух витках подряд (сигнал из `SDLC.md` → «Когда дефект проскочил»).

Субагенты по ходу цикла (руками их не запускают — их зовут скиллы):

- внутри `/sdlc-explore` — разведчик (одноразовый, general-purpose) и `sdlc-claims`: второй выводит
  приёмочный лист вслепую, для сверки с авторским, — без Bash и инструментов записи по построению;
- внутри `/sdlc-chunk` — `sdlc-locator`: read-only по построению (Read, Grep, Glob), сверяет
  карту плана с реальностью до того, как исполнитель получит права записи;
- внутри `/sdlc-verify` — `sdlc-reviewer`: получает ровно четыре артефакта (задача, план, набор
  гейтов, diff), без рассказа исполнителя, с установкой опровергнуть;
- внутри `/sdlc-retro` — `sdlc-methodologist`: получает корпус методологии и корпус трения
  прошедших витков, ищет расхождения спеки с реализацией и повторяющиеся классы отказов — read-only,
  как `sdlc-reviewer`, не правит файлы методологии.

### Пример: виток PAY-412 (тот же, что в [`example/`](../../example/))

Задача — идемпотентность `POST /api/payments` по заголовку `Idempotency-Key`.

```
/sdlc-intent PAY-412    # интервью → intent.md: цель, границы, приёмочный лист
                        #   (claim-1: повтор с тем же ключом → 200 и тот же платёж, …);
                        #   readiness.md прогон 1: «готова»; ветка sdlc/PAY-412
/sdlc-explore PAY-412   # разведчик находит готовый механизм идемпотентности заказов,
                        #   claims-агент вслепую выводит свой лист → сверка листов,
                        #   exploration-report.md, «Что придётся тронуть»: 4 файла
/sdlc-ask PAY-412       # одна развилка: TTL ключа — из кода не добыть, спросили, закрыли
                        #   ответ в задаче → clarification-report.md
/sdlc-plan PAY-412      # шаги из найденного, files_to_touch со сверкой, чем закрывается
                        #   каждый claim → человек одобряет → plan.md, поле «Одобрение»
/sdlc-chunk PAY-412     # sdlc-locator сверяет 4 файла с планом → человек подтверждает
                        #   место правки → реализация → chunk-1-attempt-1-diff.patch,
                        #   chunk-1-attempt-1-tests.txt, chunk-1-journal.md
/sdlc-verify PAY-412    # перегенерированный diff, сборка, тесты, scope, анти-обход →
                        #   sdlc-reviewer находит дефект → verification-report-1-attempt-1.md,
                        #   passed=false, retry_instruction
```

В `example/` виток на этом честно остановлен — ревью нашло дефект, и это часть примера.
Живой виток пошёл бы дальше: `/sdlc-chunk PAY-412` (попытка 2 по `retry_instruction`) →
`/sdlc-verify PAY-412` → при `passed=true` — `/sdlc-handoff PAY-412`: приёмка человеком,
локальный коммит, `handoff.md`; push и PR — отдельное решение человека.

## Состав

| Скилл | Этап | Артефакт |
|---|---|---|
| `sdlc-intent` | 1. Цель | `intent.md`, `readiness.md` (прогон 1), `gates.md` |
| `sdlc-explore` | 2. Разведка | `exploration-report.md` |
| `sdlc-ask` | 3. Вопросы (условный) | `clarification-report.md` |
| `sdlc-plan` | 4. План | `plan.md` с полем «Одобрение», `readiness.md` (прогон 2) |
| `sdlc-chunk` | 5. Chunk | `chunk-N-journal.md`; `chunk-N-attempt-K-diff.patch`, `chunk-N-attempt-K-tests.txt`, `chunk-N-attempt-K-evidence.json`, `.chunk-N-baseline.json` — их производит `attempt-evidence.py` из `sdlc-verify/tools/`, не агент |
| `sdlc-verify` | 6. Верификация | `verification-report-N-attempt-K.md`; в `tools/flow-verdict.py` — механическая сверка отчёта с набором, claims-цепочки, заполненности и адресатов исходов осей (гейт «Сверка отчёта с набором»); `tools/` — единый ящик инструментов методологии: `sdlc_common.py` (общий разбор), `attempt-evidence.py` (свидетельства, база, сравнение попыток), `gates-preflight.py` (исполнимость набора до попытки), `gates/*.py` (эталонные гейты по JSON-контракту), `base-check.py` (тесты попытки на базе), `scaffold.py` (бланк с механикой), `intent-sections.py` (законные правки задачи), `review-validate.py` (ответ рецензента по схеме verify-review-v1) |
| `sdlc-handoff` | 7. Commit | `handoff.md` с полем «Приёмка», локальный коммит |
| `sdlc-seed` | вне витка | `seed-log.md` |
| `sdlc-retro` | вне витка | `retros/<дата>-<scope>.md` в репозитории методологии |

| Агент | Роль | Инструменты |
|---|---|---|
| `sdlc-claims` | слепой вывод приёмочного листа на этапе 2 — без записи по построению; слепота к `.sdlc/` — hook `--claims-lock`, без hook'а инструкция (см. ограничения) | Read, Grep, Glob |
| `sdlc-locator` | точечная разведка этапа 5 — read-only по построению | Read, Grep, Glob |
| `sdlc-reviewer` | независимый рецензент этапа 6, модель фиксирована: opus | Read, Grep, Glob, Bash |
| `sdlc-methodologist` | независимый разбор самой методологии для `/sdlc-retro`, модель фиксирована: opus | Read, Grep, Glob, Bash, WebSearch, WebFetch |

Внутри `/sdlc-explore` разведчик — одноразовый general-purpose агент с промптом из скилла,
отдельного файла не требует; claims-агент — зарегистрированный `sdlc-claims`.

## Как реализация отображает методологию

- **Нет артефакта — нет шага**: каждый скилл заканчивается записью файла в `.sdlc/<slug>/`
  по шаблону из своей директории `templates/`. Это касается и решений человека: одобрение плана —
  поле в `plan.md`, подтверждение места правки — секция журнала chunk'а, приёмка — поле
  в `handoff.md`, готовность — `readiness.md`. Решение, оставшееся в чате, для следующей сессии
  не существует.
- **Попытки не затирают друг друга**: diff, вывод тестов и отчёт приёмки несут номер попытки
  (`attempt-K`); детект отсутствия прогресса сравнивает сохранённые diff'ы соседних попыток.
- **Этап 6 не доверяет этапу 5**: `sdlc-verify` перегенерирует diff из рабочего дерева, сборку
  и тесты прогоняет сам; файлы исполнителя — только для сверки.
- **Свидетельства производит программа**: патч, вывод тестов и `evidence.json` попытки пишет
  `attempt-evidence.py`, а не исполнитель; файлы без записи инструмента этап 6 свидетельством
  не считает. Контекст-пакет для исполнителя — секция плана, не сообщение в чате.
- **Права на шаг, а не на прогон**: `sdlc-locator` получает урезанный набор инструментов
  во frontmatter, а не обещание в промпте.
- **Автор не рецензирует себя**: `sdlc-verify` передаёт рецензенту ровно четыре артефакта —
  задачу, план, набор гейтов, diff — без рассказа исполнителя и истории его вызовов.
- **Решает человек**: одобрение плана, подтверждение места правки, приёмка вердикта и решение
  о публикации — четыре отдельных вопроса через `AskUserQuestion`, молчание одобрением не считается.

### Неинтерактивный режим (прокси человека)

Для испытаний процесса роль человека может играть файл записанных ответов — норма
`SDLC.md` → «Прокси человека»: каждый взятый из файла ответ помечается в артефакте
«источник: файл ответов», и такой виток не считается приёмкой живого человека. Скиллы
с паузами знают это правило; раннер `test/run-e2e.sh` его проговаривает в системном промпте.

### Признанные ограничения (инструкция, а не конструкция)

Честный список мест, где ограничение держится на промпте, потому что харнесс не умеет строже:

- **`sdlc-claims`** без Bash и записи по построению, но Read у него есть. С подключённым hook'ом
  `sdlc-guard.py` скилл разведки ставит `.claims-lock`, и чтение `.sdlc/` на время Phase 1
  отклоняется всем субагентам — слепота становится конструкцией; без hook'а остаётся запрет в
  промпте («не открывай `.sdlc/`»).
- **`sdlc-reviewer` имеет полный Bash**; Write у него нет по построению. Пока hook `sdlc-guard.py`
  не подключён, «не менять репозиторий» — правило промпта; с hook'ом и маркером `.review-lock`
  штатная запись отклоняется, но это запретный список по тексту команды (`python -c "open(…,'w')"`
  ловится, произвольный интерпретатор — нет), а не доказательство невозможности.
- **`allowed-tools` во frontmatter скиллов** по семантике Claude Code — **предодобрение** на ход
  скилла (инструменты из списка не спрашивают разрешения), а не ограничение: снять инструмент у
  скилла нельзя, только у субагента (`tools:`). Голый `Bash` у `sdlc-chunk`/`sdlc-verify`/`sdlc-seed`
  предодобряет любую команду на весь прогон этапа — это «права на прогон», и принцип «права на шаг»
  здесь держится только hook'ом и субагентами. Таблица прав ниже — то, что реально предодобрено.
- **«более сильная модель»** у рецензента зафиксирована как `model: opus` — если исполнитель сам
  работает на opus или сильнее, превосходство модели не гарантируется.
- **`sdlc-methodologist` тоже имеет полный Bash** (и `WebSearch`/`WebFetch`) — «не мутировать
  репозитории» так же держится на промпте, не на инструментах; Write у него нет по построению.

Кто хочет строже — переводит эти строки в свой набор гейтов как долг с принятым риском.

## Шаблоны и константы

Шаблоны в `skills/*/templates/` — установочные копии канонических из корневого
[`templates/`](../../templates/) репозитория; `skills/sdlc-verify/tools/sdlc-constants.json` —
установочная копия корневого [`sdlc-constants.json`](../../sdlc-constants.json) (минимум гейтов,
оси, умолчание бюджета, таблица вердикта — `flow-verdict.py` читает их оттуда, не из хардкода).
Правки делаются в корне и разливаются скриптом:

```bash
../../sync-templates.sh          # скопировать корень → скиллы
../../sync-templates.sh --check  # только сверить (для CI)
```

## Другие варианты реализации

Методология не привязана к Claude Code: этапы, артефакты и гейты можно собрать на любом
стеке — CI-пайплайн с ручными паузами, другой агентный харнесс, чек-листы в трекере.
Обязательный минимум гейтов — в [`SDLC.md`](../../SDLC.md) → «Набор гейтов проекта».
Новые реализации добавляются соседними директориями в `implementations/`.
