# Agent-SDLC

Как разрабатывать с агентом так, чтобы можно было принять работу. Центральная мысль: **узкое место —
не написание кода, а приёмка.** Человек владеет целью, агент — исполнением.

```
ЦЕЛЬ → РАЗВЕДКА → ВОПРОСЫ → ПЛАН → CHUNK → ВЕРИФИКАЦИЯ → РЕЗУЛЬТАТ И ПЕРЕДАЧА
  ↑                                                                          │
  └──────────────────────────────────────────────────────────────────────────┘
```

## С чего начать

1. Начни с маршрута задачи и открой правила текущего этапа. [Руководство исполнителя](SDLC.md)
   описывает семь этапов. Для разработки инструментов используй [контракт реализации](implementation-contract.md).
2. **[`example/`](example/)** — тот же процесс на живой задаче (Java/Spring), все документные артефакты.
   Виток не принят: ревью нашло дефект, интеграционные тесты не запустились. Артефакты
   этапа 5 (diff и вывод тестов) в пример не включены — они порождаются кодовой базой витка.
3. **[`templates/`](templates/)** — канонические формы документов витка.
   Копии внутри реализаций служат для установки. Изменяй исходные формы, затем запускай
   `python tools/distribution.py sync`, чтобы обновить установочные копии.
4. **[`implementations/`](implementations/)** — готовые реализации методологии на конкретных
   инструментах.
5. **[`model-runs/`](model-runs/)** — результирующие карточки моделей: какая модель какой
   этап тянет, на общей фикстурной задаче, с метриками (время/деньги/скрытые тесты),
   сравнением с эталоном и приложенными артефактами. Матрица «модели × этапы» — в её README.

## Что защищает результат

Дополнительная экспериментальная роль — [наблюдатель за направлением работы](process-quality.md#наблюдатель-за-направлением-работы).
Начальный режим `shadow` сохраняет замечания без влияния на исполнение. Он не заменяет ревью и приёмку.

- Человек задаёт приёмку; предложения ИИ имеют источник и становятся требованиями только после явного утверждения.
- Пункты приёмки имеют процедуры проверки; гейты выполняет программа, результаты относятся к проверенной редакции кода. Дополнительный независимый набор приёмочных тестов можно описать в `acceptance-checks.md`, но наличие бланка само по себе не создаёт защищённого исполнителя. В state-first Runner отдельный набор фиксирует оператор после подготовки независимым проверяющим; Docker-исполнитель использует read-only снимки без сети и Docker socket.
- План фиксирует последствия и принятые риски по правилам SDLC.md. Риски не отменяют пять обязательных гейтов; один файл не означает отсутствия риска. Автоматическая классификация низкого, обычного и высокого риска текущим Runner не заявляется.
- Записанное ограниченное разрешение плана позволяет автономные обратимые действия внутри scope без повторного согласования. Решения о цели, приёмке, разрушительных и внешних действиях остаются у человека.
- Модели допускаются к роли по испытаниям, включая пропуски дефектов и ложные замечания; native tool calling не обязателен при проверяемом исполнителе.
- Новую версию процесса сравнивают с baseline на отложенных задачах; правила меняет человек, а не метрика.

Нормативные детали — в [`SDLC.md`](SDLC.md), прежде всего в этапах 1, 4 и 6 и разделе калибровки. Реализация должна подтвердить эти защиты; наличие требования в документе само по себе не доказывает изоляцию или работоспособность.

Для проверки исполнения без модели в соседнем `Agent-SDLC-Runner` есть стенд
`npm run bench:simulate`: сценарные ответы проходят через настоящие компоненты рантайма.
PASS означает ожидаемое поведение, включая корректную остановку; готовность TaskLoop
к ревью не равна человеческой приёмке полного SDLC. Границы и запуск — в
[`test/README.md`](test/README.md#симулятор-реализации-runner).

## Какие подходы применяются

Ниже перечислены практики, которые действительно закреплены в правилах и артефактах проекта.
Это описание методологии, а не утверждение об автоматизации каждого правила во всех реализациях.

| Подход | Как он применяется |
|---|---|
| **Деминг: PDSA и SoPK** | Guided сохраняет прогноз и факт на Study, накапливает калибровку по модели/конфигурации и не меняет ею вердикт витка: [PDSA](profiles/guided.md#цикл-деминга-plan--do--study--act), [калибровка прогнозов](process-quality.md#калибровка-прогнозов-study). |
| **Операциональные определения и ISO/IEC/IEEE 29148** | Пункт приёмки содержит наблюдение, процедуру и критерий; готовность проверяет необходимость, единичность, однозначность и проверяемость: [этап 1](SDLC.md#1-цель). |
| **Знание о вариации и борьба с tampering** | P-карта различает общие и особые причины по серии не менее 20 измеримых прогонов; один прогон не меняет стандарт: [стабильность вердиктов](process-quality.md#стабильность-вердиктов-по-сериям). |
| **Калибровка проверок и мутационное тестирование** | Посев известного дефекта проверяет чувствительность гейта, а чистый контроль — ложные отказы: [калибровка посевом](process-quality.md#калибровка-гейтов-посевом), [`sdlc-seed`](implementations/codex/skills/sdlc-seed/SKILL.md). |
| **TPS: андон, дзидока и пока-ёкэ** | Агент может честно остановиться с диагнозом без расхода ремонтов; права, формы и гейты предотвращают ошибку конструкцией: [андон](SDLC.md#андон-честная-остановка-с-диагнозом), [poka-yoke](profiles/guided.md#poka-yoke-предотвращение-ошибок-конструкцией). |
| **A3, хансэй и пять почему** | Ретроспектива связывает класс дефекта, системную причину, контрмеру и проверку на одной странице: [норма](process-quality.md#a3-пять-почему-и-ёкотэн), [A3-шаблон](templates/retro-a3.template.md). |
| **Ёкотэн** | Урок считается перенесённым после правки эталона и успешной проверки на несвязанной задаче; остальные уроки остаются открытыми: [протокол переноса](process-quality.md#a3-пять-почему-и-ёкотэн). |
| **Кано** | Оператор видит обязательные проверки, принятую приёмку и дополнительные предложения отдельно. [Классификация](process-quality.md#кано-классификация-и-внимание-оператора) |
| **Инспекции Fagan и независимое ревью** | Другой агент проверяет diff, требования, оси и свидетельства без рассказа исполнителя: [этап 6](SDLC.md#6-верификация). |
| **Синго: проверка у источника и предотвращение ошибок** | Гейты останавливают переход, а выбор конструкции, проверки или принятия риска разбирает пропущенный дефект: [набор гейтов](SDLC.md#набор-гейтов-проекта), [разбор дефекта](SDLC.md#когда-дефект-проскочил). |
| **Теория ограничений и Гудхарт** | Основное ограничение — приёмка; наблюдения не превращаются в квоты, которые ослабляют требования: [обоснование](process-quality.md#почему-так-устроено). |
| **ISO/IEC 25010 и спецификация примерами** | Шесть осей структурируют разбор последствий, а Given–When–Then уточняет многошаговую приёмку: [этап 4](SDLC.md#4-план), [этап 1](SDLC.md#1-цель). |

Six Sigma и формальное соответствие ISO 9001/CMMI проект не заявляет. Границы остальных подходов указаны в [обосновании методологии](process-quality.md#почему-так-устроено).

## Реализации

Для OpenCode доступен [комплект из десяти навыков и четырёх субагентов](implementations/opencode/README.md).
Установи его командой `python implementations/opencode/install-opencode.py <корень проекта>`.
В сессии OpenCode запусти `/sdlc-run slug example; задача: опиши требуемое изменение`.
Команды отдельных этапов перечислены в README комплекта.

Для Qwen Code доступен [комплект из десяти навыков и четырёх субагентов](implementations/qwen-code/README.md).
Установи его командой `python implementations/qwen-code/install-qwen-code.py --project <корень проекта>`.
В сессии Qwen Code запусти `/sdlc-run <slug>` с явным корнем проекта и описанием задачи.

Для Cursor доступен [комплект навыков, агентов и правил](implementations/cursor/README.md).
Установи его командой `python implementations/cursor/install-cursor.py <корень проекта>`.

Выбери реализацию под свой инструмент. Комплекты Codex, Claude Code, Kimi Code и Qwen Code находятся в этом репозитории.
Runner развивается отдельно. Каталог `runner-contract/` содержит контракт и проверяющие инструменты для рантайма.

| Вариант | Что это | Статус |
|---|---|---|
| [Codex](implementations/codex/README.md) | Десять скиллов `$sdlc-*`: общий запуск `$sdlc-run`, семь этапов, посев и ретроспектива. Четыре роли. Установка в проект или домашний каталог | Переносимый Markdown-флоу без Runner. Есть автоматические проверки комплекта. Живой полный виток Codex пока не подтверждён |
| [Claude Code](implementations/claude-code/README.md) | Девять скиллов `/sdlc-*`: семь этапов, посев и ретроспектива. Четыре субагента и hook. Установка в `~/.claude/` | Есть сквозной пример и e2e-раннер. Hook требует подключения в настройках проекта; его ограничения описаны в README реализации |
| [Kimi Code](implementations/kimi-code/README.md) | Десять навыков `/skill:sdlc-*`: общий запуск `/skill:sdlc-run`, семь этапов, посев и ретроспектива. Четыре роли. Установка в проект или домашний каталог | Самостоятельный комплект с автоматическими проверками установки и ZIP. Обнаружение навыков и агентов подтверждено; живой полный виток пока не подтверждён |
| [Qwen Code](implementations/qwen-code/README.md) | Десять навыков `/sdlc-*`: общий запуск `/sdlc-run`, семь этапов, посев и ретроспектива. Четыре роли. Установка в проект (`.qwen/`) или домашний каталог | Самостоятельный комплект с автоматическими проверками установки и ZIP. Обнаружение навыков и агентов подтверждено; живой полный виток пока не подтверждён |
| Agent-SDLC-Runner, отдельный репозиторий | Сервис с UI, политикой доступа, программным запуском гейтов и вычислением вердикта. Поддерживает Claude Agent SDK и собственный цикл вызова инструментов | Результаты запусков опубликованы в [model-runs/](model-runs/). State-first требует явного включения и адаптера; прежние витки автоматически не мигрируют |
| [Контракт Runner](implementations/runner-contract/README.md) | Схемы `state.json`, формат ревью и reference-проверки состояния, свидетельств и вердикта | Это контракт для исполнителя. Изоляцию, запуск команд и происхождение решений должен обеспечить конкретный рантайм |

В комплектах роли `sdlc-claims`, `sdlc-locator`, `sdlc-reviewer` и `sdlc-methodologist`
отвечают за слепой вывод приёмочного листа, разведку, ревью и разбор методологии.
В Codex, Kimi Code и Qwen Code отдельный агент разделяет контекст, но не создаёт отдельную песочницу.
Защиты Claude Code hook и Runner в переносимые комплекты не входят.

State-first Runner хранит каноническое состояние в `state.json`.
Независимая приёмка использует защищённый набор проверок и одноразовые Docker-контейнеры.
Границы протокола описаны в [контракте Runner](implementations/runner-contract/README.md).

Другие варианты — CI-пайплайн с ручными паузами, другой агентный харнесс, чек-листы в трекере —
добавляются соседними директориями: методология одна, отличается только то, чем именно построены
гейты и кто держит артефакты.

## Артефакты витка

Правило одно: **нет артефакта — нет шага.** «Я исправил» без diff не принимается.

|---|---|---|
| _(до витка)_ | набор гейтов проекта | [`templates/gates.template.md`](templates/gates.template.md) |
| _(вне витка)_ | одностраничный A3 ретроспективы и реестр ёкотэн | [`templates/retro-a3.template.md`](templates/retro-a3.template.md) |
| 1. Цель | задача + результат проверки готовности | [`templates/intent.template.md`](templates/intent.template.md), [`templates/readiness.template.md`](templates/readiness.template.md) |
| 2. Разведка | отчёт разведки | [`templates/exploration-report.template.md`](templates/exploration-report.template.md) |
| 3. Вопросы _(если были)_ | вопросы и ответы | [`templates/clarification-report.template.md`](templates/clarification-report.template.md) |
| 4. План | план с последствиями, принятыми рисками и записанным одобрением; acceptance-checks.md — дополнительный манифест независимой приёмки при наличии соответствующего исполнителя | [`templates/plan.template.md`](templates/plan.template.md), [`templates/acceptance-checks.template.md`](templates/acceptance-checks.template.md) |

## Чем это собирается

Методология не про стек — она задаёт шаги, артефакты и гейты. Минимум, без которого виток
не стартует: команда сборки, команда тестов, сверка diff со списком файлов из плана, проверка
на обход тестов и ревью независимым агентом. Остальное включается поверх; чего ещё нет — живёт в долге набора с подписью.

Готовые комплекты для Codex, Claude Code, Kimi Code и Qwen Code покрывают семь этапов, калибровку гейтов посевом и ретроспективу методологии.
Для мелких правок используй правила раздела «Мелкий виток» в [`SDLC.md`](SDLC.md).
Команды установки приведены ниже.

## Как получить и установить скиллы

Скачай репозиторий через Git:

```bash
git clone https://github.com/DONXAKer/agent-sdlc.git
cd agent-sdlc
```

Также можно скачать **Code → Download ZIP** на GitHub и распаковать архив.
Открой терминал в корне скачанного репозитория.

Для установки без полного репозитория используй архив своего инструмента из
[Releases](https://github.com/DONXAKer/agent-sdlc/releases) или артефактов workflow
[«Комплекты SDLC»](https://github.com/DONXAKer/agent-sdlc/actions/workflows/distribution.yml).
Каждый push в `main` публикует новую сборку в Releases и Packages после успешных проверок.
Тег сборки имеет вид `main-<номер запуска>-<короткий SHA>`. Артефакты также доступны в workflow.
Тег `v<версия>` публикует отдельный версионный релиз.

Внутри комплектов Codex, Kimi Code и Qwen Code установщик лежит в корне. После распаковки перейди в `agent-sdlc-codex/`, `agent-sdlc-kimi-code/` или `agent-sdlc-qwen-code/`
и замени команду установки из соответствующего раздела ниже на `python install-codex.py`, `python install-kimi-code.py` или `python install-qwen-code.py`.
Для Claude Code перейди в `agent-sdlc-claude-code/` и выполни те же команды `bash install.sh`.
Файл `SHA256SUMS` содержит контрольные суммы ZIP.

Те же ZIP архивы публикуются как OCI пакет в GitHub Container Registry:
`ghcr.io/donxaker/agent-sdlc:<тег сборки или релиза>` и `ghcr.io/donxaker/agent-sdlc:latest`.
Для публичного скачивания установи видимость пакета `Public` в настройках пакета после первой публикации.
Если пакет приватный, сначала выполни `docker login ghcr.io` с токеном, которому разрешено чтение пакетов.
Чтобы извлечь комплект, скачай образ и скопируй файлы:

```bash
docker pull ghcr.io/donxaker/agent-sdlc:<версия>
docker create --name agent-sdlc ghcr.io/donxaker/agent-sdlc:<версия>
docker cp agent-sdlc:/packages/agent-sdlc-codex.zip .
docker cp agent-sdlc:/packages/agent-sdlc-claude-code.zip .
docker cp agent-sdlc:/packages/agent-sdlc-kimi-code.zip .
docker cp agent-sdlc:/packages/SHA256SUMS .
docker rm agent-sdlc
```

### Codex

Требуются Python 3.11+, Git и авторизованный Codex с поддержкой пользовательских агентов.
Установщик добавляет десять скиллов и четыре роли. Runner и Bash не нужны.

1. Проверь доступность инструментов:

   ```bash
   python implementations/codex/install-codex.py --doctor
   ```

2. Установи комплект в свой проект. Замени путь на каталог проекта:

   ```bash
   python implementations/codex/install-codex.py --project "/путь/к/проекту"
   python implementations/codex/install-codex.py --project "/путь/к/проекту" --check
   ```

   Для установки всем своим проектам используй пользовательский каталог:

   ```bash
   python implementations/codex/install-codex.py --user
   python implementations/codex/install-codex.py --user --check
   ```

3. Открой новую сессию Codex в целевом проекте и запусти:

   ```text
   $sdlc-run demo Добавить проверку входных данных
   ```

   Для продолжения этого витка вызови `$sdlc-run demo`.

На Windows можно заменить `python` на `py -3.11`, на Linux и macOS — на `python3`.
Проектная установка размещает скиллы в `.agents/skills/`, а роли — в `.codex/agents/` целевого проекта.
При `--user` эти каталоги создаются в домашнем каталоге пользователя.
Отличающиеся файлы сохраняются в `.codex/sdlc-backup-*`. Конфигурация Codex и чужие скиллы сохраняются.

Подробнее: [комплект Codex](implementations/codex/README.md), включая ограничения и проверку установки.

### Claude Code

Требуются Claude Code, Python 3 и Bash с Unix-утилитами. На Windows используй Git Bash или WSL.
Выполни из корня репозитория:

```bash
bash install.sh
bash install.sh --check
```

Установщик размещает девять скиллов, четыре агента и hook в `~/.claude/`.
Прежние отличающиеся версии сохраняются в `~/.claude/sdlc-backup-<время>/`.
Подключи hook в настройках проекта по [инструкции Claude Code](implementations/claude-code/README.md#установка).
Открой новую сессию Claude Code в проекте и начни с `/sdlc-intent demo`.

### Kimi Code

Требуются Python 3.11+, Git и авторизованный Kimi Code с поддержкой пользовательских агентов и навыков.
Установщик добавляет десять навыков и четыре роли.

```bash
python implementations/kimi-code/install-kimi-code.py --doctor
python implementations/kimi-code/install-kimi-code.py --project "/путь/к/проекту"
python implementations/kimi-code/install-kimi-code.py --project "/путь/к/проекту" --check
```

Для пользовательской установки замени `--project ...` на `--user`.
Проектная установка размещает навыки в `.kimi-code/skills/`, а роли — в `.kimi-code/agents/`.
Отличающиеся файлы сохраняются в `.kimi-code/sdlc-backup-*`; чужие навыки, агенты и настройки сохраняются.
Открой новую сессию Kimi Code или выполни `/reload`, затем запусти `/skill:sdlc-run demo` с явным корнем проекта и описанием задачи.
Для продолжения этого витка вызови `/skill:sdlc-run demo` с тем же корнем.

Подробнее: [комплект Kimi Code](implementations/kimi-code/README.md), включая ограничения и проверку установки.

### Qwen Code

Требуются Python 3.11+, Git и авторизованный Qwen Code с поддержкой пользовательских навыков и субагентов.
Установщик добавляет десять навыков и четыре роли.

```bash
python implementations/qwen-code/install-qwen-code.py --doctor
python implementations/qwen-code/install-qwen-code.py --project "/путь/к/проекту"
python implementations/qwen-code/install-qwen-code.py --project "/путь/к/проекту" --check
```

Для пользовательской установки замени `--project ...` на `--user`.
Проектная установка размещает навыки в `.qwen/skills/`, а роли — в `.qwen/agents/`.
Отличающиеся файлы сохраняются в `.qwen/sdlc-backup-*`; чужие навыки, агенты и настройки сохраняются.
Открой новую сессию Qwen Code, затем запусти `/sdlc-run demo` с явным корнем проекта и описанием задачи.
Для продолжения этого витка вызови `/sdlc-run demo` с тем же корнем.

Подробнее: [комплект Qwen Code](implementations/qwen-code/README.md), включая ограничения и проверку установки.

### Как обновить комплект

В исходном клоне выполни `git pull --ff-only`. Затем повтори установку и проверку для выбранного инструмента.
Если скачивал ZIP, скачай свежий архив и запусти установщик из него.
После обновления открой новую сессию агента.

## Сборка комплектов

Этот раздел предназначен для сопровождения репозитория. Выполни команды из его корня.
Требуются Python 3.11+ и Git:

```bash
python tools/distribution.py sync
python implementations/codex/test_package.py
python implementations/kimi-code/test_package.py
python implementations/qwen-code/test_package.py
python check.py
python tools/distribution.py package
```

Команда `sync` обновляет установочные ресурсы Claude Code, копирует общие ресурсы в Codex, Cursor, Kimi Code и Qwen Code,
преобразует навыки Codex для Cursor, Kimi Code и Qwen Code и пересчитывает манифесты Codex, Cursor, Kimi Code и Qwen Code.
Исходные тексты навыков и роли остаются отдельными для каждой реализации.
Команда `package` проверяет актуальность ресурсов и упаковывает текущие файлы.
Она не синхронизирует ресурсы и не запускает полный набор тестов.

Результат в `dist/`:

- `agent-sdlc-codex.zip` — самостоятельный комплект Codex;
- `agent-sdlc-claude-code.zip` — комплект Claude Code с установщиком;
- `agent-sdlc-kimi-code.zip` — самостоятельный комплект Kimi Code;
- `agent-sdlc-qwen-code.zip` — самостоятельный комплект Qwen Code;
- `SHA256SUMS` — контрольные суммы архивов.

Каждый архив содержит `build.json` с ревизией Git, версией и контрольными суммами файлов.
Сборщик использует файлы реализаций и не читает пользовательские каталоги настроек.

Workflow [distribution.yml](.github/workflows/distribution.yml) запускает сборку на Linux, Windows и macOS.
Он публикует артефакты после проверок. При запуске на `main` отдельная задача создаёт PR синхронизации ресурсов, если обнаружены изменения.
Для этого разреши создание pull requests через GitHub Actions в настройках репозитория.

Каждый push в `main` автоматически публикует новую сборку в GitHub Releases и GitHub Container Registry после успешных проверок.
Уникальный тег включает номер запуска и SHA коммита. Повторный запуск обновляет файлы того же релиза.
Версия в manifest при этом не изменяется. Поле `revision` в `build.json` указывает точный коммит.

Для версионного релиза обнови `version` в `implementations/codex/manifest.json` и выполни команды выше.
Сохрани изменения в коммите. Затем создай и отправь тег `v<версия>` для этого коммита.
Workflow проверяет совпадение версии и тега, проверяет актуальность установочных копий, публикует архивы в GitHub Releases и OCI пакет в GitHub Container Registry.

Синхронизация и проверка ресурсов работают через Python без Bash: `python tools/distribution.py check`.
Каталог `dist/` содержит воспроизводимые архивы. При расхождении ресурсов упаковка останавливается.

Список распространяемых файлов задаётся в `distribution-files.json`. Новые ресурсы добавляй в этот список явно.
Синхронизация нормализует распространяемый UTF-8 текст в LF перед расчётом SHA-256.
Удаление затрагивает только файлы из `generated-resources.json`; прочие файлы сохраняются и не включаются в ZIP.

## Разбор заполненных примеров

### [clarification-report](example/clarification-report.md)

- **Шаг состоялся — значит у него есть артефакт.** Развилки вскрыты, человек ответил, отчёт написан.
  Пропустить этап 3 можно только когда разведка не вскрыла развилок вовсе: тогда у шага нет выхода,
  и «Заполненности артефактов» для него не существует. «Развилки были, но отчёт писать не стали» —
  не пропуск шага, а незаполненный артефакт.
- **Вопрос 2 — это найденный пропуск в приёмочном листе, а не риск.** Разведка назвала адрес, человек
  решил, claim появился до кода. Дешевле ровно на один виток, чем если бы то же нашло ревью на этапе 6.
- **Отвеченный вопрос закрывается в задаче, а не только здесь.** Чекбокс `[x]` плюс ответ строкой —
  иначе второй прогон проверки готовности увидит незакрытый пункт.
- **Вопрос 3 стоило задать, а вопрос про поведение guard'а — нет.** Срок жизни ключа для нового
  endpoint'а — решение о политике, его из кода не добыть: код показывает, что делают заказы, а не
  чего хотят от платежей. Факт, который добывается чтением кодовой базы, агент добывает сам.

### [handoff](example/handoff.md)

- **Передача пишется и на обрыве, а не только на коммите.** Виток не принят, коммита нет — но
  следующая сессия начинается не с нуля: yaml-блок и «С чего начинать» дают ей состояние и первый
  шаг без чтения всей папки.
- **Запись о дефекте появилась при `retry`, не дожидаясь зелёного витка.** Кандидата назвал отчёт
  приёмки; пропуск приёмочного листа не исчезает от того, что код починят второй попыткой.
- **Статусы переносятся как есть.** `⏭` у интеграционных тестов — единственный след того, что
  в окружении нет Docker. Подмена на `✅` стирает его, и проблема окружения станет невидимой.
- **Действие выбрал человек.** Агент предложил «добавить пункт и тест»; подпись стоит рядом. Вариант
  «принять риск» закрыл бы класс дефектов, не меняя ничего в системе, — поэтому решать не агенту.
- **Приёмка — поле, не разговор.** Здесь оно заполнено «не принималась — обрыв»; на принятом витке
  тут стоят имя и дата, и следующая сессия может это проверить.

### [verification-report-1-attempt-1](example/verification-report-1-attempt-1.md)

- **Вердикт упал по нескольким разным условиям**, и все они названы в самом вердикте, а не сведены
  к одному. Часть имеет общую корневую причину — нет Docker; расхождение из §2 к ней не относится
  и починкой окружения не закроется.
- **Подтверждённое расхождение роняет вердикт само по себе.** Claim'а на это поведение нет, и
  раньше такая находка не влияла на вердикт вообще — прогон с зелёными гейтами ушёл бы в commit
  с известным дефектом.
- **`⏭` не сворачивается в `✅`, и «не было окружения» — не подпись.** Механизм включён, значит его
  пропуск роняет вердикт; строка неприменимости для этого случая не годится.
- **Статус claim'а выбирается по закреплённому типу доказательства.** Здесь все пункты требуют
  исполняемой процедуры, поэтому без её результата все они `⚠`. Для согласованного статического
  критерия допустим проверенный diff с адресом и наблюдаемым условием.
- **Механизма нет в проекте — это не `⏭` витка.** Каждая строка долга закрыта явно — ручной
  проверкой с именем и датой либо принятым риском с подписью, — и закрыта **в таблице «Долг»
  набора**, а не в этом отчёте. Отчёт на неё ссылается одной строкой в шапке. Незакрытая строка
  уронила бы вердикт так же, как упавший гейт.
- **Риск, принятый на входе, сработал на выходе.** Независимый вывод claims в долге — и именно
  полнота claims подвела. Один пропуск человек нашёл сам на разведке и закрыл вопросом (claim-11),
  второй всплыл только на этапе 6, когда правка уже сделана: повтор при изменившихся лимитах. Второй
  дороже ровно на один виток — за это и платят, когда второго измерения нет.

### [gates](example/gates.md)

Обязательный минимум — первые пять — на месте, поэтому виток стартует. Строки с «вкл = да» и
«этап 6» — ровно те, что перечислены в таблице гейтов отчёта; сверка идёт по именам, числа
не сравниваются. «Интеграционные тесты» — свой гейт проекта, добавленный строкой сверх перечня.

Закрывается здесь, и только здесь — в отчёт витка не переписывается. Дата у ручной проверки —
последний проход; у принятого риска — когда подписали.

В журнале нет и не может быть переводов для механизмов обязательного минимума: у их строк
переключателя нет, а состояние без любого из них — «процесс не сконфигурирован», при котором виток
не стартует. Запись «да → нет» здесь одна, и она показывает направление, ради которого правило
защёлки и существует: гейт выключен решением человека, с причиной, датой и именем, а работа сразу
переехала в долг.

### [exploration-report](example/exploration-report.md)
