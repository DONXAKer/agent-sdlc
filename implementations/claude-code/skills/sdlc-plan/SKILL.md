`повторная готовность → подход из найденного → files_to_touch со сверкой → покрытие пунктов → необратимое → одобрение человека`

Этап 4 из семи. Смета: что трогаем, чем закрываем каждый пункт приёмки.

Предыдущий шаг: `/sdlc-explore` или `/sdlc-ask`. Следующий: `/sdlc-chunk`.

## Phase 0 — Вход и повторная готовность

Читай `.sdlc/<slug>/intent.md`, `.sdlc/<slug>/readiness.md`, `.sdlc/<slug>/exploration-report.md`
и, если он есть, `.sdlc/<slug>/clarification-report.md`. Отчёта разведки нет — плана не строим:
план без карты кодовой базы это план из догадок (исключение — мелкий контур, там разведка
точечная на этапе 5, а планом служит подтверждённая человеком «Что придётся тронуть»).

Прогони **второй прогон готовности** — только то, что могло измениться после прогона 1
(его результат уже стоит в `readiness.md`; гонять неизменяемое второй раз — работа без выхода):

1. блокирующих вопросов без ответа нет — `- [ ] **[блокирующий]**` не встречается;
2. `grep -c '‹' .sdlc/<slug>/intent.md` = 0 — плейсхолдеров не появилось;
3. секция **«Что придётся тронуть» заполнена** — её заполнила разведка; пустая означает,
   что этап 2 не доведён;
4. **примеры пересчитаны**: если после этапа 1 задача менялась (уточнения разведки, ответы
   `/sdlc-ask`), каждый литеральный пример в изменённых или добавленных пунктах пересчитай
   исполнением заново — ошибочный пример в негативном пункте тест подтвердит молча.

Запиши результат в `readiness.md`, секция «Прогон 2», с вердиктом. Любой невыполненный пункт —
останов, план не строим.

## Phase 1 — Подход и шаги

**Подход** — одно-два предложения: как решаем. Нашёлся на разведке готовый механизм — здесь
сказано, что мы его **используем**, а не пишем свой.

**Шаги** — каждый проверяемое действие. Каждая строка из «Найдено для переиспользования» обязана
превратиться в шаг формы **«использовать `путь:символ`»**. Ненайденный хелпер порождает второй
экземпляр той же логики, который потом ловится ревью как дефект; найденный и проигнорированный —
то же самое, только осознанно. Если решено не использовать найденное — это не молчание, а строка
с причиной.

## Phase 2 — files_to_touch

`files_to_touch` — **не копия** «Что придётся тронуть». Разведка говорит, что придётся тронуть;
план говорит, что **решено** тронуть. Список вправе сузиться или расшириться, но каждое расхождение
объясняется здесь одной строкой:

- путь добавлен сверх разведки → строка «Добавлено сверх разведки» под таблицей с причиной;
- путь из задачи исключён → строка «Из задачи исключено» с причиной. В `files_to_touch`
  он не входит: иначе scope-проверка этапа 6 разрешит правку в файле, который трогать
  не собирались;
- пути `.sdlc/**` в `files_to_touch` не пишутся — артефакты процесса из scope-сверки исключены.

Именно это расхождение и проверяет человек. Потом с `files_to_touch` сверяется настоящий diff —
в обе стороны.

## Phase 3 — Чем закрывается каждый пункт приёмки

На каждый пункт из задачи — строка: чем он будет закрыт (тест или место в коде) и попадает ли
в **этот** chunk. Пункт без строки означает, что chunk его не закрывает: тогда он либо уходит
следующему chunk'у явно, либо план неполон. Новых id не выдумывать — работать строго по id из задачи.

Chunk должен остаться достаточно малым, чтобы его можно было проверить целиком. Не влезает —
режь на несколько chunk'ов и скажи, какие пункты в каком.

## Phase 3.5 — Полнота листа (если гейт включён)

Если в наборе включена строка **«Полнота приёмочного листа»** — прогони её здесь, до одобрения:

1. выпиши сценарии из текста задачи («Что делаем», требования словами) — у каждого есть claim-id?
2. выпиши **новые публичные контракты**, которые вводят шаги плана: методы, поля, исключения,
   события, экспорты — у каждого есть claim-id?

Дыра — это дыра в задаче, не в плане: покажи её человеку сейчас, когда правка листа стоит
минуту, а не на этапе 6, когда за ней круг реализации и ревью. Человек либо дополняет лист
(законная правка задачи с одобрения), либо явно выносит сценарий в «Чего не делаем».
Статус и список контрактов запиши в секцию «Полнота листа» плана — оттуда его переносит
отчёт приёмки. Гейт выключен — в секции «⏭ — гейт в долге».

## Phase 4 — Необратимые шаги

Выпиши отдельно: миграции, удаление или перезапись данных, внешние вызовы, публикации, письма.
Каждый требует подтверждения человека **перед выполнением** — это записывается в план, а не
вспоминается на этапе 5.

## Phase 5 — Артефакт и одобрение

Скопируй `templates/plan.template.md` из директории этого скилла в `.sdlc/<slug>/plan.md`
и заполни, включая поле «База» — текущий `git rev-parse HEAD`. Плейсхолдеров `‹…›` не оставлять,
пустое — `н/п`.

**План одобряет человек.** Покажи ему: подход, шаги, `files_to_touch` с расхождениями против
разведки, покрытие пунктов, необратимые шаги. Если сессия в plan mode — бери одобрение через
`ExitPlanMode`; иначе через `AskUserQuestion` с вариантами «одобряю», «правки» (и какие),
«переделать подход».

Получив одобрение, **запиши его в поле «Одобрение» плана — имя и дата**; одобрение из файла
записанных ответов (неинтерактивный прогон) помечается там же: «источник: файл ответов». Одобрение, оставшееся
в чате, для следующей сессии не существует: `/sdlc-chunk` проверяет поле в файле, а не память
диалога. Без заполненного поля `/sdlc-chunk` не начинается. Молчание одобрением не считается.
Правки плана после одобрения обнуляют поле — новая редакция одобряется заново.

## Выход

- Путь к плану, число шагов, число путей в `files_to_touch`, число пунктов, не покрытых этим chunk'ом.
- Статус одобрения и следующий шаг: `/sdlc-chunk <slug>`.
- Контекст-пакет для исполнителя одним блоком: стек, конвенции, соседний пример, найденные символы.
  Он идёт вместе с планом — качество создаётся на входе, а не инспекцией на выходе.
