## Точная диагностика (второй прогон)

Скрытые тесты, прогнанные вживую против рабочей копии: **7 из 9 зелёные**, включая все три
human-кейса. Красные — оба граничных (сторона ровно 120 см, сумма ровно 300 см — по правилу
«строго больше» ни один не должен считаться негабаритом), и оба падают ОДНОЙ причиной:

```ts
const longest = Math.max(longestSideCm, dimensionSumCm);
const sum = longestSideCm + dimensionSumCm;        // ← прибавляет сторону к сумме ЕЩЁ РАЗ
if (sum > DIMENSION_SUM_LIMIT_CM) return percent(base, SUM_SURCHARGE_PCT);
else if (longest > LONGEST_SIDE_LIMIT_CM) return percent(base, SIDE_SURCHARGE_PCT);
```

Показательно: **модель сама написала верный тест** (`test/oversize.test.ts`, кейсы claim-2 и
claim-4 с ожиданием `0`) — план она прочитала и процитировала правильно, включая тестовые
случаи. Не совпадает с этим текстом только реализация: лишнее сложение/`Math.max` вместо прямого
сравнения параметров с порогами. Однострочная правка чинит оба падения.

Второе, независимое препятствие — бюджет ходов: журнал chunk'а не финализирован
(`исчерпан лимит ходов этапа (25)`), хотя код почти готов.

**`formFill` проверена и не помогла.** Механика дозаполнения журнала по полям подключается
ПОСЛЕ того, как исполнитель естественно завершает ход или исчерпывает бюджет — а эта модель
не завершает ход сама: весь бюджет уходит на сам цикл работы (разведка, чтение, код, тесты,
правки), до финализации журнала дело не доходит вообще, `formFill` не успевает подключиться.
Это противоположно классу `ministral-14b`, которая завершала содержательную работу быстро и
тонула именно в оформлении бланка. Все три измеренных прогона этой модели (без `formFill` и
дважды с ней) упёрлись в один и тот же лимит 25 ходов — узкое место в бюджете, не в оформлении.
Кандидат на следующий замер — `--max-turns` выше, не `formFill`.

## Итог

**Вердикт: ❌ этап 5, но с известным и дешёвым путём к зелёному.** Единственная модель
сессии, где диагноз сведён к одной строке кода плюс бюджету ходов, а не к фундаментальной
неспособности. Первый прогон (без правок раннера) показывал куда более опасный профиль —
правдоподобно доказанная неверная задача; после трёх точечных правок раннера (сверка
импорта, содержимое файла на промахе `Edit`, сверка чисел плана с diff'ом) исход сместился
на честный, локализуемый дефект. `formFill` проверена и откачена — не тот рычаг для этой
модели. Кандидат на следующий замер — `--max-turns` выше 25, вместе с точечной правкой
арифметики.
