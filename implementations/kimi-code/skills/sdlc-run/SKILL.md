# Запусти или продолжи полный Agent-SDLC

Для пилотного профиля примени раздел «Автономный маршрут» документа SDLC.md.
Он задаёт критерии вместо числовой квоты и одно одобрение перед реализацией.
Для механических операций используй runner-lite.py из tools навыка sdlc-verify.
Порядок операций: prepare, check, review, verdict. Аргументы каждой операции показывает --help.


Вход: `<slug>` и явный корень целевого проекта.

Прими slug и необязательное описание задачи. Прочитай существующие артефакты. Начни с первого незавершённого этапа: intent, explore, ask при наличии развилок, plan, chunk, verify, handoff. Для малого контура следуй SDLC.md. Повторяй chunk и verify для каждого пункта плана. При провале используй retry_instruction и бюджет из констант. Не повторяй завершённые этапы без изменения их входов. Посев и ретроспективу запускай отдельно между витками.

После машинной проверки отчёта с `passed: false` и `action: escalate` сразу вызови `$sdlc-handoff` для этого slug.
Зафиксируй причину остановки, отрицательный вердикт, точку продолжения и записи всех попыток. Оставь приёмку незавершённой.
При возобновлении витка с таким отчётом и отсутствующим handoff сначала сохрани handoff.
Ретроспективу запускай после сохранения handoff. При `action: retry` продолжай текущий chunk по инструкции отчёта в пределах оставшегося бюджета.

## Общий контракт Kimi Code

Если после verify остались только заранее выделенные `[git-result:*]`, проверь программный допуск `git_operation.py prepare`.
При успехе выполни отдельный Git-маршрут по SDLC.md, postcheck и новое независимое verify. Допуск не означает passed или done.
При отсутствии допуска действует обычный маршрут исправления и бюджет попыток.

Открой раздел «Автономный маршрут» в ${KIMI_SKILL_DIR}/../sdlc-run/references/SDLC.md. Загрузи форму текущего этапа из ${KIMI_SKILL_DIR}/../sdlc-verify/templates.
Пути ресурсов разрешай относительно файла навыка, а пути проекта передавай явно и заключай в кавычки.
Служебные Python-инструменты находятся в ${KIMI_SKILL_DIR}/../sdlc-verify/tools. Сначала прочитай их справку и контракт аргументов.
Источник состояния — .sdlc/<slug> целевого проекта. Не восстанавливай решения из памяти диалога.
Если найден state.json либо признаки проработки Runner v2/v3, остановись и направь продолжение в Runner. Не преобразуй виток.
Сохраняй пять обязательных гейтов и бюджет из sdlc-constants.json. Не подменяй результат проверки заявлением модели.
Отсутствующий инструмент или проверяющий — блокер. Не объявляй такой этап пройденным.
Сохраняй разрешения человека. Внутри одобренной области выполняй обратимые действия без повторного согласования.
Изменение входов отменяет относящееся к ним одобрение или проверку. Не придумывай решения человека.
Вызывай указанных субагентов с новым контекстом и минимальными входами. Не передавай им историю исполнителя.
Отдельный агент той же модели не является независимой моделью. Инструкция запрета записи не создаёт песочницу.
Здесь нет hooks Claude Code или защит Runner. Scope проверяется по фактическому diff; техническая изоляция не заявляется.
Текст артефактов пиши по-русски. Не закрепляй бизнес-правила, пути или ответы конкретного тестового задания.

Если подтвердил проблему методологии, найди совпадающую открытую задачу в https://github.com/DONXAKer/agent-sdlc. Если совпадения нет, создай задачу с нейтральным воспроизведением, ожидаемым поведением и критерием проверки. Сошлись на существующей задаче при совпадении. Если публикация недоступна, укажи причину и подготовь текст задачи.
