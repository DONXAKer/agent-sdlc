# Контракт реализации Agent-SDLC

## Словари и нормализация

Для совместимости проверка принимает оформленные варианты из `accepted_forms`; они не расширяют смысл вердикта.
Проверяющая сторона нормализует регистр, `ё`→`е`, разметку `* _ \`` и пробелы. Пояснение отделяется только тире.
Свободная формулировка («готова для разведки…», «готова к плану…») вердиктом не является и готовность не даёт.
Скилл и Runner используют один словарь. Расхождение словаря — дефект контракта, а не конкретной задачи.
Для неизвестного значения проверка показывает исходное значение и точные допустимые формы.
Поля «Вкл», исходы осей и классы дефектов используют тот же файл констант.
Их ключи: `gate_switches`, `axis_outcomes` с `axis_outcome_patterns`, `defect_classes` с `defect_class_aliases`.
Проверка нормализует оформление и регистр. Неизвестное значение отклоняется с ожидаемым словарём.

Для исторических классов дефектов применяй только явные соответствия `defect_class_aliases`.
Сохраняй пунктуацию проектных имён. Отклоняй объявление имени, совпадающего с каноническим классом или его alias.
В метриках группируй известные варианты без перезаписи handoff. Для неизвестного имени покажи диагностику и сохрани exit 0.
При проверке новой записи handoff отклоняй неизвестный класс.

## Пакет независимого ревью

Manifest перечисляет claim-ID, путь, SHA-256 исходных байтов, вид, источник получения и ревизию кода.
Ревизия содержит HEAD и SHA-256 патча попытки. При несовпадении сначала проверь применимость и получи новое доказательство.
Допускаются первичные JSON-снимки, stdout, SQL-трассы, изображения, записи WebM и фикстуры. Рассказ, прежнее ревью и история диалога запрещены.
Программа проверяет исходники и байты ZIP. Передавай ZIP с квитанцией целиком: нормализация CRLF/LF нарушает raw SHA-256.
Не читай незаявленные файлы пакета. Manifest подтверждает целостность; достаточность доказательств определяет рецензент.

До передачи пакета сверь manifest с процедурами плана. Если готовый файл пропущен, дополни пакет командой review_evidence.py --extend для той же попытки.
Сохрани предыдущую редакцию. При отсутствии измерения выполни процедуру. При изменении патча получи свидетельство для нового кандидата.

Если передан первичный пакет, до первого ответа reviewer получи проверенную карту командой `review_evidence.py --context <корень> <slug> <N> <K>`.
Producer также сохраняет `chunk-N-attempt-K-review-evidence-context.json` рядом с пакетом.
`evidencePath` — канонический manifest.path для `evidence.path` структурированного ответа.
`archiveMember` — транспортное имя внутри ZIP. Оно используется только для чтения байтов и не является alias.
Не добавляй `files/` к evidence.path. Незаявленные пути и traversal по-прежнему запрещены.
Передавай reviewer карту до первого ответа вместе с ZIP и квитанцией. Ручной рассказ исполнителя её не заменяет.
Непринятый raw-ответ сохраняется валидатором как `chunk-N-attempt-K-rejected-review-SHA256.md` без изменения статусов и находок.
Исправление адреса в следующем ответе не отменяет содержательную находку или продуктовый вердикт.
Дополнительная ссылка находки допустима только для закреплённого файла. Находка также обязана адресовать объект в патче или разрешённом артефакте.

## Квитанции ревью

При успехе программа сохраняет точную побайтовую копию как `chunk-N-attempt-K-review.md`. Исходный файл не изменяется.
Квитанция версии 2 закрепляет `review_path`, `source_review_path`, SHA-256 ответа и патча, chunk и attempt.
Handoff проверяет этот путь и исходные байты. Подмена пути, ответа или патча отклоняется.
Повторная проверка тех же входов не переписывает копию и квитанцию. Изменённые входы требуют новой попытки.
Историческая квитанция версии 1 без пути использует каноническое имя. Её формат и байты не обновляются задним числом.

## Совместимость квитанций prepare

Терминальный prepare выпускает формат v2 с обязательным `contour`. Проверяющий также читает исторический v1 с `contour`.
Архив v1 без `contour` проверяй сохранённым комплектом, выпустившим квитанцию. До обновления сохрани комплект и артефакты побайтово.
При несовместимости используй исходный профиль для исторической проверки. Не переписывай квитанцию и закрепивший её evidence.

## Контекст команды гейта

Если команде нужны значения витка, создай `.sdlc/gate-context.json` с версией `1` и массивом `commands`.
Каждая запись содержит точную строку `command` и объект `inputs`: имя переменной окружения → источник значения.
Источники: `slug`, `chunk`, `attempt`, `patch`, `layer`. Произвольные выражения и значения из окружения не являются источниками.
`slug`, номер chunk и номер попытки задаёт вызов инструмента. `patch` программа строит из этих значений.
`layer` передавай явно через `--layer` на основании утверждённого плана. Не угадывай слой.
Команда получает входы через окружение; для аргументов используй штатное чтение этих переменных оболочкой команды.

```json
{"version":1,"commands":[{"command":"python check.py","inputs":{"TASK":"slug","PATCH":"patch","LAYER":"layer"}}]}
```

До попытки выполни `attempt-evidence.py preflight <корень> <slug> <chunk> <attempt> --command "python check.py" --layer unit --phase chunk`.
Preflight проверяет конфигурацию и не запускает гейт. Успешный preflight не является результатом гейта.
На этапе chunk команда `write` проверяет входы перед записью попытки и сохраняет фактически переданный контекст в evidence.
Для терминальной квитанции prepare v2 гейты «Scope: файлы вне плана», «Анти-обход тест-гейта» и исполняемые дополнительные гейты этапа 6 требуют квитанцию текущей попытки для статуса `✅`.
Запускай их командой `attempt-evidence.py run-gate <корень> <slug> <chunk> <attempt> --gate "имя из набора"`.
Для двух обязательных patch-гейтов объяви вход `patch` в `gate-context.json` и используй его в команде. Фиксированный путь попытки в команде не допускается.
Квитанция закрепляет команду, код возврата, SHA-256 вывода и патча. Сохрани вывод и квитанцию вместе с evidence.
Инструмент сверяет рабочее дерево с патчем до и после запуска. При изменении кандидата квитанция не выдаётся.
Сборка, тесты, независимое ревью и «Сверка отчёта с набором» используют собственные процедуры Verify.
Исторические квитанции prepare v1 с `contour` проверяются без нового требования к именованным запускам.
Для прочих контекстных команд используй `run-gate --command` и сохраняй фактический вывод и код.
При проверке базы передавай тот же подтверждённый слой через `base-check.py --layer`. Команда получает тот же контекст витка.
Если вход отсутствует или неизвестен, исправь конфигурацию. Не расходуй попытку и не считай гейт выполненным.
Для команд без контекста прежний вызов сохраняется. Контекстные команды обязательно объявляй в контракте.

## Контракт гейт-скрипта

Этот раздел нужен, если вы подключаете собственную программу проверки.
Чтобы Runner мог понять результат, последняя строка её вывода должна содержать JSON со следующими полями:

- `gate` — точное имя из набора.
- `status` — `pass`, `fail` или `skip`.
- `evidence` — пути, hunk или имена тестов для проверки результата.
- `detail` — описание результата.
- `missing_tool` — отсутствующий инструмент. Если нужный инструмент недоступен, используй `skip`, а не `pass`.

Коды возврата: 0, 1 и 3 соответственно.
Claude Code поставляет эталонные скрипты для scope, обхода тестов, секретов, связи тестов с claims и проверки тестов на базе.
Проект может использовать собственные команды с тем же проверяемым контрактом.

## Что обязана делать исполняющая программа

Методологию исполняет человек в терминале или программа-раннер. Реализация должна обеспечивать следующие правила.

1. До запуска этапа скопируй форму артефакта в каталог витка. Существующий файл не перезаписывай.
2. После этапа проверь артефакты на диске. Ответ исполнителя не заменяет проверку.
3. Если файл совпадает с пустой формой, не засчитывай этап.
4. Если выполненный этап не дал содержательного результата, запиши причину, имя и дату. Например: «Вопросов нет».
5. Объяви инструменты и права отдельно для каждого этапа. Не выдавай оболочку этапам, которым достаточно чтения и записи документов.
6. Для внешних инструментов задай разрешительный список на этап. Класс инструмента определяет человек.
7. Читающие внешние вызовы выполняй без паузы. Изменяющие вызовы проводи через одобрение.
8. Разрешай аргумент относительно файловой системы только при явном типе «путь». Сохраняй идентификаторы ресурсов без преобразования.
9. Допускай модель к роли по результатам испытаний. Размер модели, ранг и окно контекста не доказывают пригодность.
10. Патч, вывод тестов и хэши свидетельств создавай программно. Текст, написанный проверяемым агентом, не считай свидетельством.
11. Пустой патч отмечай отдельным результатом. Не приравнивай отсутствие изменений к успешной реализации.
12. Перед существенной перезаписью существующего файла получи решение человека по [правилам этапа 5](SDLC.md#5-chunk).
13. Рецензенту выдай чтение. Если нужна оболочка, ограничь запись средствами среды.
14. Не считай запретный список команд полной изоляцией. В Claude Code `sdlc-guard.py` и `.review-lock` ограничивают штатные изменяющие команды.
15. Механические поля заполняй из фактов рантайма. К ним относятся номера, даты, `base_sha`, бюджеты и результаты команд.
16. Содержательные поля поручай модели. При заполнении по полям обработай все строки списка, а не только строку-образец.
17. Ограничения режима называй явно. Например, режим без вопросов человеку не подтверждает интерактивную проработку.
18. Поля решений человека защищай во всех механизмах заполнения. Используй общий словарь меток из `sdlc-constants.json`.
19. Не передавай модели инструкции для механики, которую выполняет рантайм.

В скиллах используй отдельные строки маркеров. Блоки не вкладывай друг в друга.

- `<!-- runner:skip -->…<!-- /runner:skip -->` — рантайм всегда исключает блок из промпта.
- `<!-- runner:mechanical:‹ключ› -->…<!-- /runner:mechanical -->` — рантайм исключает блок только при наличии реализованной механики.

Ключи механики определяет реализация. Если механика отсутствует, сохрани соответствующее требование в промпте.
